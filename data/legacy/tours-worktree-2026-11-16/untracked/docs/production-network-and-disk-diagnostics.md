# Production: сеть, доступность и место на диске

Короткий runbook для первичной диагностики production. Сначала собираем признаки, затем меняем маршруты или чистим данные. Значения IP и интерфейсов ниже относятся к проверке 2026-11-09; перед использованием их нужно получить заново.

## 1. Если SSH или сайт недоступны

### На Windows: проверить маршрут именно до сервера

```powershell
Find-NetRoute -RemoteIPAddress <SERVER_IP> |
  Format-List IPAddress,InterfaceAlias,DestinationPrefix,NextHop,RouteMetric
Test-NetConnection <SERVER_IP> -Port 22 -InformationLevel Detailed
Test-NetConnection <DOMAIN> -Port 443 -InformationLevel Detailed
```

Смотреть нужно на `InterfaceAlias`, `SourceAddress` и `NextHop`. Успешный TCP connect на 22 не гарантирует, что SSH-обмен продолжится: `Connection timed out during banner exchange` означает, что TCP-соединение установилось, но клиент не получил SSH banner. Проверить маршрут и повторить SSH следует до изменений на сервере.

Если подтверждено, что маршрут через VPN вызывает проблему, а прямой маршрут доступен, можно временно добавить узкий маршрут `/32` через текущий физический шлюз и интерфейс:

```powershell
route add <SERVER_IP> mask 255.255.255.255 <LAN_GATEWAY> metric 1 if <LAN_INTERFACE_INDEX>
```

Адрес шлюза и индекс интерфейса заранее узнать через `Get-NetIPConfiguration`; не копировать исторические значения вслепую. Не добавлять широкий bypass-маршрут и не отключать VPN, если он нужен Codex или другим приложениям. Удаление временного маршрута:

```powershell
route delete <SERVER_IP>
```

### Разделять сетевую и серверную неисправность

Когда SSH доступен, проверить локальные сервисы и ответы приложения отдельно от внешнего маршрута:

```bash
systemctl --no-pager --full status nginx daibilet-web daibilet-api
curl -sS -o /dev/null -w 'web %{http_code}\n' http://127.0.0.1:3001/
curl -sS -o /dev/null -w 'events %{http_code}\n' http://127.0.0.1:3001/events
curl -k -sS -o /dev/null -w 'nginx %{http_code}\n' https://127.0.0.1/
```

Затем проверить домен с клиентского устройства. Если локальные проверки сервера успешны, а внешний запрос с конкретного маршрута зависает, не считать это падением приложения без дополнительных данных.

Для packet capture запускать `tcpdump` одновременно с одной конкретной попыткой клиента, ограничивать время и фильтр по адресу клиента. VPN делит внешний IP между пользователями: совпадение IP без времени и SSH-версии клиента не доказывает, что пакет пришёл от нужной попытки.

### Разбирать crawler 5xx по слоям

1. Найти запрос в `/var/log/nginx/access.log`, перевести время (nginx пишет UTC) и посмотреть тот же интервал в `/var/log/nginx/error.log`.
2. `upstream timed out ... while reading response header from upstream` к `127.0.0.1:3001` означает: nginx подключился к Next, но Next не успел вернуть заголовки. Сверить `journalctl -u daibilet-web` и `journalctl -u daibilet-api`, затем RAM/swap/PSI и нагрузку. Простое увеличение `proxy_read_timeout` причину не исправляет.
3. `connect() failed (111: Connection refused)` к `127.0.0.1:4000` означает, что API в этот момент не слушал порт. Проверить, совпало ли это с явным restart в `journalctl -u daibilet-api`.
4. Повторно проверить каждый URL после восстановления: прежний 504 может смениться на 200, 308 или 404. Это разные результаты; URL, который сейчас даёт 404, нужно отдельно сверить с картой EventPage/исторических адресов.

## 2. Перед очисткой диска

Сначала получить общий размер файловой системы и крупнейшие каталоги:

```bash
df -hT /
lsblk -f
sudo du -xhd1 /var /opt /root /home 2>/dev/null | sort -h
sudo du -xhd2 /opt/daibilet/apps/web/.next 2>/dev/null | sort -h | tail -n 30
docker system df
sudo journalctl --disk-usage
sudo lsof -nP +L1 | head -n 30
```

Для Git-репозитория запускать диагностические команды от владельца репозитория:

```bash
sudo -u deploy git -C /opt/daibilet count-objects -vH
sudo -u deploy pnpm --dir /opt/daibilet store path
```

### Что считать данными, а что кэшем

- Сначала сохранять БД, пользовательские/редакционные данные, изображения, проверочные файлы сайта и активные конфиги.
- Не удалять активные Docker volumes, `.git` packs, текущую сборку Next, резервные копии БД или неизвестные временные файлы ради процента заполнения.
- Next route/fetch/image cache регенерируется, но очистка делает кэш холодным и может увеличить нагрузку/время ответа. Использовать проектный maintenance-скрипт и контролируемый лимит; выяснить, какой systemd timer снова наполняет кэш.
- PNPM store — кэш пакетов, но сначала подтвердить фактический путь, отсутствие install/build-процесса и применить штатный `pnpm store prune` от владельца.
- Перед удалением релиз-копии проверить `systemctl show -p WorkingDirectory -p ExecStart ...`, процессы, symlink-и и маркер деплоя. Дубли могут содержать hardlinks; поэтому `du` по копиям может завышать реально занятые уникальные блоки.
- После очистки сравнить `df -hT /`; сумма `du` по hardlink-дубликатам не равна занятому месту файловой системы. Проверить локальные и внешние HTTP-ответы и systemd-сервисы.
- Не запускать `git gc --prune=now` и не удалять Docker volumes без отдельного анализа владельца данных и резервной копии.

## 3. Снимок проверки 2026-11-09

- Последняя проверка: `/dev/sda1`, ext4, `53G / 77G`, 70% (`df -hT /`). Контрольный источник заполнения — `df`, а не метрика с фиксированной шкалой 80 GB.
- Production cache limits закреплены в `/etc/systemd/system/daibilet-web-disk-maintenance.service.d/cache-limits.conf`: route `1024 MiB`, fetch `512 MiB`, image `512 MiB`. Timer запускает maintenance каждые 15 минут; лимиты применены и проверены через `systemctl show`.
- Применение лимитов удалило 1,543 MiB route cache, 529 MiB fetch cache и 355 MiB image cache. Cache регенерируется по запросам; это может добавить холодные SSR/image cache misses.
- `pnpm store prune` удалил 638 неиспользуемых пакетов (около 1.26 GB). Основной store остался `/opt/daibilet/.pnpm-store`; для prune потребовался отдельный `XDG_CACHE_HOME`, потому что старая временная cache-директория принадлежала root.
- Перед этим диск был около `57G / 77G`; после prune и ограничения кэшей стал `53G / 77G` (70%). Следить, чтобы не пересекать 70% при дальнейшем росте.
- Ранее один запуск pruning удалил около 3.2 GiB route cache и 37 MiB fetch cache. При прежней политике route cache снова вырос примерно до 2.7 GiB: maintenance допускал рост до 5 GiB. Поэтому разовая очистка без постоянной настройки не решала возврат роста.
- `/opt/daibilet/.git` занимал около 7 GiB; это Git history, не build cache. Сначала выяснять происхождение крупных объектов, не переписывать историю.
- Основные Docker volumes были активны и не reclaimable; не удалять.
- Удаление `/opt/daibilet-releases/80acd17f9` не изменило `df`, что указывает на отсутствие освобождённых уникальных блоков (например, из-за hardlinks). Проверять результат через `df`, а не по сумме `du`.
- После применения лимитов локальные и внешние запросы к главной и `/events` возвращали 200; `daibilet-web`, API и nginx активны. Проблема SSH была в маршруте клиента, не в состоянии веб-сервиса.
- В новом разборе access log нашёл 14 nginx 504 за окно 17:40–17:49 UTC; три были от Googlebot. `error.log` подтверждает таймаут ожидания заголовков от Next на `127.0.0.1:3001`, включая страницы, площадки и `/_next/image`. Последний 504 в текущем access log — 17:43 UTC; более поздняя повторная проверка главной и `/events` дала 200. Это временный сбой/замедление web upstream; точная внутренняя причина по имеющимся логам не установлена.
- В тот же день API явно перезапускался по клиентскому запросу в 09:16 и 14:20 UTC; рядом есть `ECONNREFUSED 127.0.0.1:4000` из Next и 502 от nginx. После рестартов API поднялся, текущий `/api/public/landings-catalog` отвечает 200.
- После 504 площадка из алерта сейчас отвечает 308; два точных event URL (`zooteatr...6abbcd...` и `detskii-branch...6abf...`) сейчас дают 404 и `GET /api/public/events/{slug}` отвечает для них `not_found`. У зоотеатра есть соседний адрес с тем же названием и другим ID (`evt_6abbcf87411348d7d5e54067`), который API и Googlebot получили с 200; автоматическую связь/редирект не назначать без сверки Event ID/EventPage.

## 4. Цель по заполнению

Долгосрочная цель проекта — держать корневую файловую систему не выше 70%. Если заполнение растёт, сначала найти источник и настройку, из-за которой он растёт вновь; разовая чистка не закрывает проблему. Любое удаление должно быть ограничено проверенными кэшами/дубликатами, а затем подтверждено новым `df` и smoke-проверкой.
