# AGENTS.md — Daibilet

Правила проекта для любых ИИ-агентов (Cline, Cursor, Codex) и человека.
Читать **до** правок. Ветка-источник для prod: `feat/next-monorepo`.

Этот файл заменяет необходимость держать знания в голове: раньше правила жили
только в `.cursorrules` ветки Cursor, поэтому агент на другой машине их не видел.

## Что это за проект

Маркетплейс событий и экскурсий (daibilet.ru). Каталог + админка + API, покупка
идёт через виджеты Ticketscloud и Teplohod.info.

- pnpm workspace, Node 22.x (`.nvmrc`), pnpm 11.7, `engineStrict: true`
- `apps/web` — Next.js App Router, **это production public**
- `apps/admin`, `apps/backend` — админка и API
- `apps/worker` — фоновые задачи
- `apps/public` — **legacy Vite-фронт**, в CI не собирается, новый функционал сюда не пишем
- `packages/db` — Prisma 7.8, `packages/contracts` — Zod DTO, `packages/config` — tsconfig

## Жёсткие запреты

- **Не включать YooKassa, чеки, возвраты и внутренний checkout в runtime.**
  Они лежат в Prisma как foundation фаз 2-4, но MVP работает widget-first.
- **Не удалять Prisma-миграции** и не редактировать БД руками. Только `pnpm db:deploy`.
- **Не смешивать `ExternalOrder` и `CheckoutOrder`** в одном UI без явного DTO-слоя.
- **Не трогать** finance-хост `.159`, секреты YooKassa, secrets ЛК поставщика.
- **Не коммитить** `.env`, credentials, приватные ключи.
- **Не засорять `D:\coding`.** Корень не под git, поэтому `.gitignore` его не
  защищает. Временные файлы — логи, одноразовые скрипты, выгрузки `tsc`,
  распакованные архивы — только в `D:\coding\_scratch\<дата>\` или в игнорируемый
  путь внутри репозитория, и утилизируются в конце задачи. Секреты (`.env`,
  `metrika.env`, ключи, токены) — **никогда** в корень `D:\coding\` и никогда в
  репозиторий. В корне допустимы только каталоги-репозитории и служебные папки
  (`_rules`, `_scratch`).
- **Не делать force-push** ни на одной ветке, включая `main`.
- **Не затирать** backend/Prisma/TS foundation поверх старого JS-монолита.

## Контент (статьи, лендинги, описания)

Правила из `.cursorrules`, действуют и для других агентов:

- **В пользовательских текстах** (блог, лендинги, UI-копирайт, колонки) **никогда
  не использовать длинное или среднее тире.** Только обычный дефис `-`.
  Длинное тире выдаёт ИИ. Внутренняя документация и комментарии в коде под это
  правило не попадают.
- Модель **не выдумывает факты**. Рерайт переписывает предоставленный текст,
  но цены, время, адреса, наличие билетов и факты о площадках берутся из
  источника. Никогда не «улучшай» числа.
- У любой статьи обязателен blog cover: `apps/public/public/images/blog/{slug}.jpg`
  плюс `coverImageUrl` / `imageAlt` во frontmatter. Запрещены city-placeholder
  и публикация в `PUBLISHED` без файла на диске.
- В теле статьи обязательны **1-2 inline-фото**:
  `[image side=left|right src="/images/blog/{slug}-inline.jpg" alt="…"]`
  (вторая: `{slug}-inline-2.jpg`). Без них не переводить в `PUBLISHED`.
- Колонки (`articleType: column`): бейдж в UI всегда «От автора», в конце статьи
  курсивная подпись одной строкой `{Имя}, штатный корреспондент Дайбилет`
  (имя из `authorName`). Подпись не дублировать в лиде body.
- Батчи рерайтов версионируются в репозитории рядом с каноном, который они
  меняют: `data/teplohod/editorial/`, `data/ticketscloud/editorial/`.

## Git и деплой

Cadence владельца (2026-08-05): работаем локально, **commit + push** после
итерации, **web deploy на live — пачкой раз в сутки или по явному запросу**.
Не гонять полный MSK build после каждого мелкого фикса: агенты конкурируют за
deploy-lock, VPS тратит 10-20 минут на итерацию.

- Docs-only изменения = commit + push **без** деплоя.
- Deploy сразу: live HTTP 500, сломанный критичный хаб-редирект, security,
  launch-blocker.
- Предпочтительный путь: GitHub Actions workflow **Deploy MSK web**
  (CI build + `swap-web-next-artifact.sh`). Fallback:
  `BRANCH=feat/next-monorepo ./deploy/scripts/deploy-prod-next.sh` на MSK.
- Web build и live-каталог — только MSK `201.24.125.184`. SPB `.16` выведен из
  оборота.

**Известные gotchas** (детали и статус в `docs/pipeline-status.md`):

- `deploy-verify`: входной `marker` ищется в HTML **главной**, а маркеры вида
  `data-venue-cta-kind` живут на Venue PDP — своп проходит, шаг падает с
  `ERROR: marker absent`. Проверять надо на URL, где маркер есть.
- `next/font`: тянет шрифты из сети на каждой сборке, CI падает случайно.
- Красный прогон деплоя ≠ плохой деплой: своп идёт **до** верификации, читать
  лог, а не судить по статусу.

## Проверки перед коммитом

```bash
pnpm install --frozen-lockfile

pnpm backend:typecheck      # жёсткий гейт, блокирует CI

pnpm --filter @daibilet/web typecheck   # см. baseline ниже, не блокирует
pnpm web:test:ci            # 231 тест, только веб-пакет
pnpm web:build              # 202 статические страницы
```

`pnpm web:typecheck` даёт **140** ошибок и завершается с ненулевым кодом — это
ожидаемо, гейтом не является. `web:test:ci` гоняет **только** `apps/web`;
общее число по монорепо выше, не искать его в выводе этой команды.

`pnpm web:build` требует БД: поднять `pnpm db:up`, применить `pnpm db:deploy`.
Без БД сборка проходит, но SSG-страницы собираются пустыми — это ловушка,
результат выглядит зелёным.

### Baseline типов

`apps/web` сейчас содержит **140 ошибок типов**, и они не блокируют сборку:
в `apps/web/next.config.ts` стоит `typescript: { ignoreBuildErrors: true }`.
Это осознанное решение, но ошибки копятся незаметно.

- CI считает число в job summary (шаг `Web typecheck (non-blocking baseline)`).
- **Baseline: 140.** Если после твоей правки число выросло — ты добавил
  регрессию, даже если сборка зелёная.
- Снять `ignoreBuildErrors` — отдельной задачей, после того как дойдёт до нуля.
- Основные источники: `src/lib/selected-city.test.ts` (22),
  `src/server/day-route-match.ts` (16), `src/components/DayRoutePanel.client.tsx` (15).

### Next.js 16

- Собран с `--webpack`, см. `apps/web/scripts/next-build.mjs`. Turbopack стал
  дефолтом в Next 16, но не поддерживает `resolve.extensionAlias`, а ~301
  импорт в `apps/backend/src` и `packages` используют ESM-конвенцию
  `from './foo.js'` для `foo.ts`. **Не удаляй webpack-хук** из
  `next.config.ts`, пока не переписаны эти спецификаторы.
- `middleware.ts` переименован в `proxy.ts`, хендлер экспортируется как `proxy`.
  В нём admin basic-auth, www→apex редирект, SEO-заголовки canonical и matcher
  на 44 маршрута. Правки здесь ломают авторизацию админки.
- `revalidateTag(tag)` требует второй аргумент. Используем `{ expire: 0 }`,
  чтобы теги истекали немедленно, как раньше, а не переходили на
  stale-while-revalidate. `updateTag()` документирован, но не виден в типах

- ESLint больше не гоняется на сборке, ключ `eslint` в конфиге удалён.

## Точечные правки через .NET на Windows

Правило появилось после двух сбоев 01.10, оба раза скрипт отработал «успешно»,
а код оказался битым:

1. Скрипт вставил блок с CRLF в файл, оказавшийся в LF. Шесть строк склеились
   в одну, `const isFirstPage` формально исчез, а `robots` ссылался на
   незаявленную переменную.
2. Скрипп искал якорь с CRLF в файле с LF. Якорь не нашёлся, ушло в
   `ANCHOR NOT FOUND` — без падения.

**Перед любой точечной правкой через `[IO.File]` прочитай переносы целевого
файла и подставь те же в строке скрипта:**

```powershell
$t = [IO.File]::ReadAllText($p)
([regex]::Matches($t, "`r`n")).Count   # 0  => файл в LF, скрипт тоже в LF
```

Никогда не подставляй `"`r`n"` в текст, вставляемый в файл, пока это не
проверено. Якорь и вставляемый блок должны использовать **один и тот же** стиль
переносов, иначе либо склейка, либо тихий промах.

Проверка после правки обязательна: распечатать затронутые строки через
`Get-Content` и убедиться, что структура цела, а не судить по «written».

**Скрипты с кириллицей** должны сохраняться в UTF-8 **с BOM**
(`[Text.UTF8Encoding]::new($true)`), иначе Windows PowerShell читает `.ps1` как
ANSI и не может его разобрать. Аналогично: кириллица не проходит через
интерактивную команду PowerShell - искать такие буквы нужно из файла-скрипта с
BOM, а не из строки в терминале.

**Через PowerShell в этой среде недоступно** `ForEach-Object -Parallel`.
Долгие прогоны запускать отдельным фоновым процессом с записью в файл.

## Проверять ключ, а не результат

Перед сравнением двух множеств или чтением поля сначала проверить, что **ключ
одинаково нормализован с обеих сторон**. Одинаковое имя ≠ одинаковое значение.

Если ключ может принимать разные формы (кириллица/латиница, URL с хешем и без,
`ID` против `slug`, «все события» против «будущих»), нормализовать или взять
устойчивый ключ — `id` или координаты. Признак «не совпало» не равен сущности
«не существует».

Пять случаев, где это стоило неверных выводов:

| Ключ | Форма A | Форма B | Что выглядело как проблема |
|---|---|---|---|
| `slug` | кириллица в БД | транслитерация в sitemap | 604 записи «не существуют» |
| `events` | все сессии в DTO | будущие сессии в рендере | 930 страниц `noindex` в карте |
| `isIndexable` | `true` в БД | `noindex` на проде | «карта полна мусора» |
| `canonical` | присутствует | указывает в другое место | «консолидация невозможна» |
| HTTP-код | `308` | тело — страница ошибки | «редирект работает» |

### Порядок работы

1. Проверить форму ключа на 3–5 примерах **до** подсчёта.
2. Прогнать подсчёт.
3. Прогнать подсчёт **вторым независимым способом** и сверить на20 записях.
4. Только после этого строить вывод и план.

Проверять результат дважды бесполезно — нужно проверять **метод**.

### Числа по прода

Числа по индексируемости, краулу и содержимому страниц брать обходом прода, а не
из полей БД: база хранит намерение, рендер решает по факту. Расхождение между ними
— не баг данных, а два уровня правды.
