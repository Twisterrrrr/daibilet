# Покупатель: ЛК и админка

## Фактическое состояние

- `SiteUser` уже хранит аккаунты сайта. Отдельная таблица пользователей в БД не нужна. Гостевой покупатель может не иметь `SiteUser`.
- ЛК `GET /api/account/purchases` собирает внутренние `CheckoutOrder` и внешние `ExternalOrder` через единый DTO. Заказы по `siteUserId` доступны владельцу. Подбор гостевых покупок по email допустим только после подтверждения владения адресом.
- Регистрация сейчас не подтверждает email. До появления проверенного email-сценария сервер не должен присоединять гостевые заказы только по адресу из такого аккаунта. Старый путь `GET /api/account/orders/:id` также требует этого правила.
- Текущий `GET /api/admin/buyers` собирает людей только из внешних заказов. Он не равен реестру `SiteUser`, не содержит внутренних покупателей и может терять строки после архивации внешних заказов.
- В legacy SPBBOATS раздел `admin/site-users` был отдельной read-only проекцией аккаунтов; список сотрудников админки был другой сущностью. Подход с раздельными сущностями стоит сохранить, подсчёт заказов пересчитать по двум каналам.

## Целевой экран «Покупатели»

Один рабочий реестр из `SiteUser` и гостевых идентичностей заказов, а не новая таблица БД. Строка показывает наличие аккаунта, статус подтверждения email, число внутренних и внешних заказов, последнюю покупку и обращения. Контактные данные выдаёт сервер только роли с `orders.pii.read`; всем остальным нужен маскированный DTO. Поиск по номеру заказа и контакту требует отдельного права и журналирования. Карточка связывает заказы, заявки на возврат и обращения, но не исполняет денежные операции одним кликом.

Сопоставление делать по `siteUserId` прежде всего. Email можно использовать для подсказки на стороне оператора и привязки заказа к ЛК лишь после подтверждения адреса. Нельзя автоматически сливать разных людей по имени или телефону. Заказы внешнего и внутреннего канала остаются разными записями, объединёнными read-model DTO.

## Приёмка связи кабинетов

1. Гостевая покупка с email A не видна новому аккаунту A без подтверждения email.
2. Внутренний заказ с `siteUserId=A` виден A, не виден B; билет появляется только после подтверждённой оплаты и выпуска.
3. После подтверждения email A ранее купленный гостевой заказ A появляется в ЛК; B его не видит.
4. Оператор находит оба канала по номеру и видит одинаковые статусы оплаты, билета, возврата и обращения. Поставщик видит только свою часть и маскированные контакты.
5. Запрос возврата покупателя создаёт одну заявку, админ видит её в той же карточке; финальный статус возникает только по подтверждённому финансовому событию.

## Следующие серверные срезы

1. Подтверждение email и безопасная привязка гостевых заказов.
2. Единый admin buyer DTO с пагинацией и серверным поиском; отдельно `account` и `guest`, без второй таблицы пользователей.
3. Права `orders.read`, `orders.pii.read`, `support.read` и аудит чтения PII перед внешними операторами.
4. Сквозной smoke ЛК → заявка → админка → финконтур после подключения YooKassa тестового магазина.
