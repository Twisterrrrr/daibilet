# SEO индексация событий: аудит, фаза 1 - 27.11.2026

## Границы проверки

Проверка read-only. Публичные production API, sitemap и HTML запрашивались
27.11.2026. Локальные Docker PostgreSQL и backend проверялись отдельно.
Миграции, статусы SEO и runtime-правила не менялись.

## Текущее состояние кода

- В основной ветке `cline/2b0e8` на начало работы не было незакоммиченных
  изменений SEO. В Cline оставалась урезанная копия `daibliet` с четырьмя
  файлами, без `seo-indexing.ts` и без migration. Компонент из неё лежал в
  `apps/web/public/src/components/EventPage.tsx`, вне исходников Next.js.
- Текущие сущности каталога используют `Event.isIndexable` и nullable
  `EventOverride.isIndexable`. Для редакционных страниц есть отдельные
  `EventPage.status`, `publishedAt` и `isIndexable`. Поля `seoStatus` и enum
  `SeoStatus` в рабочей Prisma-схеме отсутствуют.
- Публичный `/events/[slug]` строит robots из URL-политики стабильной
  EventPage/legacy alias и доступности расписания. Каталожный sitemap собирает
  канонические ключи публичного API и отдельно добавляет опубликованные
  индексируемые EventPage с привязанными Event.
- Действующая проверка публичного сеанса находится в
  `apps/backend/src/catalog-availability.ts`. Она учитывает отмену, флаг
  активности, статусы продаж, временную границу для уже начавшихся сеансов,
  длительность текущего сеанса и исключение Ticketscloud. Новое правило должно
  использовать именно эти predicates.
- Модель `SourceSyncRun` хранит статус и ошибку запуска на уровне источника.
  Это полезный сигнал, но сама по себе не доказывает состояние каждого Event и
  не сообщает, какие записи были частично затронуты конкретным запуском.

## Production: sitemap и отбор ключей

Повторная сверка выполнена 27.11.2026 по полному обходу публичного API с
`limit=200` и sitemap `/sitemaps/events.xml`. API сообщил `total=3 999`; были
прочитаны все страницы пагинации. Ключ нормализован к
`eventPageIndexableSlug || slug`, как при построении sitemap. Важно: строка
API уже представляет группу `Event`, а не обязательно один исходный слот; её
`groupKey`, `groupedEventsCount` и `upcomingSlots` описывают эту группировку.
Sitemap дополнительно содержит индексируемые опубликованные EventPage, даже
если их slug не выбран представителем группы каталога.

| Показатель | Количество |
|---|---:|
| Строки публичного каталога API | 3 999 |
| Уникальные canonical keys каталога | 3 997 |
| Уникальные URL событий в sitemap | 4 635 |
| Ключи каталога, найденные в sitemap | 3 997 из 3 997 |
| Ключи каталога, отсутствующие в sitemap | 0 |
| URL sitemap, отсутствующие в каталожном API | 638 |

Все 638 URL, которые не совпали с canonical keys каталога, сопоставлены с
production `EventPage`: все 638 существуют, имеют статус `READY`,
`publishedAt`, `isIndexable=true` и хотя бы одну связь `EventPageEvent`.
Распределение числа связанных Event на этих страницах: 615 страниц с одним
Event и 23 страницы с несколькими. Это отдельные адреса стабильных страниц, а
не потерянные строки API и не автоматически лишние URL.

Проверка обратным направлением: в production 1 773 опубликованные индексируемые
EventPage с непустыми связями и 7 пустых индексируемых shell. Пустые shell
исключаются генератором sitemap; в sitemap попали все 1 773 непустые страницы.
Из них 638 дают дополнительные адреса, а остальные 1 135 уже покрыты ключами
публичного каталога. Ещё 201 связанная опубликованная EventPage имеет
`isIndexable=false` и не является источником индексируемого адреса.

Две пары строк каталога имеют один и тот же canonical key, но разные группы:

- два Ticketscloud продукта «Бурлеск-кабаре-шоу Мадам Бум» имеют разные
  `tc-meta` group keys и ведут на одну стабильную EventPage;
- два новогодних продукта имеют разные venue-контексты в `merge` group keys и
  ведут на одну вручную объединённую EventPage.

Это не один и тот же тип объединения: первая пара связана stable page mapping,
вторая - редакционным `mergeGroupKey`. Прежнее описание этих двух совпадений в
первой версии отчёта («группа из 9 и 3 слотов») не соответствует повторно
проверенному live API и заменено этим результатом.

Производственная модель на момент сверки: 42 077 уникальных связей
`EventPageEvent` к Event; среди них 19 075 Event связаны с опубликованными
индексируемыми страницами. Эти числа описывают состав инвентаря страниц, а не
число публичных URL. В частности, нельзя приравнивать один Ticketscloud slot
Event к отдельной индексируемой странице.

## Production: HTML выборка

Проверены 20 URL, равномерно выбранных из 638 sitemap-only адресов. Для всех
получены HTTP 200, `robots: index, follow` и self-canonical. Проверка БД
подтверждает, что вся совокупность 638 адресов является опубликованными
индексируемыми EventPage с инвентарными связями; HTML smoke подтверждает
рендер-результат на выборке.

Это проверка текущего состава sitemap и индексируемости выбранных страниц, не
оценка редакционного качества всех 4 635 страниц и не сравнение с новой моделью
индексации.

## Production: страницы без рерайта и предварительный отбор

Дополнительная read-only сверка production EventPage дала 7 862 записи. По
редакционному маркеру 1 982 страницы имеют активный рерайт: 1 780 опубликованы
с индексированием и 202 опубликованы без него. Остальные 5 880 не имеют этого
маркера и сейчас закрыты на уровне EventPage: 5 879 имеют статус `DRAFT`, ещё
одна имеет статус `READY` и `isIndexable=false`. Это распределение по записям
EventPage, а не по уникальным публичным URL.

Предварительная проверка содержимого и связанных Event дала следующие
множества среди 5 880 записей без рерайта:

| Предварительное условие | EventPage | Доля от 5 880 |
|---|---:|---:|
| Хотя бы один связанный Event проходит текущий фильтр качества и продажи | 3 171 | 53,9% |
| Все связанные Event проходят этот фильтр | 2 946 | 50,1% |
| Разница между вариантами агрегации | 225 | 3,8% |
| Нет текущих связей `EventPageEvent` | 384 | 6,5% |

Фильтр применял признаки `READY`, названия, города, места, содержательного
описания, доступного пути покупки, допустимой цены/бесплатного входа и будущего
активного сеанса. Это диагностический SQL-предикат, а не утверждённое правило
публикации: он не доказывает редакционную ценность каждой страницы и не заменяет
ручную проверку дублей, достоверности источника и canonical.

Из 384 страниц без текущей связи все являются черновыми. В последних revision
snapshot у каждой сохранились ID одного или двух Event; все эти Event существуют
и теперь связаны с другими EventPage. Заметки ревизий указывают на сохранённые
исторические оболочки после объединения связей. Поэтому их не следует считать
потерянными Event или включать в пилот публикации без отдельной проверки.

Подготовлена выборка из 100 записей из более узкого пула после предварительной
проверки точных и нормализованных совпадений идентичности. У всех 100 найдено
соответствие действующему публичному каталогу с будущим предложением и путём
покупки. В парной HTML-проверке 8 стабильных EventPage URL все ответили HTTP 200,
но показали `noindex, follow` и canonical на соответствующий существующий URL
каталожной карточки. Все 8 canonical-адресов также ответили HTTP 200, имели
`index, follow`, self-canonical и присутствовали в sitemap.

В текущем коде публикация индексируемой EventPage переводит canonical на её
стабильный slug; запрос к связанному старому Event URL распознаётся как alias и
получает `noindex`. Поэтому выбранные 100 пригодны для ревью качества, но не
являются корректной контрольной группой перехода `noindex -> index`: в проверенной
паре старый адрес уже индексируем и включён в sitemap. Кандидатов для такого
пилота нужно пересобрать по текущему публичному canonical route, отбирая только
те группы, где именно текущий canonical сейчас закрыт от индексации. Число
2 946 остаётся предварительным количеством подходящих записей EventPage, но не
числом новых индексируемых URL.

Файл [100 кандидатов](./seo-no-rewrite-pilot-100-candidates-2026-11-27.csv)
является списком на ручную проверку контента и идентичности, не распоряжением на
публикацию и не контрольной группой для открытия индексации. Ни статусы
production, ни robots, canonical или sitemap в этой проверке не менялись.

## Начало реализации

Добавлена чистая read-only функция `calculateEventIndexability()` в
`apps/backend/src/event-indexability.ts`. Она принимает известные факты, отдаёт
предложенный статус и причины, учитывает `AUTO / INDEX / NOINDEX`, технические
блокировки, доверие к синхронизации, подтверждённый duplicate review и
существующие правила активного сеанса. При `UNKNOWN` функция сохраняет последнее
подтверждённое решение как `effective`; ничего не записывает и пока не подключена
к публичным robots, sitemap или админке.

## Следующие шаги

1. Зафиксировать единицу решения: индексируется публичный canonical route
   стабильной `EventPage` или legacy Event URL, но не каждая техническая запись
   слота Ticketscloud. Для EventPage сначала агрегировать расписание, офферы,
   качество и sync confidence всех связанных Event; для catalog-only групп
   применять согласованную политику к `groupKey` и её inventory.
2. Разделить подтверждённые связи на `EventPageEvent`, точные provider product
   groups (`metaExternalId` + город и проверки идентичности) и editorial
   `mergeGroupKey`. Название, дата или общий поставщик по отдельности не дают
   основания объединять индексируемые страницы.
3. Сопоставить сохранённые `Event.isIndexable`/`EventOverride.isIndexable` с
   фактически отрендеренными robots/canonical на уровне resolved URL. Отдельно
   учитывать ручные решения, legacy alias/route и неуверенность после sync.
4. После согласования page/group-level политики подготовить preview агрегаты и
   тесты на production-shaped безопасной копии. Новую миграцию пока не
   применять: сначала установить, нужно ли поле `seoStatus` хранить на Event,
   EventPage или обеих сущностях с чёткой иерархией.
5. Подключать единый расчёт к metadata и sitemap только после URL parity,
   контрольной выборки и отдельного пилота; старые URL и сохранённые флаги до
   этого не менять.

Массовое открытие каталога и массовая смена статусов не выполнялись.
