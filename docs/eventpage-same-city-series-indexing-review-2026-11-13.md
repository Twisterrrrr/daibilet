# Повторяющиеся EventPage в одном городе: отдельное SEO-ревью

Дата production-среза: 13 ноября 2026 года. Проверка выполнена read-only. Файлы редакционных батчей пока локальные; в production рерайты из этой новой очереди не записывались.

## Почему нужно отдельное решение

В production есть серии с десятками отдельных EventPage одного города. Для ряда серий совпадают не только названия, но и исходный текст. Если всем таким URL выдать одинаковое индексируемое описание и различать их только датой, адресом или ценой в блоке практической информации, Google и Яндекс могут выбрать одну страницу основной, а остальные исключить из поиска как дубли или малоценные страницы. Это риск индексации и распределения сигналов между URL, а не автоматический «бан» сайта.

Текущая модель `TourGroup` рассчитана на разные города: backend запрещает помещать в одну группу две страницы одного города. Поэтому она не решает задачу повторяющихся сеансов в одном городе.

Первый и второй батчи вместе содержат 60 мастер-текстов для 268 EventPage. Среди них 224 страницы входят в повторные форматы одного города; ещё две EventPage музея Гарри Поттера относятся к разным городам и имеют общий исходник. Третий батч содержит 30 отдельных страниц без пересечения Event ID с первыми двумя. Во всех трёх наборах 90 мастер-текстов, 298 целевых EventPage и 430 уникальных Event ID. Основные тексты прошли проверку: не короче видимого текста оригинала и не менее двух содержательных абзацев. Рерайты, связи, canonical и индексация в production не менялись.

Перед первым батчем шесть совпадающих ID были найдены и заменены на другие события, поэтому один Event ID не попадает в несколько редакционных очередей. «Зоотеатр рептилий» исключён из новой очереди: редакционный текст уже есть как минимум на одной EventPage, а оставшиеся дубликаты нужно учитывать в отдельном аудите, не писать заново.

## Рекомендация

1. **Не открывать все URL повтора индексированию только после копирования одного мастер-текста.** Сначала определить, какая страница должна представлять программу в городе.
2. Для подтверждённой серии в одном городе предпочесть одну EventPage с общим описанием и расписанием будущих сеансов. Остальные URL связывать с ней или объединять только после точной сверки событий, активных слотов, офферов и текущих canonical/redirect правил.
3. Если отдельные страницы действительно описывают разные постановки, составы, места или условия, сохранить самостоятельные описания и индексировать их только при наличии отличимого пользовательского содержания.
4. Для тура между городами оставить отдельную EventPage на город. Общий мастер-текст допустим при добавлении подтверждённого локального контекста; блок других городов должен вести только на опубликованные индексируемые страницы.
5. До отдельного решения сохранить старые URL, связи, canonical и редиректы. Ничего из этого в рамках новой редакционной очереди не изменялось.

## Что требуется подтвердить перед изменением модели

- какой URL считать основным для серии в пределах города;
- безопасно ли собрать несколько текущих EventPage/Event ID под одной страницей и какие старые адреса должны получить 301;
- как показывать ближайшие даты, площадки и цены, если у одной программы несколько площадок в одном городе;
- индексировать ли отдельные показы, если они различаются только датой и ценой;
- как отличать реальную смену программы, состава или площадки от повторного импорта того же события.

До этого ревью батчи могут хранить по одному мастер-тексту на подтверждённую серию, но автоматическое размножение этого текста и массовое включение индексации таких URL приостановлены.
