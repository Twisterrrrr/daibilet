# Персональный доступ, 2FA и подтверждение выплат

Дата решения: 2026-10-24. Область: сотрудники Daibilet, внутренняя админка и finance API. Доступ поставщиков и покупателей остаётся отдельным.

## Решения

1. **Общая Basic Auth не считается персональной защитой.** Сотрудник должен входить под своей учётной записью. Пока персональная сессия не подключена на Next, catalog API и finance API, финансовые действия остаются закрытыми для новых ролей.
2. **2FA обязательна для роли FINANCE и SUPERADMIN до доступа к финансовым данным и операциям.** Базовый фактор второго уровня — TOTP в приложении-аутентификаторе. SMS не использовать как основной второй фактор. В дальнейшем WebAuthn/passkey можно добавить как более устойчивый к фишингу способ.
3. **TOTP секрет хранится только зашифрованным на сервере.** Ключ шифрования хранится отдельно от БД в секретах окружения. Резервные коды создаются одноразово, хранятся в БД только в виде криптографических хешей, каждый код используется один раз.
4. **OTP нельзя принимать повторно.** На аккаунт действуют лимиты попыток и задержки после серии ошибок. Использованный TOTP time-step сохраняется; повторный код в том же периоде отклоняется. Учитывается ограниченное расхождение времени.
5. **Создание запроса выплаты не перемещает деньги и не требует финансового step-up.** Перед одобрением сотрудник повторно подтверждает вход. Перед фактическим исполнением требуется отдельный step-up; входной 2FA сам по себе не является разрешением на перевод.
6. **Подтверждение исполнения привязано к неизменному снимку операции:** payout ID, сумма, валюта, получатель/счёт и версия реквизитов. Любое изменение отзывает challenge и требует нового подтверждения. Challenge одноразовый, короткоживущий, ограничен сотрудником и сессией; повторный запрос идемпотентен.
7. **Одобрение и исполнение - отдельные полномочия и записи аудита.** По умолчанию автор одобрения не может исполнить ту же выплату. Исключение для экстренной процедуры требует отдельной явно включаемой политики, причины и усиленного аудита; не включать его автоматически для SUPERADMIN.
8. **Доказательство выплаты - только подтверждение банка/платёжного провайдера.** Нажатие сотрудником «Подтвердить» не должно само по себе переводить выплату в `paid`; оно инициирует исполнение или фиксирует внешний банковский reference после сверки.

## Модель угроз и ограничения

- TOTP - практичная MFA, но вводимый вручную одноразовый код не защищает от фишингового relay. Для выплат повышенного риска предпочтителен WebAuthn с проверкой origin и challenge, привязанным к конкретной операции. NIST требует ограничивать срок TOTP и не принимать один OTP более одного раза за период; ручные OTP не считаются phishing-resistant. См. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html) и [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238/).
- Повторная авторизация не отменяет RBAC: каждый endpoint всё равно проверяет персональную сессию, permission, статус пользователя и объектную область.
- Секрет TOTP, пароль, OTP, резервные коды и полные банковские реквизиты никогда не попадают в журнал. Для payout audit достаточно ID выплаты, безопасного diff, результата, actor, времени и correlation ID.
- Потеря устройства обрабатывается одноразовым recovery code либо операторской процедурой восстановления с проверкой личности, уведомлением владельца и отзывом всех сессий. Администратор не может тихо сбросить 2FA сотруднику.

## Порядок внедрения

| Этап | Результат | Gate |
|---|---|---|
| A. Персональная личность | Приглашение, пароль, вход, сессия в БД, отзыв, блокировка пользователя, аудит | Два сотрудника имеют разные сессии; suspended и revoked теряют доступ |
| B. Server-side RBAC | Разрешения на Next, catalog API и finance API; неизвестные действия запрещены | Прямые URL/API проверены для всех профилей; сервисный токен без user assertion не авторизует сотрудника |
| C. MFA enrollment | TOTP enrollment и подтверждение, recovery codes, шифрование секрета, single-use и rate limit | Нельзя получить активную финансовую сессию до enrollment; replay и перебор отклоняются |
| D. Financial step-up | Повторная аутентификация на одобрение/исполнение, challenge привязан к immutable payout snapshot | Подмена суммы/получателя аннулирует challenge; повторное исполнение невозможно |
| E. Dual control и банк | Разделение approve/execute, банковский reference/webhook, сверка результата | `paid` только после подтверждённого внешнего факта; actor и события доступны в аудите |

Весь контур сначала реализовать и проверять в локальном тестовом окружении. Не включать рабочий магазин, реальные переводы или продовые секреты в разработческие smoke-тесты.

## Проверенная текущая граница авторизации

| Путь | Текущий механизм | Что нужно изменить |
|---|---|---|
| `/admin/*` в Next | `apps/web/middleware.ts` проверяет общий Basic Auth | Персональная session cookie; middleware пропускает login, backend подтверждает действительность сессии |
| `apps/web/src/server/admin-api-fetch.ts` → catalog backend | Forward входящего Basic `Authorization` | Читать HttpOnly admin session cookie и передавать серверному backend сессию, не сырой credential из браузера |
| `/api/admin/*` в `apps/backend/src/server.js` | Один Basic Auth до dispatch маршрута | На каждом запросе проверить hash сессии, срок, отзыв, `AdminUser.state`, permission и объектную область; default deny |
| Finance read: `admin-orders-data.ts` | Прямой fetch на finance host с `DAIBILET_FINANCE_ADMIN_READ_TOKEN` | Передавать отдельное подписанное короткоживущее утверждение сотрудника поверх service auth; finance самостоятельно проверяет audience, подпись, expiry и permission |
| Finance operation: `admin-order-actions.ts` | Прямой POST с `DAIBILET_FINANCE_ADMIN_OPERATION_TOKEN` | Тот же подписанный actor context, отдельный permission и audit; убрать возможность превратить service token в пользовательский допуск |

Это означает, что один только вход в Next или проверка меню недостаточны. Пока finance bridge не умеет проверять пользователя, финансовые страницы и действия не должны считаться защищёнными персональным RBAC. Не включать staff-сессии для рабочих финансовых ролей до закрытия этапов A-C и read/action guards на finance API.
