## Не закрыто — и почему

### lastmod: события, лендинги, города, площадки

Статьи сделаны end-to-end. Остальные четыре — не «не успел», а разная цена работы:

- **События** — нужна правка главного SQL каталога (`public-catalog.dto.ts`).
  `PublicSessionDto` не имеет `updatedAt`, в выборке его нет: `link."updatedAt"`
  используется только для дедупликации. Это правка самого трафикового запроса,
  ей нужен отдельный заход с проверкой на реальном каталоге, не в конце сессии.
- **Лендинги** — `buildPublicLandingPage` собирает `landing` из правила и данных
  событий (`strength: ready|seed|empty` по `matchCount`). Своей строки в БД нет,
  значит осмысленный `lastmod` = `max(updatedAt)` по contributing-событиям, то
  есть новый агрегат на каждый лендинг.
- **Города и площадки** — то же: у города нет своей даты, нужен `max(updatedAt)`
  по агрегату событий. Для площадок дополнительно нужен срез по `type`.

### Метрика: доступ есть, данных для замера нет

Токен рабочий — вопрос был в параметрах, а не в правах:

```
stat/v1/data принимает ids + metrics, НЕ counters + fields
counters=... -> 403 access_denied (выглядит как нет metrika:read, но это ложь)
ids=...      -> 200
```

Проверено: 131 визит за 2026-08-30..2026-09-29 по всему счётчику.

**Замер Wave 1 методологически невозможен.** 131 визит в месяц на весь сайт,
3660 площадок, из них 12 целевых получают порядка 20-33 визита в месяц суммарно
(2-3 на страницу). При конверсии в CTA 5-10% это 0-0,3 конверсии на страницу.
Отличить эффект от шума на такой базе нельзя в принципе.

**Что использовать вместо:** Search Console — показы и позиции. База нулевая,
любой рост будет виден. CTA-эксперимент на этом объёме не измеряем.

Не решена техническая мелочь: разрез по URL в stat API не работает — имя измерения
отвергается с `4001` (перебрано 15 вариантов), фильтр `ym:s:URL==...` тоже `4003`.
На выводы выше это не влияет, но понадобится, если захотим per-URL цифры.

### Тонкие страницы площадок — главная проблема, не закрыта

Это перевес всё остального. Страницы на 152 слова при 131 визите в месяц на весь
сайт не получают показов вообще, поэтому A/B-раскладка CTA и не имеет смысла
сейчас. Приоритет — наполнение и индексация, а не оптимизация конверсии.

Разведка показала, что проблема не в «мусорных» типах:

- Полный скан 1391 строки `venues.xml` → **0 записей, которые снимает с индексации
  правило по типу** (коммит `b344d1bfc`).
- `pageStatus === PUBLISHED` использовать нельзя: в выборке 19 `CANDIDATE`,
  6 без статуса, **0 `PUBLISHED`**. Такой фильтр обнулил бы карту целиком.
- Пример с полной инверсией вывода: `/venues/base` сначала ответил
  `type: meeting_point`, что читалось как мусорная запись. На деле это BASE,
  концертный зал в «Гигант Конти» (Кондратьевский пр. 44), ~2850 отзывов в Google.
  Тип `concert_hall`, 4 события, `pageStatus: CANDIDATE`, описание пустое.
  То есть 2850 отзывов спроса против 4 событий — страница недозаполнена, и её
  нужно наполнять, а не скрывать.

**Что делать:** найти площадки с заметным спросом и малым числом событий и
наполнять их. Прототип UX/UI — `dbshablon.lovable.app`.
