# Админка Daibilet: операционный план

**Версия:** 2026-10-13. **Цель:** за две рабочие недели получить админку, в которой оператор может найти заказ, обработать обращение и заявку, управлять каталогом и поставщиком без знания внутренней архитектуры. Это план инкрементальной работы в канонической Next-админке, не переписывания приложения.

## 1. Источники и границы

- Канонический интерфейс: `apps/web/app/(admin)/admin` и `apps/web/src/components/admin`. Legacy Vite не развиваем.
- Существующий backend и Prisma остаются источниками данных; UI не должен угадывать статусы или смешивать `ExternalOrder` и `CheckoutOrder` без явной проекции покупки.
- Текущий `docs/admin-lovable-v4-mvp-plan.md` описывает хорошие паттерны каталога. `docs/phase-2-finance-supplier-blueprint.md` задаёт модель поставщика, заявок и расчётов. SPBBOATS служит референсом рабочих сценариев, а не источником кода для прямого переноса.
- Старые фразы в документах о widget-only и запрете checkout относятся к историческому MVP. Пилот Stage 0 с YooKassa уже ведётся; платежные операции меняем только отдельным проверенным срезом.
- Задача двух недель: **операционно рабочий MVP**. Полный SEO cockpit, ЭДО, все API поставщиков, сложная поддержка и массовый merge относятся к следующим этапам. Их места в архитектуре фиксируем сейчас.

## 2. Принципы интерфейса

1. Меню отражает работу человека: продажи, каталог, поставщики, поддержка, контент, система.
2. Каждый счётчик ведёт к точной выборке, а не на общий список.
3. Один объект = одна карточка с историей, связанными объектами, текущим состоянием и допустимыми действиями.
4. Список сохраняет поиск, фильтры, сортировку и страницу в URL; переход в карточку и назад сохраняет контекст.
5. Статусы понятны по-русски; исходные коды API доступны в диагностике, но не заменяют человекочитаемый статус.
6. Действие видно только когда оно допустимо. Перед денежной, публикационной и merge-операцией показываются последствия и подтверждение; результат записывается в аудит.
7. Ошибка API явно отличается от пустого списка. Нет фиктивных нулей и макетных кнопок в рабочей навигации.
8. На мобильном экране меню прокручивается, фильтры доступны, таблица имеет компактное представление; основная операторская работа оптимизирована для desktop.
9. Права и роли вводятся по мере появления реальных пользователей. Не показываем фиктивный RBAC поверх одного Basic Auth.

## 3. Навигация

| Раздел | Экраны | Смысл |
|---|---|---|
| Обзор | Очередь задач, сбои, важные показатели | Что требует действия сегодня |
| Заказы | Единый реестр, карточка покупки, возвраты как сохранённая выборка, поиск покупателя | Продажа и обслуживание покупки |
| Каталог | События, площадки, города, очереди кандидатов и дублей | Полный жизненный цикл каталога |
| Поставщики | Реестр, карточка, заявки, интеграции, баланс/выводы, отчёты/документы | Подключение и обслуживание партнёра |
| Поддержка | Обращения покупателей и поставщиков | Единая очередь коммуникаций |
| Контент | Лендинги, статьи, главная, отзывы | Редакционная работа |
| Система | Импорт, состояние API, диагностика | Технические операции |

В навигации показываем только работающие экраны. Для будущих пунктов есть маршрут в плане, но нет пустых страниц. `ECR` переименовать в «Заявки поставщиков», `Hero` в «Главная страница», `Sources` в «Импорт». «Настройки» с технической справкой убрать из основного меню. Покупатели остаются поиском внутри заказов, пока нет самостоятельного CRM-процесса.

## 4. Ключевые рабочие сценарии

### 4.1 Один реестр заказов

Одна страница и один поиск. Фильтры: статус оплаты/заказа (`ожидает`, `оплачен`, `ошибка`, `отменён`, `возвращён`), канал (`Daibilet`, `Ticketscloud`, `Teplohod`), дата, событие, площадка, поставщик, наличие возврата/проблемы. Быстрый фильтр **«Оплачены»** — одно нажатие; число найденных соответствует той же выборке. Номер заказа, email и номер билета ищутся из одного поля. Фильтры сочетаются предсказуемо, есть явный «Сбросить».

**API-шлюз поставщика — отдельный способ исполнения внутренней продажи.** Покупатель оформляет заказ у Daibilet и платит через наш checkout, а бронь/номер/QR билета выдаёт система поставщика через адаптер API. Такой заказ остаётся `CheckoutOrder` и входит в продажи Daibilet, агентские расчёты и финансовые показатели **один раз**. Он не превращается в импортированный `ExternalOrder` только потому, что у поставщика есть внешний ID. В реестре показывать два независимых признака: «Оплата: Daibilet / внешняя система» и «Билет: Daibilet / API поставщика / виджет». Для API-заказа рядом нужны поставщик, статус передачи/подтверждения, внешний ID, номер билета и последняя ошибка; технические ID открываются в диагностике карточки.

Если покупатель переходит в оплату поставщика, это другой сценарий: подтверждение платежа и возврата приходит от его системы, а не выводится из наличия нашей записи заказа. `sourceKind: internal/external` сегодня описывает источник записи в read model и недостаточен как единственный бизнес-признак. Финансовые фильтры и сводка должны опираться на фактического владельца платежа; способ выпуска билета — отдельный фильтр. Для одного заказа могут быть разные способы исполнения по позициям, поэтому признак исполнения хранится также на уровне строки/`FulfillmentItem`.

Карточка покупки имеет общие блоки: статус и сумма; покупатель; событие/сеанс; билет; платеж; возврат; поставщик; история. Канал определяет доступные операции. Для внутренней покупки деньги и статус берутся из finance, для внешней — из источника. Общая проекция чтения не объединяет две таблицы БД и не создаёт платёжные действия для внешнего заказа. Билет действителен только при подтверждённой оплате и неотменённом состоянии.

Для исполнения через API поставщика факт оплаты не равен факту выпуска: после подтверждения платежа заказ может ждать ответа поставщика. Покупателю не выдаётся действительный билет до подтверждённого выпуска и сохранённого номера/QR; таймаут, повтор и отмена брони требуют идемпотентных операций и отдельного статуса ошибки. Возврат денег и аннулирование билета должны проходить согласованно, с явной очередью ручного разбора при частичном сбое. Правила формата номера/QR, проверки на входе и возврата задаются в паспорте конкретного адаптера.

### 4.2 Каталог как рабочая система

- **События:** список с готовностью и причиной блокировки; карточка с обзором, классификацией, площадкой, расписанием, предложениями/ценами, медиа, SEO, исходными данными и историей. Исходные данные провайдера отделены от наших override. Модератор может перейти к следующему событию той же очереди.
- **Площадки:** отдельные реальные площадки, точки сбора и кандидаты; адреса, алиасы, источники, связанные события, предпросмотр дубля и безопасное объединение. Merge возможен только после списка затрагиваемых ссылок и плана отката.
- **Города:** нормализация географии, связи с площадками и событиями, состояние публичной страницы; не сводить к SEO-тексту.
- **Входящие каталога:** новое событие, новая площадка и изменения существующих объектов попадают в типизированную очередь, затем в соответствующую карточку. Никакой автопубликации импорта или черновика поставщика.

### 4.3 Поставщики и черновики

Нужен отдельный реестр поставщиков с поиском по названию/ИНН/статусу и карточка: договорные и налоговые данные, пользователи, связанные события и площадки, режим управления каталогом, платежные настройки, комиссия, интеграции, продажи, баланс, заявки на вывод, отчёты и документы. На первом этапе часть финансовых блоков может быть только для чтения, но данные не должны быть пустым макетом.

Типизированные входящие:

| Тип | Куда попадает | Проверка |
|---|---|---|
| Новый поставщик | Поставщики → На проверку | Юрданные, договор, пользователи, права и реквизиты |
| Новое событие | Каталог → События → Черновики | Дубль, площадка, расписание, офферы, готовность |
| Изменение события | Каталог → События → Изменения | Diff и конфликт с новой версией источника |
| Новая площадка | Каталог → Площадки → Кандидаты | Совпадение адреса, название, алиасы и события |
| Изменение площадки | Каталог → Площадки → Изменения | Влияние на карточки и публичный URL |

`EventChangeRequest` и админская модерация уже существуют. `CREATE` apply и полноценный путь нового события не считаются готовыми; для заявок площадок и новых поставщиков требуются отдельные контракты. Статусы: черновик → отправлен → на проверке → одобрен/отклонён → применён; ошибку применения показывать отдельно. Поставщик видит решение и комментарий.

### 4.4 API-адаптер поставщика

Разделить **тип адаптера** (код авторизации, синхронизации и нормализации) и **подключение поставщика** (credentials, внешний account ID, выбранные возможности, расписание, правила маппинга). Повторное подключение совместимого API не требует копировать реализацию.

Паспорт подключения: события/площадки/сеансы/цены/остатки; создание и отмена заказа; выпуск, проверка и погашение билета; webhooks или polling; idempotency; лимиты, журнал ошибок и последняя успешная синхронизация. Не все API обладают всеми возможностями; готовность к импорту и готовность к продажам — разные статусы.

Хранить отдельно: внутренний ID билета, видимый номер, внешний ID поставщика, payload QR/штрихкода. Правило номера и кода задаётся поставщиком или адаптером: источник значения, формат, длина, уникальность, повторный выпуск, отмена и считывание. Код заказа не считается номером билета. Перед включением автоматической продажи необходим тест физического или API-считывания и аннулирования.

### 4.5 Поддержка

Единая очередь для покупателя и поставщика: заявитель, канал, тема, связанный заказ/билет/поставщик/событие/площадка, статус, ответственный, приоритет, сроки и история. Первые темы: билет, оплата, возврат, посещение, выплаты, документы, каталог. Обращение не заменяет финансовый `RefundRequest`, а ссылается на него. На двухнедельном этапе достаточно регистрации, классификации, назначения, статусов, заметок и перехода к связанному объекту; почта и полноценный чат — отдельное расширение.

### 4.6 SEO и merge

SEO-показатели и проблемы показывать в карточке объекта: индексация, canonical, title/description, готовность контента, причины исключения из sitemap/лендинга. Позднее агрегировать в «SEO и качество каталога»: отчёты, приоритеты, дубли, история изменений. Merge остаётся действием внутри событий/площадок; отдельный отчёт лишь собирает кандидатов. Массовый merge и автоматические редиректы не входят в первый двухнедельный выпуск.

## 5. План на две рабочие недели

Даты ориентировочные; отсчёт от начала реализации. Каждый день заканчивается небольшим проверяемым срезом, а не накоплением непроверенного UI.

| День | Результат | Гейт |
|---|---|---|
| 1 | Инвентаризация экранов, DTO и маршрутов; согласованная карта статусов заказов и заявок; baseline smoke | Нет неучтённых денежных действий и пустых разделов |
| 2–3 | Меню, названия, удаление устаревших текстов, единые компоненты фильтра/статуса, сохранение URL | Оператор находит нужный раздел за ≤2 перехода |
| 3–5 | Единый реестр заказов и фильтр «Оплачены»; единая карточка покупки и возвратная очередь | Реальные внутренние и внешние заказы проверены; статусы не смешаны |
| 5–7 | Обзор с рабочими очередями; карточка и реестр поставщиков, связи с событиями/площадками | Каждая очередь ведёт к точной выборке, supplier данные из API |
| 7–9 | Каталог: события/площадки/города как рабочие модули; входящие черновиков и изменений там, где backend уже поддерживает процесс | Можно пройти список → карточка → действие → вернуться к выборке |
| 9–10 | Минимальная поддержка или, если backend не готов, контракт+первый рабочий срез; end-to-end smoke и выпуск | Обращение привязано к объекту, есть владелец и история |

**Обязательное ограничение срока:** реалистично закрыть навигацию, заказы, обзор и реестр поставщиков. Полная автоматизация новых черновиков площадок/поставщиков, интеграция почты, API-адаптер и весь SEO/merge cockpit могут требовать следующего цикла. Не помечать их «готово» после одной только формы или маршрута.

## 6. Разделение работы

- **Codex:** этот продуктовый контракт; аудит API и схемы; проекция покупок и статусы; поставщики/финансы/черновики/поддержка на уровне contracts и backend; интеграционные проверки; финальная приёмка.
- **Cline:** Next admin shell, навигация, таблицы, карточки, фильтры и взаимодействия; визуальная проверка desktop/mobile; UI-тексты. Работает поверх согласованных DTO и не меняет финансовую бизнес-логику.
- **Владелец:** приёмка ежедневных сценариев и приоритеты при конфликте сроков; тестовые оплаты/возвраты и юридические реквизиты там, где требуется реальное участие.

Точки интеграции: сначала DTO и статусы, затем UI; изменения `packages/db` и `packages/contracts` отдельным коммитом; не совмещать миграцию БД и широкий UI diff в одном коммите. У каждого среза один ответственный за merge. Ничего не перетирать при параллельной работе с контентными скриптами и public-сайтом.

## 7. Приёмка MVP

1. По номеру заказа или email оператор находит внутреннюю и внешнюю покупку; фильтр «Оплачены» показывает только оплаченные, счётчик и таблица совпадают.
2. Неоплаченный заказ не даёт действительный билет. Возврат меняет отображение заказа и билета; повторная операция не создаёт второй возврат.
3. Заявка поставщика имеет тип, автора, связанный объект, diff/проверку, решение и запись в истории; неподдерживаемый `CREATE` не выглядит как готовая операция.
4. Поставщик находится в отдельном реестре, открывается его карточка, видны связанные события, площадки и доступные расчёты.
5. Из главной очереди можно открыть проблему и вернуться к прежней выборке; API error не изображается нулём.
6. На desktop и mobile ключевые действия доступны без горизонтального поиска по 13 пунктам; статус и следующий шаг понятны без знания `ECR`, `pageStatus` и внутренних кодов.
7. Для нового API поставщика заранее определён паспорт подключения и правила номера/QR билета; это архитектурный результат, не обещание реализованного коннектора за две недели.

## 8. Выпуск и риски

Итерации проверять локально и в preview; выпускать небольшими проверенными пачками по проектному cadence. Перед каждым деплоем сверять свежий `origin/feat/next-monorepo`. Денежные операции, миграции и merge данных требуют отдельной проверки. Главные риски срока: неполный backend для новых черновиков/поддержки, расхождение каталог/finance host, состояние реальных данных и параллельные изменения Cline в `apps/web`. Если срок сжимается, не урезать корректность заказов и возвратов ради видимого числа разделов.

## 9. Первый срез

1. Зафиксировать DTO единой строки покупки и карту статусов для двух каналов.
2. Сделать фильтр «Оплачены» и сохранение всех фильтров в URL.
3. Упростить shell и названия, не показывая пустые будущие экраны.
4. Пройти на реальных тестовых заказах: оплачен, ожидает, ошибка, отменён, возвращён; проверить билет и возврат.

После этого начинать поставщиков и очереди каталога. Это даст измеримую пользу уже в первую неделю.

### Выполнено 2026-10-13

- В finance-проекции `status=paid` теперь объединяет оплаченные статусы (`PAID`, `CONFIRMED`, `FULFILLED` и внешние успешные статусы); проверено интеграционным тестом на внутреннем и внешнем заказе. Финансовый коммит `32532dc5a` на `codex/stage0-admission-ticket-core`.
- В Next-админке добавлен быстрый статус «Оплачены» и экран «Все каналы». Для общей страницы Next запрашивает обе read-модели, сортирует по времени и суммирует точные totals. Если один API недоступен, список явно показывает ошибку и не выдаёт частичную выборку за полную.
- Временное ограничение реализации: для глубокой страницы сервер собирает префикс обеих выборок порциями по 100. Это корректно по порядку, но цена запроса растёт с номером страницы. После операторского MVP нужна локальная материализованная проекция либо cursor API; до этого использовать поиск для старых заказов.
