# PDP событий: админка, ЛК поставщика и переход с импортных URL

**Снимок кода:** 27.10.2026, ветка `feat/next-monorepo`. Это план реализации, а не разрешение на смену canonical, sitemap или массовые редиректы.

Связанная карта URL: [event-pdp-url-correspondence-audit-2026-10-27.md](./event-pdp-url-correspondence-audit-2026-10-27.md). Машинный список текущих адресов: [CSV](./event-pdp-url-map-current-2026-10-27.csv).

## Зафиксированные продуктовые правила

- Событие в продуктовой модели одно; временной слот — `EventSession` внутри события.
- Публично индексируется PDP события. Слот не становится отдельной индексируемой страницей.
- Новые импортированные события должны оставаться доступными посетителям, даже если им требуется редактура. Отдельное правило публикации можно поменять, когда появится штатный редактор.
- Импортированная запись и `metaExternalId` помогают найти возможные соответствия, но сами по себе не дают права объединять события.
- Для проверенного гастрольного события PDP показывает остановки и доступные показы по городам/площадкам. «Васса Железнова» подтверждена владельцем как такой случай.
- «Северная Венеция» — один PDP с выбором причала отправления.
- «Не стоит вызывать его», иммерсивный мастер-класс, оба джазовых мероприятия — самостоятельные PDP. «Проявляйся играя» остаётся кандидатом до отдельного решения.
- Старые URL продолжают отвечать fallback-страницей, пока у соответствия нет готового целевого PDP и проверенного маршрута.
- Тип продажи (разовое, повторяющееся, открытая дата), категория события и источник управления (импорт, Daibilet, API) — разные оси одной сущности.

## Что уже есть в репозитории

- `Event` содержит `kind` (`SINGLE` / `RECURRING` / `OPEN_DATE`), статус, источник управления, slug, SEO-поля, город, площадку и поставщика.
- `EventSession` хранит даты/время и вместимость; `EventOffer` — предложения и тарифы; `ProviderLink` различает идентичность EVENT / SESSION / OFFER / VENUE.
- `EventSourceLink` хранит внешний ID и `metaExternalId`.
- `PdpDocument` содержит редакционные блоки и привязан ровно к одной записи `Event` (`eventId @unique`).
- В `/admin/events/[id]` уже есть редактор события и вкладка PDP. Есть отдельное API чтения/сохранения редакционного документа.
- `EventOverride.mergeGroupKey` используется как строковой ключ ручной группы.
- Публичные DTO и `buyer-order-event-links` расширяют некоторые группы по `metaExternalId`. Это шире решения владельца: перед новым объединением PDP этот путь нужно заменить явной проверенной связью. Не отключать его массово без сохранения fallback и проверки существующих страниц.
- В Prisma есть supplier event memberships, change requests и роли, но в `apps/web` нет страниц `/supplier/*`.
- Payload `CREATE` проходит валидацию черновика, однако `applyApprovedEventChangeRequest` отвечает `EVENT_CHANGE_CREATE_UNSUPPORTED` (501). Полный путь «поставщик предложил событие → редактор проверил → PDP создан/опубликован» ещё не работает.

## Целевая схема без дублирования доменной сущности

Канонической сущностью PDP остаётся `Event`. Слот — `EventSession`. Идентификаторы поставщиков и их источники остаются на `ProviderLink` / `EventSourceLink`.

Для уже импортированных данных, где один продукт представлен несколькими строками `Event`, добавить явную проверенную связь участников с корневым PDP (кандидат на join-модель: `EventPdpMember` с `canonicalEventId`, `memberEventId`, состоянием проверки и причиной связи). Такая связь только указывает, какая запись владеет публичной страницей; исходные записи и билеты/заказы не удаляет и не переносит. При чтении PDP backend собирает расписание и варианты покупки участников с исходными `eventId`, чтобы существующие виджеты и исполнение заказа сохраняли владельца.

Публичная выдача, peer events, URL alias и покупательская ссылка должны использовать только эту проверенную связь. `metaExternalId` остаётся поисковым сигналом и источником кандидатов, но не публичным grouping key. `mergeGroupKey` следует либо заменить ссылкой на проверенную запись связи, либо оставить совместимым временным полем, которое не имеет самостоятельного SEO-эффекта.

Это предложение требует отдельного schema/contract-коммита. Не применять схему к БД до согласования миграции с каталогом и существующей finance-историей.

## UX админки

Существующую карточку `/admin/events/[id]` расширять, не создавая отдельный слот-маршрут:

1. **Список:** тип и подтип для поиска; источник/режим управления; статус публикации PDP и продажи; готовность контента; число слотов, предложений и связанных импортных записей.
2. **PDP и идентичность:** стабильный slug/canonical, заголовок и контент PDP, признак «нужна редактура», список внешних исходников и записей-кандидатов.
3. **Связать кандидата:** оператор видит сравнение названия, организатора/поставщика, города/площадки, описания, категорий, тарифов и расписания. Связь создаётся вручную с причиной; похожесть по `metaExternalId` только открывает кандидатов.
4. **Расписание:** одиночный сеанс, повторяющиеся сеансы или открытая дата. Включает кросс-городские остановки и причалы как варианты PDP, когда связь подтверждена. Гибкий массовый грид/календарь слотов — отдельный будущий срез, сейчас не блокирует основную модель.
5. **Билеты и квоты:** общие и, где источник позволяет, по категории/слоту. Нельзя показывать редактируемую квоту там, где поставщик управляет ею только через API.
6. **Контент, медиа и SEO:** сохраняют факты и источник; готовность PDP отдельно от продажи. Индексацию менять только после проверки URL и fallback.

## ЛК поставщика

Сначала нужен реальный route group и API-контракт кабинета; их нет в текущем `apps/web`. Первым работающим сценарием сделать черновик:

- приглашённый поставщик видит только свои события и исходный режим управления;
- для импортного события доступны чтение и заявка на изменение, но не запись поверх внешнего источника;
- для своего кабинета поставщик может подготовить черновик события с городом/площадкой, типом, описанием и предложенными слотами/тарифами;
- для API-поставщика отображаются доступность и источник квоты, а слоты меняются только предусмотренным API действием;
- отправка переводит черновик в очередь модерации; поставщик видит уточнение/отказ и историю;
- публикация, stable URL и SEO остаются у редактора Daibilet. Поставщик не меняет canonical и не склеивает события.

Нужно включить безопасное применение `CREATE`: создание чернового `Event` и связанных сущностей после решения модератора, аудит изменений и идемпотентность. Не разрешать прямое создание опубликованного PDP поставщиком.

## Порядок реализации

1. **Контракт/модель:** выбрать join-модель для явно проверенных участников старых импортных `Event`; миграция и DTO отдельным обозримым коммитом. Существующие URL продолжают вести на прежние страницы.
2. **Backend read path:** резолвер стабильного PDP и списка его сеансов/предложений только по проверенной связи; alias старых URL; fallback archive для прошедших сеансов. Проверки на чужой supplier, циклы, двойное членство, неоднозначный canonical.
3. **Админка:** инвентаризация кандидатов, предпросмотр сравнения, ручная связь, вкладка PDP и readiness. Никакого массового merge.
4. **ЛК поставщика:** личная авторизация/изоляция, черновик CREATE, заявка/диалог/уточнение и просмотр результата модерации.
5. **SEO-переключение:** сначала закрыть 78 текущих URL без Event-сопоставления и исторический список из GSC/Вебмастера. Затем по одной проверенной группе включать canonical/redirect; проверять HTTP, canonical, robots, JSON-LD и sitemap, иметь rollback map.

## Критерии готовности первого выпуска

- Новые события после синка получают стабильную страницу и остаются доступными при недостающем редакционном контенте.
- Сеансы не получают самостоятельных индексируемых PDP.
- Несвязанные записи Ticketscloud/Teplohod не попадают в расписание страницы только из-за одинакового `metaExternalId`.
- Проверенные слоты/остановки можно выбрать на одном PDP, но каждый заказ сохраняет реальный исходный event/session/provider ID.
- Исторический URL не становится 404 из-за истечения последнего сеанса или смены slug.
- Поставщик может видеть только свой контент; создание и публикация разделены; API-поставщик не получает фиктивные ручные квоты.
- Никаких изменений canonical/sitemap до полной ручной проверки конкретного batch и его fallback.
