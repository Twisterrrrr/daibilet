# Дайбилет: SEO public MVP

## Цель

Public часть Дайбилета должна расти не только как каталог событий, а как сеть быстрых SEO-страниц:

- страницы городов;
- страницы регионов;
- страницы площадок;
- тематические лендинги;
- позже - блог и SEO-статьи с перелинковкой на события, города, площадки и лендинги.

Финансовый контур остается у билетных систем. Public задача - помочь пользователю выбрать событие и перейти к покупке через внешний виджет или ссылку.

## Главный принцип

Страница не должна быть тяжелой витриной с большим количеством изображений. Для SEO MVP используем:

- одно основное изображение в hero, если оно действительно помогает запросу;
- текстовые и табличные блоки;
- быстрые фильтры;
- внутреннюю перелинковку;
- JSON-LD и корректные meta/canonical;
- минимальный клиентский JavaScript на публичных SEO-страницах.

## Типы страниц

### Город

Пример URL:

- `/cities/moskva`
- `/cities/sankt-peterburg`

Задачи:

- собрать события города;
- показать основные категории;
- дать быстрые входы в посадочные;
- показать площадки;
- добавить короткий редакционный intro;
- связать с регионами и тематическими лендингами.

Блоки:

- hero с H1, intro и счетчиками;
- быстрые категории;
- ближайшие события;
- популярные площадки;
- подборки по городу;
- FAQ;
- SEO text;
- внутренние ссылки.

### Регион

Пример URL:

- `/regions/moskovskaya-oblast`

Задачи:

- группировать малые города;
- не плодить слабые страницы с 1-2 событиями;
- давать пользователю понятную карточку региона.

Блоки:

- hero региона;
- города внутри региона;
- ближайшие события;
- популярные категории;
- ссылки на крупные города рядом.

### Площадка

Пример URL:

- `/venues/planetariy-1`
- `/venues/prichal-fontanka-...`

Площадка публикуется только если есть смысловая ценность:

- много событий;
- понятная локация;
- известный объект;
- площадка сама является поисковым интентом.

Не публикуем как отдельные страницы:

- случайные точки сбора;
- памятники как meeting point;
- адреса без самостоятельного спроса;
- мусорные дубли причалов до дедупликации.

Блоки:

- hero с названием, адресом, городом;
- программа / события площадки;
- как добраться;
- что важно знать;
- похожие площадки;
- FAQ;
- SEO text.

### Лендинг CITY

Пример URL:

- `/cities/moskva/uzhin-na-teplohode`
- `/cities/sankt-peterburg/razvodnye-mosty`

Это главная SEO-единица для коммерческого спроса.

Блоки:

- hero;
- быстрые фильтры;
- табличная выдача для быстрой покупки;
- featured variants;
- comparison;
- how to choose;
- FAQ;
- related landings;
- SEO text.

### Лендинг MULTI_CITY

Пример URL:

- `/river-cruises`
- `/bus-tours`
- `/salute-9-may`

Это верхний тематический уровень. Он не обязан повторять полный каталог. Его задача:

- объяснить тему;
- показать города;
- вести на CITY-лендинги;
- дать несколько сильных примеров событий;
- собрать органический спрос верхнего уровня.

### Блог / статьи

Позже:

- `/articles/:slug`
- возможно legacy alias `/blog/:slug`, если нужно сохранить старые URL.

Статьи должны ссылаться на:

- события;
- лендинги;
- города;
- площадки;
- категории.

Каждая статья получает `Article`, `SeoMeta`, canonical и JSON-LD Article.

## Индексация

Страница может быть indexable только если выполнены условия:

- есть H1;
- есть seo title;
- есть seo description;
- canonical понятен;
- выборка событий не пустая, если страница завязана на каталог;
- есть достаточный набор контента;
- нет конфликта интента с другой страницей.

Примеры проблем:

- `NO_H1`
- `NO_SEO_TITLE`
- `NO_SEO_DESCRIPTION`
- `NO_HERO`
- `NO_FAQ`
- `NO_SEO_TEXT`
- `NO_MATCHED_EVENTS`
- `LOW_EVENT_COUNT`
- `CANONICAL_MISSING`
- `CANONICAL_CONFLICT`
- `INDEXABLE_WITH_THIN_CONTENT`
- `BROKEN_RELATED_LINK`

## Public stack

Для SEO-страниц целевой стек - Next.js:

- server rendering / static generation;
- generateMetadata;
- sitemap;
- robots;
- JSON-LD;
- быстрые HTML-first страницы.

Текущий Vite public можно использовать как прототип интерфейса, но SEO MVP лучше переносить в Next public до индексации.

## Admin MVP для SEO

В админке нужны не только списки, но и контроль качества SEO:

- список городов с indexability;
- список площадок-кандидатов;
- список лендингов;
- редактор блоков посадочной;
- preview выборки событий;
- SEO audit;
- related links;
- статус canonical.

Редактор лендинга должен иметь вкладки:

- Основное;
- Hero;
- Источник событий;
- Блоки;
- Связи;
- SEO;
- Диагностика.

## Что берем из legacy

Из SPBBOATS имеет смысл переносить идеи и блоки:

- `LandingCompositionRenderer`;
- `ContentSections`;
- `ComparisonTable`;
- `FaqSection`;
- `ClusterHubLinks`;
- `PromoBlock`;
- `buildVenueTemplateSections`;
- city/venue/landing page contracts;
- sitemap/robots/json-ld helpers.

Не переносим тяжелые или лишние части:

- внутренний checkout;
- корзину;
- финансовый контур;
- сложные промо-механики;
- пользовательский кабинет до отдельного решения.
