# DAIBILET Events V2 - аудит и карта реализации

Дата: 2026-11-25  
База аудита: `origin/feat/next-monorepo` (`3996e111f48136fd86cd7b48260c03163fa8dda5`).  
ТЗ: приложенный документ «DAIBILET Events V2 — Афиша, каталог и интеллектуальный поиск» и дополнение о едином поиске.

## Краткий вывод

В проекте уже есть серверный каталог сгруппированных событий, режим каталога `/events`, серверный поиск `/api/public/search`, глобальный мобильный overlay в шапке, отдельная страница `/search`, городские афиши, тематические лендинги, статьи, hero-banner CMS и редакционные маршруты внутри city hub. Это хорошая база; новую БД для афиши создавать не следует.

Основные пробелы перед полной Events V2:

- `/events` сейчас является каталогом, а не отдельной управляемой редакционной витриной.
- Поиск каталога в `CatalogToolbar.client.tsx` показывает подсказки категорий из facets, но не серверные результаты общего поиска.
- Общий endpoint выдаёт не более 8 смешанных результатов; для `context=events` сервер ограничивает выдачу событиями, городами и площадками без запросов статей/подборок. Готовые day-route presets в выдачу не входят.
- Полноценная конфигурация последовательности блоков афиши и редактор этих блоков не обнаружены.
- Нужно подтвердить в `PublicCatalogDto`/`PublicCatalogListItemDto` отображаемые поля сессий, типов посещения и числа связанных городов перед UI-изменениями.

## Поиск: установленное поведение и изменения

`GET /api/public/search?q=...&city=...` требует минимум 2 символа и ограничивает общий ответ 8 элементами. На сервере параллельно ищутся:

- доступные события через pg_trgm с fallback на Prisma и ссылкой только при наличии подходящей EventPage;
- городские geo-hit;
- видимые Venue, включая дальнейшее разделение href на `/venues` и `/locations`;
- опубликованные статьи;
- активные тематические подборки.

`HeaderSearch.client.tsx` уже имеет 220 мс debounce и стрелочную клавиатурную навигацию, но `fetch` не получает `AbortSignal`; старый ответ может перезаписать новый. Inline вариант также не закрывается по Escape. На ошибке endpoint глобальный поиск сохраняет ввод и позволяет перейти на `/search?q=...`, однако отдельное состояние ошибки не отображается.

Требуемая интеграция:

1. Вынести общий контрол поиска в переиспользуемый `SearchAutocomplete` с контекстом `global | events`; сохранить существующую оболочку/позицию в шапке и существующий endpoint.
2. `global`: выдавать ограниченные результаты по доступным типам, визуально группировать только когда группы не ухудшают компактный overlay. Поддержать подсказки `event`, `city`, `venue`, `landing`, `article`; `suburb` остаётся разновидностью city. `route` можно добавить после серверного подключения подтверждённых `dayRoutePresets` с точными существующими href. `place` пока не вводить отдельно от Venue/location.
3. `events`: ограничить подсказки событиями, городами, площадками и подборками, если они нужны для фильтрации; нажатие Enter/submit по свободному тексту ведёт на `/events?q=<query>` (или на фиксированный городской маршрут с `q`), а выбор результата ведёт на href результата.
4. В обоих контекстах использовать debounce 250 мс, отмену предыдущего запроса AbortController, защиту от гонок, Escape/outside close, `aria-activedescendant`/listbox и fallback отправки текста при недоступности API.
5. Для каталогового компонента сохранять город и остальные применимые URL фильтры, сбрасывая только параметры, несовместимые с новым поиском и страницу пагинации.
6. Не читать каталог в браузер для подсказок. Не увеличивать ответ без лимита; если потребуется больше результатов, расширить endpoint типовым `context` и малым контролируемым лимитом.

Серверный endpoint не зависит от `/events`, поэтому общий компонент должен находиться в нейтральной директории `components/search`, а не внутри каталожной страницы.

## Этапы реализации

### A. Каталог и контракты

- Зафиксировать контракт карточки группы, состав `upcomingSlots`, `sessionCount`, `peerCityCount`, `groupedEventsCount`, наличие оффера и поведения событий без даты.
- Сверить активную публичную Prisma-схему и public catalog mapper; UI не должен выводить неподтверждённый тип посещения.
- Сохранить EventPage href, существующие URL, каноникалы, sitemap и городские маршруты.

### B. Общий поиск

- Расширить DTO `/api/public/search` параметром контекста и ограниченным типизированным ответом, если серверное фильтрование контекста нельзя выполнить безопасно в UI.
- Добавить поиск подтверждённых готовых маршрутов только с реальными href; не сканировать целиком ленивые модули всех городов на каждое нажатие клавиши.
- Реализовать общий `SearchAutocomplete`, подключить в header и `CatalogToolbar`.
- Добавить backend/web unit tests для limit, типов, ссылок, abort/race и URL query preservation.

### C. Режим афиши

- Сохранить `/events` как стабильный URL каталога. Режим афиши добавлять через безопасный параметр/вкладку или отдельный маршрут только после продуктового решения по каноникалу; не делать фильтруемые URL индексируемыми.
- Собрать серверный provider блоков с `AUTO | MANUAL | HYBRID`, схемой валидации, лимитами, временными окнами и проверкой наличия целевых материалов.
- Использовать существующие promo blocks/interstitials, опубликованные Article/Landing, city hubs и HeroBanner после аудита API и модели таргетинга.
- Карточки блоков строить по группам существующего PublicCatalogDto; не создавать отдельные Event на сессию.
- Исключать прошедшие/отменённые/без предложения карточки согласно существующим правилам каталога.

### D. Приёмка

- Проверить каталог: URL-фильтры, пагинацию, back/forward, пустое состояние, ошибки API без mock данных, мобильные фильтры.
- Проверить header и Events поиск: мероприятие, город, статья, подборка, площадка, подсказка/Enter, offline/error fallback, mobile overlay, keyboard и конкурирующие запросы.
- Проверить группировку Event/Session, цены и даты по существующему контракту.
- Проверить ссылки на статьи, подборки, city hubs и маршруты по фактически существующим URL.
- SEO smoke: canonical, robots, sitemap и EventPage URL остаются без изменений; arbitrary filter combinations не индексируются.

## Границы этой итерации

- Реализацию `apps/web` координировать с владельцем фронтенд-зоны по таблице ownership в `AGENTS.md`.
- Не менять Prisma schema/миграции, backend/contracts DTO без отдельного согласования: они являются общей точкой конфликта.
- Не включать checkout/платежи, полноценный Places, My-day planner или массовую SEO-миграцию.
- Не выполнять staging/prod deploy в рамках локальной реализации без явного запроса владельца.

## Реализация showcase - 25.11.2026

В noindex preview `/afisha` добавлен валидируемый конфигурационный provider
`apps/web/src/lib/events-v2-blocks.ts`. Порядок задаётся полем `order`, а типы
блоков включают ленты событий, избранные карточки, баннер, статью, подборку,
городской хаб, готовые маршруты и custom content. Статусы и окно публикации
фильтруются до рендера; лимиты ограничены 12 объектами, ссылки конфигурации
допускают только внутренние пути. AUTO/MANUAL/HYBRID работают поверх уже
серверно ограниченного каталога и опубликованных источников.

`EventsV2Preview.tsx` теперь выводит блоки по разрешённой последовательности.
AUTO-ленты распределяют доступные Event group по категории без повторов,
материалы без публикации/событий скрываются. Маршруты загружаются через
существующий lazy city-hub provider и ведут на `/my-day?route=...&city=...`.
Превью принимает `?city=` только после сопоставления с публичным destination,
запрашивает каталог с этим городом и сохраняет его при переходе в каталог и
поиске. `/events`, canonical и sitemap не изменялись. Это config-file фаза 1,
не админский CMS-редактор; визуальный mobile smoke ещё нужен.

Маршрутная схема: `/afisha` - новая редакционная витрина, `/events` - прежний
каталог с фильтрами и стабильными Event URL. Основная и мобильная навигация
«Афиша» ведёт на `/afisha`; поиск, календарь, категории и CTA каталога ведут на
`/events`. `/afisha` остаётся `noindex` с canonical на себя до приёмки.
