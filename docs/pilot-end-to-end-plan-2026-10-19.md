# Первый поставщик: план сквозного запуска

Дата: 19.10.2026, обновлено 20.10.2026. Цель: завести отдельного тестового поставщика, создать его событие и товар, провести оплату в тестовом магазине ЮKassa и показать один и тот же заказ покупателю, оператору и поставщику. После основного прохода проверить отмену, возврат, остатки, расчёты и документы. Продажа за реальные деньги требует отдельного решения по агентскому чеку и реквизитам поставщика.

## Границы первого прохода

- Один поставщик по персональному приглашению, одна площадка, одно событие с открытой датой и две категории билетов. Повторяющиеся слоты и конкретные места проверяются следующим сценарием, после базовой продажи.
- Режим `INTERNAL_SALES` и оплата тестового магазина ЮKassa. TC/Teplohod остаются внешними каналами со своими виджетами и фискализацией.
- Три способа работы с каталогом: импорт событий (`IMPORTED_TICKETING_SYSTEM`), управление предложениями через ЛК (`INTERNAL_SALES`), обмен через API (`API_SYNC`). Это не три способа оплаты: у API-поставщика деньги могут проходить через Daibilet либо через его сторону, согласно отдельным `defaultCatalogMode`/`paymentMode` и возможностям адаптера. Импортный поставщик не получает автоматический доступ в ЛК; приглашение выдаётся отдельно.
- Заказ создаётся покупателем на публичном сайте. Его нельзя подтвердить по возврату браузера с платёжной страницы: факт оплаты берётся из уведомления ЮKassa или серверной сверки. Билет виден только после выпуска.
- В качестве технического smoke можно использовать `phase-g-test-museum`, но приёмка онбординга требует отдельного поставщика, заведённого штатным операторским путём. Скрипт seed не подтверждает работу приглашений, модерации и договорных условий.

## Очередь работ и критерии готовности

| Шаг | Работа | Доказательство завершения |
|---|---|---|
| 0. Среда | Выбрать одну локальную/тестовую БД, поднять сервисы, проверить миграции, сборки и доступ к sandbox ЮKassa. Зафиксировать SHA и используемый ShopID без секретов. | Сервисы и миграции здоровы; тестовый магазин не перепутан с боевым. |
| 1. Поставщик | Создание в админке, персональное приглашение OWNER, вход и обновление сессии; реквизиты и банк на проверку, решение оператора; договор, версия, ставка комиссии и налоговый режим поставщика как отдельные данные. | В ЛК виден только свой поставщик; чужой ID даёт 403; версия условий и комиссия заморожены в заказе. |
| 2. Каталог | Связать площадку и город; заявка поставщика на событие/входной билет; модерация и применение; две категории билетов, квоты, тип даты, доступность для продажи. | Публичная карточка и checkout появляются лишь при `canSell=true`; отклонённая заявка не публикует товар. |
| 3. Продажа | Создать заказ, открыть тестовую оплату, пройти тестовой картой; дождаться webhook либо сверки; выпустить билет. | Один платёж, один переход в paid, один комплект билетов, один набор ledger entries; неоплаченный заказ не содержит действующего билета. |
| 4. Три кабинета | Сверить сумму, категорию, статус, билет и поставщика в ЛК покупателя, карточке оператора и ЛК поставщика. | Данные согласованы; поставщик видит только свои строки и серверно замаскированные контакты. |
| 5. Негативные сценарии | Ошибка/таймаут оплаты, `payment.canceled`, повтор webhook, истечение неоплаченного заказа, исчерпание квоты и параллельная покупка. | Нет билета до оплаты, отрицательного остатка, двойного списания или двойного выпуска. |
| 6. Возврат | Запрос покупателя, решение оператора, полный и частичный возврат в sandbox, подтверждение `refund.succeeded`, погашение билета и обратные записи в ledger. | Повтор уведомления не создаёт второй возврат; во всех кабинетах отображён один итог. |
| 7. Деньги и документы | Сверка оплаты и заказа, подтверждение оказания услуги, доступный баланс, запрос выплаты, одобрение, факт банковского перевода; месячный отчёт агента и закрывающие документы. | Запрос/одобрение не подписаны как «выплачено»; суммы отчёта равны ledger; файл доступен только своему поставщику. |
| 8. Выпуск | Деплой finance API, БД, web, admin и supplier в правильном порядке; повтор шагов 1-7 на тестовом магазине, затем отдельное разрешение боевой агентской фискализации. | Сохранены ID тестовых заказов, статусы, время событий, снимки экранов и результаты сверки без секретов и полных ПДн. |

## Нынешнее состояние и блокеры, установленные по коду

- Есть модели поставщика, площадки, admission product, checkout, payment, fulfillment, ledger и документов. Есть приглашение, заявки на admission, YooKassa checkout, supplier purchase projection и операторские страницы. Это основание для первого прохода, но не его доказательство.
- Seed `seed-stub-admission.ts` создаёт технического поставщика, площадку и open-date admission. Ранее он сбрасывал пароль тестовому пользователю при каждом запуске; теперь пароль и членство не меняет. Вход проверяется через штатное приглашение.
- Операторское создание черновика и привязка площадки реализованы в текущей ветке и проверены через локальный HTTP. Площадка `codex-pilot-museum-20261019` создана непубличной; поставщик `codex-pilot-20261019` получил OWNER через одноразовое приглашение. Его заявка на входной билет с двумя категориями прошла `SUBMITTED -> APPROVED -> APPLIED`. Поставщик остаётся `DRAFT`; публичная продажа для него не открыта.
- Технический STUB-заказ `1593204` на отдельном smoke-поставщике прошёл: `CONFIRMED`, один успешный платёж `MANUAL`, один действующий билет, SALE 70000 коп., COMMISSION 8400 коп. и семь проверок инвариантов. Это не проверка ЮKassa и пока не продажа нового пилотного поставщика.
- Сверка предыдущего STUB-заказа `1723330` выявила подтверждённый fulfillment без `IssuedTicket`. В текущей ветке STUB checkout теперь создаёт запись билета в той же транзакции, что заказ и ledger; старые тестовые заказы можно восстановить только адресным `backfill-issued-tickets.ts --public-code=... --apply` после проверки оплаты.
- В finance QA отмечены незакрытые сценарии: применение CREATE Event, исполнение частичного возврата, реальная выдача/подписание документов и выплата по банку. Их статус нужно перепроверять по текущему коду и живому сценарию, а не считать готовыми из старого документа.
- На текущей машине Docker Engine недоступен (`dockerDesktopLinuxEngine` отсутствует), `prisma migrate status` не смог подключиться к локальному PostgreSQL `127.0.0.1:5437`. БД-сценарий и реальную тестовую продажу здесь пока не запускали.
- Для боевых денег отдельно подтвердить с бухгалтером агентский чек, ставку НДС по каждому товару поставщика, реквизиты поставщика и момент формирования чека. УСН 6% Daibilet не определяет НДС поставщика. Sandbox-проверка не является разрешением на боевую продажу.

## Порядок реализации

Сначала замкнуть шаги 0-4 на одном open-date товаре. После зелёного прохода закрыть 5-6. Затем внедрять подтверждение оказания услуги, выплаты и документы (7). Отдельно расширить путь на повторяющееся событие со слотами, а затем на закреплённые места. Для продажи через API поставщика потребуются его схема, стабильные seat ID и операции резерва/снятия; схема TC остаётся в виджете TC.

Каждый шаг заканчивается не только тестом кода, но и проверкой в интерфейсе с конкретным заказом и сверкой фактов в БД/API. Отключённая кнопка или мок не считается работающей функцией.
