# Карта соответствий Event → PDP / слот / архивный URL

**Снимок:** 27.10.2026. **Среда:** production, только чтение через уже поднятый локальный туннель; изменений БД, canonical, sitemap и redirect-правил не выполнялось.

## Принятое правило

- Индексируемая сущность — PDP события. Сеансы и билетные слоты живут внутри этой страницы и не получают самостоятельные индексируемые PDP.
- Пока соответствие старого URL устойчивому PDP не доказано и целевой PDP не готов, старый URL сохраняет fallback. Не ставить `noindex`, не менять canonical и не редиректить массово.
- Прошедшее событие не должно исчезать с 404 только потому, что у него больше нет продаваемого сеанса. Если надёжной группировки нет, сохраняется самостоятельный архивный PDP.
- `MetaEvent` — сильная подсказка для поиска серии, но не автоматическое разрешение на слияние: встречаются крупные группы, отличающиеся редакционные выпуски и варианты места проведения.

## Объём и ограничения аудита

- Живой `/sitemaps/events.xml` содержал 4 346 URL; 4 008 URL оканчивались 24-значным hex-ID. Это формат идентификатора, сам по себе он не доказывает, что каждая запись является отдельным слотом.
- Для Ticketscloud в БД найдено 1 375 значений `metaExternalId`; 1 121 связывает более одной Event-записи, 127 групп охватывают больше одного города. Медианный размер группы — 8 Event-записей; 21 группа превышает 1 000, максимальная — 4 500. Поэтому полное автоматическое объединение по `metaExternalId` небезопасно.
- Сопоставление ID из sitemap с `EventSourceLink` выявило 553 TC meta-группы в текущей карте. В 7 группах sitemap содержал по два URL (14 страниц). Все 14 проверены: HTTP 200, каждая имела self-canonical.
- Архивная часть ниже ограничена тремя URL, ранее переданными владельцем и проверенными как 404. Это не полный список из Google Search Console; для полного восстановления старых адресов понадобится выгрузка URL-ошибок и исторических URL.

## Следующий проход карты

1. Получить URL-level выгрузку ошибок Яндекс.Вебмастера и добавить её к историческому инвентарю. Текущий GSC Coverage export содержит только сводку.
2. Для текущих sitemap URL построить реестр `public URL → Event ID → provider external ID → meta group → proposed PDP → decision → confidence`.
3. Для прочих, ещё не классифицированных туров и спецвыпусков проверить площадку/организатора и программу вручную. Уже подтверждённые владельцем решения из таблицы не пересматривать автоматически. Большие TC meta-группы (`>30` записей) не объединять автоматически; сначала разбить на продукты/города/серии.
4. После подтверждения создать стабильные PDP и только потом менять canonical/redirect/sitemap. До этого fallback сохраняется.

## Исторические адреса и числовые ID

Причина 78 URL без Event match выяснена: все 78 URL в текущем sitemap имеют старый числовой хвост (`...-1359`). Это формат Teplohod event ID, который в каталоге использует внутренний ключ `evt_tep_1359`. Приложение преобразует такой хвост в ключ через `extractEventTrailingLookupToken()` и `buildTepEventIdFromTrailingToken()` в `apps/backend/src/public-event.dto.ts`. Production API spot-check подтвердил соответствие для `1359`, `1455`, `769` и `1375` (ID, название и slug соответствуют адресам).

Причина первоначального пропуска — ограничение аудиторского запроса: он искал Event по Ticketscloud hex ID, slug и canonical path, но не по внутреннему `evt_tep_<id>`. [Read-only exporter](../scripts/audit-event-pdp-url-map.mjs) теперь распознаёт числовой TEP-хвост, ищет по внутреннему Event ID и включает source identity из `ProviderLink` вместе с `EventSourceLink`. Повторный export с read-only БД нужен, чтобы заполнить остальные поля всех 78 строк; в этой сессии `EVENT_MAP_DATABASE_URL` не настроен.

Добавлен отдельный [исторический инвентарь URL из Search Console](./event-pdp-search-console-url-inventory-2026-10-27.csv), который объединяет:

- 534 URL событий из GSC Performance export от 29.09.2026 (период метрик 18.07–27.09.2026);
- 987 URL событий из GSC Event Enhancement «missing performer» export от 19.10.2026;
- 3 старых URL, ранее переданных владельцем.

После дедупликации — 1 521 URL: 213 совпадают с текущим event sitemap, 1 305 URL из GSC-выгрузок в нём отсутствуют. Инвентарь сохраняет доступные метрики и даты последнего сканирования, URL ID-хвосты и возможные сопоставления с текущим snapshot. Отсутствие URL в sitemap не означает, что он отвечает 404. Статусы, canonical и целевой PDP массово не проверялись; все записи оставлены в состоянии `KEEP_URL_PENDING_PDP_AND_IDENTITY_REVIEW`, `seo_change=none`.

Локальный GSC Coverage export от 29.09 содержит агрегированные 131 «Не найдено (404)» и 3 soft 404, но без URL-строк. Полной выгрузки адресов из Яндекс.Вебмастера в доступных локальных файлах нет: прежний отчёт содержит агрегаты и несколько сокращённых примеров. Поэтому список Search Console расширен реальными URL страниц, но не является полным списком 404 обоих поисковиков.

Для полного списка старых 404 из Яндекс.Вебмастера нужна URL-level выгрузка: локально доступна только сводка. До проверки PDP-соответствий canonical, sitemap и redirects не переключать.

## Проверяемые инварианты перед SEO-изменениями

- У каждой прежней индексируемой ссылки остаётся HTTP 200 или однозначный 301 на готовый PDP; 404 не является допустимым способом «склеить слоты».
- У каждого PDP есть один self-canonical; слот или старый slug получает canonical/redirect только при однозначной связи с PDP.
- Sitemap содержит PDP, а не дублирующие slot-страницы; страницы со спорной идентичностью пока не удаляются из карты.
- Проверить 200/301/404, canonical, robots, sitemap membership и JSON-LD до и после переключения; сохранить список старых URL для rollback.
