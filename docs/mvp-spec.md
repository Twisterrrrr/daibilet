# MVP: агрегатор событий из билетных систем

## 1. Назначение продукта

Сервис является каталогом-агрегатором событий, импортируемых из внешних билетных систем:

- Ticketscloud;
- Teplohod.info.

Сервис не обрабатывает платежи, не выпускает билеты, не делает возвраты и не управляет финансовым контуром. Все финансовые операции остаются на стороне билетных систем.

Задача сервиса:

- импортировать и нормализовать события;
- типизировать каталог по городам и категориям;
- показывать события пользователям;
- открывать покупку через виджет или внешний интерфейс билетной системы;
- хранить факт покупки, данные покупателя, внешний идентификатор заказа/билета и актуальный статус билета.

## 2. Границы MVP

### Входит в MVP

- Каталог событий.
- Страница события.
- Фильтры по городу, категории, дате и источнику.
- Импорт событий из Ticketscloud и Teplohod.info.
- Ручной запуск импорта из админки.
- Регулярная синхронизация по расписанию.
- Логирование результатов импорта.
- Хранение внешних заказов/билетов и их статусов.
- Получение статусов покупок через API билетных систем.
- Админка для просмотра и корректировки импортированных данных.

### Не входит в MVP

- Прием платежей.
- Эквайринг.
- Возвраты.
- Выпуск PDF/QR билетов.
- Управление местами в зале.
- Личный кабинет покупателя с полным финансовым профилем.
- Собственная корзина.
- Собственная система промокодов.

## 3. Роли

### Пользователь

- Просматривает каталог событий.
- Фильтрует события по городу, категории и дате.
- Открывает страницу события.
- Переходит во внешнюю билетную систему для покупки.

### Администратор

- Запускает импорт вручную.
- Смотрит журнал импортов.
- Проверяет ошибки синхронизации.
- Управляет категориями и городами.
- Корректирует привязки импортированных событий.
- Смотрит статусы внешних заказов/билетов.

### Внешняя билетная система

- Отдает данные о событиях.
- Принимает пользователя для покупки.
- Возвращает статус покупки через webhook или API.

## 4. Основные сущности

### Source

Источник данных.

Поля:

- `id`;
- `code`: `ticketscloud` или `teplohod`;
- `name`;
- `is_active`;
- `created_at`;
- `updated_at`.

### City

Город каталога.

Поля:

- `id`;
- `name`;
- `slug`;
- `external_mappings`;
- `is_active`;
- `created_at`;
- `updated_at`.

### Category

Категория события.

Поля:

- `id`;
- `name`;
- `slug`;
- `external_mappings`;
- `is_active`;
- `created_at`;
- `updated_at`.

Основные категории:

- экскурсии;
- музеи и арт;
- мероприятия;
- активный отдых;
- развлечения.

Мероприятия включают концерты, театр, фестивали и похожие форматы.

Активный отдых включает спорт, активности и экстрим.

Развлечения включают зоопарки, парки, шоу и похожие объекты досуга.

### Subcategory

Подкатегория события.

Поля:

- `id`;
- `category_id`;
- `name`;
- `slug`;
- `kind`: `primary`, `additional`;
- `external_mappings`;
- `is_active`;
- `created_at`;
- `updated_at`.

Правила:

- основная подкатегория жестко привязана к одной основной категории;
- событие должно иметь одну основную категорию и одну основную подкатегорию, если маппинг позволяет;
- дополнительно событие может иметь 1-2 допподкатегории;
- допподкатегории могут относиться к любой категории и использоваться как уточняющие признаки.

### Tag

Тег события.

Поля:

- `id`;
- `name`;
- `slug`;
- `is_active`;
- `created_at`;
- `updated_at`.

Теги дополняют особенности события и не заменяют категорию или подкатегорию.

Площадка, место проведения, причал или точка отправления.

- `longitude`;
- `has_page`;
- `description`;
- `image_url`;
- `external_mappings`;
- `created_at`;
- `updated_at`.

Площадка может быть простой локацией внутри карточки события или иметь собственную страницу со списком связанных событий. Не каждую внешнюю `venue` нужно публиковать как площадку: точки встречи экскурсий, памятники и адресные ориентиры должны оставаться `meeting_point`.

## 5. Импорт событий

### Источники импорта

#### Ticketscloud

Каталог событий импортируется через gRPC-сервис `tc-simple`.

Минимально нужные методы:

- `Events` - мероприятия;
- `MetaEvents` - группы повторяющихся мероприятий;
- `Categories` - категории Ticketscloud;
- `Tags` - теги/жанры;
- `Venues` - площадки;
- `Cities` - города;
- `Seats` - места и билеты, если понадобится отображать доступность глубже уровня категории билета.

Авторизация выполняется API-ключом. Для REST API ключ передается в заголовке `Authorization` с префиксом `key`. Для gRPC ключ передается в metadata `authorization`; дополнительно можно передавать `preferred-language: ru`.

Endpoints:

- stage gRPC: `simple.stage.freetc.net:443`;
- production gRPC: `simple.ticketscloud.com:443`;
- stage REST: `https://stage.freetc.net`;
- production REST: `https://ticketscloud.com`.

#### Teplohod.info

Интеграция выполняется по API Teplohod.info с доступом по User-Agent и/или белому IP. Наш сервер уже должен быть добавлен в allowlist на стороне Teplohod.info.

Base URL:

- `https://api.teplohod.info/v1`

Методы каталога:

- `GET /events` - список публичных событий и расписаний;
- `GET /events/{id}` - конкретное событие.

Полезные параметры `GET /events`:

- `compact` - получить события без `eventTimes`, ускоряет ответ и доступен без авторизации;
- `dateFrom` и `dateTo` - фильтр по датам сеансов;
- `cityId` - фильтр по одному или нескольким городам;
- `expand=eventSections` - дополнительные HTML-секции описания;
- `per-page` и `page` - пагинация.

Для локальной разработки нужен один из вариантов:

- использовать тестовый/stage endpoint, доступный с локальной машины;
- запускать импорт через сервер с разрешенным IP;
- использовать сохраненные fixture-ответы для разработки парсера и нормализации.

### Общая логика

1. Администратор запускает импорт вручную или импорт стартует по расписанию.
2. Сервис получает список событий из источника.
3. Каждое событие приводится к внутренней модели.
4. Сервис ищет существующее событие по `source_id + external_id`.
5. Если событие найдено, обновляет изменяемые поля.
6. Если событие не найдено, создает новое.
7. Сервис импортирует сеансы события.
8. Сервис записывает результат в `ImportJob` и `ImportJobItem`.

### Правила нормализации

- Категории внешних систем маппятся на внутренние категории.
- Города внешних систем маппятся на внутренние города.
- Площадки/причалы маппятся на `Venue`.
- Сырые данные источника сохраняются в `source_payload` для диагностики.
- Если категория или город не распознаны, событие импортируется, но получает статус `draft` или специальную категорию `needs_mapping`.

### Защита от дублей

Главный ключ сопоставления:

- `source_id + external_id`.

Дополнительная эвристика для админской диагностики:

- похожее название;
- одинаковый город;
- одинаковая площадка;
- пересекающиеся даты;
- одинаковый источник изображения или URL.

События из разных источников можно объединять или выбирать один приоритетный вариант для показа, но только после проверки. В MVP алгоритм предлагает потенциальные дубли администратору, а финальное решение принимает человек.

## 6. Покупка

### Пользовательский сценарий

1. Пользователь открывает событие.
2. Выбирает дату/сеанс, если применимо.
3. Нажимает кнопку покупки.
4. Сервис открывает виджет или отправляет пользователя во внешний интерфейс билетной системы.
5. Покупка происходит на стороне билетной системы.
6. Сервис получает факт покупки и статус через API билетной системы.

### Что хранит сервис

- Внешний ID заказа.
- Внешний ID билета, если есть.
- Ссылку на событие и сеанс.
- Статус билета.
- Данные покупателя для быстрой обработки обращения.
- Сумму и валюту, если источник передает эти данные.
- Время последнего обновления статуса.
- Сырой payload для диагностики.

### Что сервис не хранит и не делает

- Данные банковской карты.
- Платежные токены.
- Чеки.
- Эквайринговые операции.
- Возвраты денег.
- Выпуск билетов.

## 7. Статусы

### Статусы события

- `draft`: импортировано, но требует проверки;
- `published`: опубликовано в каталоге;
- `hidden`: скрыто вручную;
- `archived`: больше не актуально.

### Статусы сеанса

- `available`: доступен к покупке;
- `sold_out`: мест нет;
- `cancelled`: отменен;
- `unknown`: источник не передал понятный статус.

### Статусы заказа/билета

- `pending`: покупка начата или ожидает подтверждения;
- `paid`: покупка оплачена;
- `cancelled`: заказ отменен;
- `expired`: заказ просрочен или резерв истек;
- `refunded`: возврат оформлен на стороне билетной системы;
- `used`: билет использован;
- `unknown`: статус не удалось сопоставить.

## 8. API и обмен данными

### Внешние API источников

#### Ticketscloud

Для каталога:

- `tc-simple.Events`;
- `tc-simple.MetaEvents`;
- `tc-simple.Categories`;
- `tc-simple.Tags`;
- `tc-simple.Venues`;
- `tc-simple.Cities`.

Для заказов и статусов:

- `GET /v2/resources/orders`;
- `POST /v2/resources/orders`;
- `PATCH /v2/resources/orders/:id`.

В рамках нашего агрегатора `POST` и `PATCH` не используем в MVP, чтобы не проводить через себя checkout и чеки. Пользователь покупает через виджет Ticketscloud или внешний интерфейс Ticketscloud. Нам достаточно импорта каталога и синхронизации статусов заказов через `GET /v2/resources/orders` или другой API-метод статусов, доступный в договоре.

#### Teplohod.info

Каталог:

- `GET /events`;
- `GET /events/{id}`;
- упомянутый endpoint городов: `GET /cities`.

В предоставленной документации не описаны методы заказа, получения факта покупки и статуса билета. По рабочей модели статусы заказов доступны через API, но точный endpoint нужно отдельно добавить в спецификацию после получения контракта.

Для MVP используем:

- покупку через виджет или внешний интерфейс Teplohod.info;
- получение статуса заказа/билета через API;
- сохранение данных покупателя, если API их передает и это допустимо по договору/политике ПДн.

### Внутреннее API админки

Минимальные endpoints:

- `GET /admin/events`;
- `GET /admin/events/{id}`;
- `PATCH /admin/events/{id}`;
- `GET /admin/import-jobs`;
- `POST /admin/import-jobs`;
- `GET /admin/import-jobs/{id}`;
- `GET /admin/orders`;
- `GET /admin/orders/{id}`.

### Публичное API каталога

Минимальные endpoints:

- `GET /cities`;
- `GET /categories`;
- `GET /events`;
- `GET /events/{slug}`;
- `GET /events/{id}/sessions`.

Фильтры для `GET /events`:

- `city`;
- `category`;
- `date_from`;
- `date_to`;
- `source`;
- `q`.

### Webhook для статусов покупки

Пример endpoint:

- `POST /webhooks/{source}/orders`.

Обязательная логика:

- проверка подписи или секретного ключа;
- идемпотентность по внешнему ID заказа/билета;
- сохранение сырого payload;
- обновление статуса;
- запись технического события в лог.

## 9. Админка

### Разделы

- События.
- Сеансы.
- Города.
- Категории.
- Источники.
- Импорт.
- Заказы/билеты.
- Ошибки синхронизации.

### Основные действия

- Запустить импорт по источнику.
- Посмотреть результат импорта.
- Открыть карточку импортированного события.
- Изменить категорию или город.
- Скрыть событие.
- Опубликовать событие.
- Посмотреть исходный payload.
- Повторить импорт проблемной записи.

## 10. Нефункциональные требования

- Импорт должен быть идемпотентным.
- Ошибка одной записи не должна останавливать весь импорт.
- Все внешние payload нужно сохранять для диагностики.
- Webhook должен быть защищен подписью или секретом.
- Время всех событий хранить в UTC, показывать пользователю в локальном часовом поясе города.
- Все внешние запросы логировать технически, без хранения чувствительных данных.
- Данные покупателя хранить только в объеме, нужном для обработки обращений и сверки статусов заказов.
- Мультиязычность в MVP не нужна.

## 11. Правила каталога

### Таксономия

- У события есть одна основная категория.
- У события есть одна основная подкатегория, если ее удалось определить.
- Основная подкатегория жестко принадлежит основной категории.
- У события может быть 1-2 дополнительные подкатегории.
- Дополнительные подкатегории могут относиться к любой основной категории.
- Теги используются для особенностей, подборок и фильтров, но не заменяют категории.
- Маппинг внешних событий строится по паре `категория + основная подкатегория`; дополнительные подкатегории и теги могут назначаться поверх этого маппинга.

Основные категории:

- экскурсии;
- музеи и арт;
- мероприятия;
- активный отдых;
- развлечения.

Типы событий:

- `single` - разовое событие;
- `recurring` - повторяющееся событие с несколькими сеансами;
- `open_date` - событие с открытой датой.

### Города

- Города импортируются из билетных систем.
- В публичном каталоге отдельными городскими посадочными показываются крупные города и административно/туристически значимые центры.
- Малые города, спутники и локальные населенные пункты группируются в область/регион, даже если в них много событий.
- Пример: Раменское группируется в `Московская область`, а не получает отдельную городскую посадочную.
- Для группировки нужен ручной справочник соответствия `city -> region` и список городов, которым разрешена отдельная посадочная.
- В интерфейсе направления выводятся карточками: `Москва` с количеством событий и площадок, затем связанная карточка `Московская область` с количеством событий и площадок.
- Города и регионы должны иметь собственные посадочные страницы с кратким описанием, предложениями активностей и выборками из каталога.

### Площадки

- Площадка может быть только локацией события.
- Если площадка значима сама по себе, она получает собственную страницу.
- Страница площадки содержит описание, адрес, карту/координаты и связанные события.
- Причалы хранятся как `pier`, но перед публикацией страницы требуют дедупликации по адресу и координатам.
- Точки встречи экскурсий хранятся как `meeting_point` и не получают публичную страницу площадки по умолчанию.
- Кандидатами на страницы становятся музеи, театры, концертные залы, бары/клубы, арт-пространства, спортивные объекты и значимые достопримечательности.

### Модерация

- Ручная модерация нужна, но не должна блокировать весь импорт.
- Новые события можно импортировать в `draft`, если не распознаны город, категория, площадка или есть признаки дубля.
- События с полным и уверенным маппингом можно публиковать автоматически, если этот режим включен для источника.

### Дубли

- Одинаковые события из разных источников можно объединять в одну карточку или показывать один выбранный вариант.
- Любое объединение дублей должно проходить проверку.
- В MVP автоматический алгоритм только предлагает потенциальные дубли, а финальное решение принимает администратор.
- Для объединенного события нужно сохранить все внешние источники и варианты покупки.

### Второй этап

Во втором этапе добавляем:

- коллекции - фильтр карточек каталога по определенной тематике;
- лендинги - отдельные посадочные страницы под одну тему или дату;
- табличный вывод событий на лендингах;
- расширенное управление городскими посадочными страницами.

## 12. Открытые вопросы

- По Ticketscloud: подтвердить точный способ получения статуса заказа при покупке через виджет.
- По Teplohod.info: получить контракт по заказам/билетам, потому что текущий документ описывает только каталог событий.
- По Teplohod.info: уточнить endpoint статусов заказов/билетов.
- По Teplohod.info: подтвердить `GET /cities`, так как endpoint упомянут в документации, но его формат не описан.
- Какие категории являются обязательными на старте?
- Нужна ли отдельная категория для событий с открытой датой?
- Нужно ли выделять водные прогулки/теплоходы в отдельное верхнеуровневое направление?
- Нужны ли тематические подкатегории: гастрономия, музыка, вечерние прогулки, детские, экскурсионные, романтические?

## 13. Предлагаемый порядок реализации

1. Утвердить модель данных и статусы.
2. Получить API-документацию Ticketscloud и Teplohod.info.
3. Сделать базовый каталог: города, категории, события, сеансы.
4. Сделать первый импорт одного источника.
5. Добавить журнал импорта и диагностику ошибок.
6. Сделать публичный каталог и страницу события.
7. Добавить переход на внешнюю покупку.
8. Подключить получение статусов покупок.
9. Подключить второй источник.
10. Добавить админские инструменты маппинга и устранения дублей.
