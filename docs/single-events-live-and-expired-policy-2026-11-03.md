У 45 событий из группы «только прошедшие» всё ещё есть активное предложение без будущего активного сеанса. Перед редиректом или отключением предложения нужно отдельно сверить остаточное состояние источника.

В production сейчас 0 строк `EventPage`, 0 связей `EventPageEvent` и 0 маршрутов `EventPageRoute`. Stable EventPage foundation уже есть в коде/схеме, но соответствия и целевые маршруты для этого набора ещё не созданы.

## Первым делом: живые события

Из 4 632 DB-кандидатов классификация по нормализованному названию с учётом **всех** production `SINGLE` (включая скрытые и прошедшие) даёт:

| Класс | Event ID | Значение |
|---|---:|---|
| Точное нормализованное название встречается ровно один раз во всей базе `SINGLE` | 2 187 | Наиболее простой первый пакет для отдельной EventPage, после проверки slug и старых URL. |
| Название повторяется в том же городе в базе | 1 900 | Сверить все варианты, в том числе скрытые/прошедшие, площадку, поставщика и source identity. |
| Название встречается в других городах, но в своём городе уникально | 545 | Возможные гастроли или одноимённые события; локальные EventPage остаются отдельными, `tourGroupId` только после подтверждения. |

Классы разложены с приоритетом: сначала повтор названия в том же городе, затем совпадение только в других городах. Точное совпадение названия — фильтр для проверки, не команда на объединение. Event ID и записи источника сохраняются; несколько Event ID можно связать одной EventPage лишь после подтверждения, что это одна страница/программа.

## Предлагаемая SEO-политика

1. **Событие без `EventSession` вообще:** отдавать страницу с HTTP 200 и `noindex,follow`, не включать её в sitemap. URL и данные не удалять. Если синхронизация добавит сеансы, пересчитать indexability по правилам EventPage и продаже.
2. **Прошедшее событие:** не восстанавливать слоты и не перенаправлять все прошедшие URL на каталог. Сначала связать Event ID с целевой EventPage. После проверки старый адрес события/слота получает постоянный 301 на стабильный адрес EventPage. Пока target не назначен, старый URL и fallback сохраняются.
3. **Сезонное или возвращающееся событие:** EventPage остаётся HTTP 200. Индексация определяется ценностью страницы и редакционным статусом, а не фактом, что все текущие сеансы завершились. При синхронизации новых сеансов расписание и покупка появляются на существующей EventPage.
4. **Живые `READY` с активным сеансом и предложением:** создать/использовать стабильную EventPage и прикрепить явный Event ID. Сначала 2 187 без точной коллизии названия; повторные и межгородские группы идут через проверку. Не переключать canonical/sitemap/redirect, пока не создана и проверена карта URL.
5. **Постоянный редирект:** для публичного GET-пути достаточно 301; 308 технически допустим, но преимуществ для обычного GET не даёт. Включать редирект только после проверки цели и отсутствия цепочки/цикла.

`noindex` для событий без сеансов и редиректы для прошедших — разные операции: первое не должно вести к 404; второе требует реальной целевой страницы. Бизнес-правило для отсутствия сеансов следует реализовать в server-rendered metadata, чтобы `robots` не зависел от клиентского JS.
