# Supplier LC UX/UI brief

Дата: 2026-07-30  
Зона: `apps/supplier` на finance `.159`  
Канон границы: [catalog-finance-projection.md](./catalog-finance-projection.md)  
Backend contracts: `GET /api/supplier/*`, PurchaseProjection, public finance projection CF.P1

## 1. Роль дизайнера

Нужен senior product designer RU с опытом B2B SaaS, fintech, личных кабинетов, операционных таблиц и Figma handoff.

Не нужен landing-page designer, рекламное агентство или дизайнер витрин без портфеля кабинетов.

Цель макетов: не "красивый сайт поставщика", а рабочий инструмент, где владелец, оператор и бухгалтер быстро понимают:

- что мешает продаже;
- какие товары и события готовы к продаже;
- какие заказы пришли;
- сколько денег в обработке, сколько к выплате;
- какие документы и отчеты нужны.

## 2. Продуктовая граница

ЛК поставщика живет на finance `.159`.

Запрещено в рамках ЛК:

- трогать TC/Teplohod widgets, secrets, import sync;
- ходить в catalog DB напрямую;
- смешивать AdmissionProduct с event slot;
- выводить покупателю или поставщику технические ids;
- включать широкий CTA на catalog до закрытого smoke STUB/YooKassa path.

Поставщик видит только свой срез данных:

- свои события и входные билеты;
- свои checkout items и заказы через PurchaseProjection;
- свои реквизиты, документы, выплаты и отчеты;
- свои проблемы готовности.

## 3. Главные пользователи

### Владелец

Задачи:

- пройти onboarding;
- заполнить реквизиты;
- подключить продажи;
- видеть деньги, отчеты и документы;
- пригласить команду.

Права:

- все настройки организации;
- просмотр финансов;
- запросы на изменение данных;
- управление командой.

### Оператор

Задачи:

- смотреть заказы;
- сверять билеты;
- контролировать слоты, вместимость и остатки;
- видеть проблемы карточек.

Права:

- операционный просмотр;
- заявки на правки;
- без банковских реквизитов и чувствительных финансовых настроек.

### Бухгалтер

Задачи:

- смотреть выплаты;
- скачивать отчеты;
- проверять акты, реестры, комиссии.

Права:

- финансы и документы;
- без редактирования событий и контента.

### Viewer

Задачи:

- контроль состояния без действий.

Права:

- только чтение.

## 5. UX принципы

### Плотность и ясность

Интерфейс должен быть рабочим и сканируемым:

- таблицы по умолчанию;
- карточки только для summary, onboarding, деталей и пустых состояний;
- фильтры сверху или в compact toolbar;
- side panel для деталей без ухода из списка;
- batch actions только там, где они реально безопасны.

### Статусы важнее декора

Каждая сущность должна быстро отвечать:

- можно продавать или нет;
- что именно мешает;
- кто следующий владелец действия: поставщик, админ, покупатель, платежный провайдер;
- когда статус обновился.

### Без технического шума

Не показывать:

- `CheckoutOrder.id`;
- provider ids;
- source ids;
- `paymentMode`;
- raw enum без перевода;
- внутренние payload/debug поля.

Показывать:

- короткий номер заказа;
- понятный статус;
- товар/событие;
- покупатель, если данные нужны оператору;
- сумма, комиссия, дата, канал.

### Финтех-аккуратность

Деньги и документы должны выглядеть надежно:

- суммы выравнивать по правому краю;
- статусы платежа и выплаты разделять;
- комиссии показывать рядом с gross/net;
- даты периода отчетов видны сразу;
- опасные действия подтверждаются.

## 6. Экран 1: Вход и выбор поставщика

Цель: пользователь понимает, в какой организации он работает.

MVP:

- login через существующий supplier key/dev selector можно оставить только для внутреннего smoke;
- production UX должен быть email/password или magic link через `SiteUser` + `SupplierUser`;
- если у пользователя несколько поставщиков, сначала selector организаций.

Состояния:

- нет доступа;
- приглашение не принято;
- поставщик архивирован/на паузе;
- роль viewer без прав на действие.

Figma:

- login;
- organization switcher;
- empty/no access;
- invite accepted.

## 7. Экран 2: Главная

Цель: за 30 секунд понять состояние продаж.

Блоки:

- верхняя строка: название поставщика, статус, режим продаж, роль пользователя;
- readiness summary: можно продавать или нужны действия;
- KPI: входные билеты, события, активные слоты, заказы за 7 дней, сумма продаж, к выплате;
- "Требует внимания": blockers по canSell/listing health;
- последние заказы;
- ближайшие слоты;
- ожидаемые документы/отчеты.

Главное действие:

- "Завершить настройку";
- "Добавить входной билет";
- "Создать черновик события";
- "Открыть заказы".

Не делать:

- маркетинговый hero;
- декоративные графики без решения;
- длинные поясняющие тексты.

## 8. Экран 3: Onboarding и реквизиты

Цель: довести поставщика до состояния, когда его товары можно продавать.

Checklist:

1. Основные данные организации
2. Юридические реквизиты
3. Банк и счет для выплат
4. Налоговый режим
5. Контакты для документов
6. Комиссия и условия
7. Платежная схема
8. Тестовый товар или событие
9. Smoke заказа

UX:

- слева checklist;
- справа форма текущего шага;
- наверху статус проверки;
- поля, которые меняет только админ, disabled с объяснением;
- submit как "Отправить на проверку", не "Сохранить и опубликовать".

Состояния:

- draft;
- submitted;
- needs changes;
- verified;
- rejected with comment.

## 9. Экран 4: Входные билеты

Цель: музеи, галереи, арт-пространства и другие площадки продают open-date/validity tickets без фейкового события.

Таблица:

- название;
- площадка;
- город;
- тип;
- статус;
- canSell;
- цена от;
- остаток;
- срок действия;
- обновлено;
- действия.

Фильтры:

- статус;
- canSell;
- площадка;
- город;
- тип;
- есть проблемы;
- цена отсутствует.

Деталь в side panel:

- основные данные;
- офферы и категории билетов;
- validity rules;
- остатки/capacity;
- readiness issues;
- история изменений;
- заявки на правки.

Основные действия:

- создать черновик;
- отправить на модерацию;
- изменить цену;
- закрыть продажи;
- открыть публичную карточку, когда появится catalog consumer.

## 10. Экран 5: События и черновики

Цель: поставщик видит афишу и может создавать/редактировать события в допустимой модели.

Три режима:

- imported ticketing system: read-only;
- internal sales: supplier drafts/admin approval;
- API sync: read-only или partner-api-managed по capability.

Таблица:

- событие;
- площадка;
- город;
- статус публикации;
- режим управления;
- ближайший слот;
- цена от;
- canSell;
- проблемы;
- обновлено.

Деталь:

- контент;
- медиа;
- SEO summary;
- расписание;
- цены;
- продажи;
- история заявок.

Правило:

- поставщик не публикует напрямую, если включена модерация;
- действие называется "Отправить на проверку", не "Опубликовать".

## 11. Экран 6: Расписание и слоты

Цель: оператор управляет временем начала, вместимостью и остатками.

Views:

- список слотов;
- неделя/месяц для плотного расписания;
- open-date settings для входных билетов и open-date событий.

Таблица слотов:

- дата;
- время;
- событие;
- вместимость;
- продано;
- доступно;
- цена от;
- статус;
- действия.

Действия:

- добавить слот;
- массово создать повторы;
- отменить слот;
- изменить вместимость;
- закрыть продажи.

Риск:

- импортные TC/TEP слоты read-only;
- нельзя случайно редактировать source-managed schedule.

## 12. Экран 7: Цены и готовность к продаже

Цель: отдельно видеть, почему товар нельзя купить.

Компонент canSell:

- status badge: "Готово", "Нужны настройки", "Заблокировано";
- список blockers;
- список warnings;
- next best action.

Цены:

- категории билетов;
- цена;
- старая цена;
- группа/количество;
- активность;
- capacity;
- источник: ручной, imported, API sync.

Не показывать:

- `sourceCode` как технический термин;
- raw enum.

Показывать:

- "ручная цена";
- "из билетной системы";
- "из API поставщика".

## 13. Экран 8: Заказы

Источник: PurchaseProjection.

Цель: поставщик видит свои продажи, не внутреннюю бухгалтерию Daibilet.

Таблица:

- номер;
- дата;
- товар/событие;
- слот или open-date;
- покупатель;
- статус;
- билеты;
- сумма;
- комиссия;
- к выплате;
- действия.

Статусы на русском:

- ожидает оплаты;
- оплачен;
- подтвержден;
- билет выпущен;
- отменен;
- возвращен;
- ошибка обработки.

Деталь заказа:

- состав покупки;
- покупатель и контакты, если нужны для исполнения;
- билеты/ваучеры;
- платежный статус;
- fulfillment статус;
- комиссия;
- история событий;
- заметки оператора;
- ссылка для поддержки.

Ограничение PII:

- viewer и бухгалтер видят меньше персональных данных;
- телефон/email показывать только ролям, которым это нужно.

## 14. Экран 9: Финансы

- основание;
- заказ/отчет;
- сумма;
- баланс после операции;
- комментарий.

Payouts:

- период;
- сумма;
- статус;
- дата выплаты;
- счет;

Статусы:

- черновик;
- на проверке;
- ожидает выплаты;

## 15. Экран 10: Отчеты и документы

Цель: бухгалтер может закрыть период без переписки.

Документы:

- акт;

- тип;
- период;
- статус;

Состояния:

- не сформирован;
- сформирован;
- ожидает подписи;
- подписан;
- требуется исправление.

## 17. Экран 12: Интеграции

Цель: показать тип подключения поставщика.

Типы:

- imported ticketing system;
- internal sales;
- API sync.

Для API sync:

- base URL;
- auth status;
- last success;
- last failure;
- consecutive errors;
- capabilities;
- issues.

Для imported ticketing system:

- read-only;
- источником управляет админ/каталог;
- поставщик видит заказы и статусы, но не редактирует source-managed сущности.

## 18. UI system

### Layout

- sidebar слева;
- topbar с supplier switcher, ролью и environment badge;
- content max-width не нужен для таблиц, таблицы занимают рабочую ширину;
- detail side panel 480-720 px;
- sticky action bar в формах.

### Tables

Обязательные паттерны:

- sticky header;
- сортировка;
- фильтры сверху;
- быстрые tabs;
- pagination;
- empty state;
- loading skeleton;
- error state с retry;
- сохранение фильтров в URL.

### Status badges

Цвета должны быть спокойными:

- success: готово/выплачено;
- warning: нужны действия;
- danger: заблокировано/ошибка;
- neutral: draft/read-only;
- info: на проверке/ожидает.

### Copy

Тон:

- коротко;
- операционно;
- без внутренней терминологии;
- "Нужно добавить цену", а не `MISSING_PRICE`;
- "Продажа закрыта: нет доступных билетов", а не `NO_TICKETS_LEFT`.

## 19. Figma handoff

Дизайнер должен отдать:

- desktop 1440;

- mobile/tablet только для просмотра, не для полноценной операционной работы;

- все empty/loading/error states;
- clickable prototype main flow;

## 20. Acceptance для вёрстки в `apps/supplier`

Готово, когда:

- поставщик логинится или выбирается в dev selector;
- видит Dashboard с readiness и последними заказами;
- видит свои входные билеты и canSell;
- видит свои события и слоты;
- видит заказы через PurchaseProjection без технических ids;
- видит финансы, выплаты, отчеты и документы хотя бы read-first;
- ошибки backend показываются честно, без mock fallback;
- все таблицы имеют фильтры и pagination;
- роли и PII ограничения заложены в UI policy;
- imported/source-managed сущности визуально read-only.

## 21. Когда верстать

Можно заказывать макеты сейчас: API read-контракт уже есть.

В production supplier LC расширять после:

- STUB path живой;
- поставщик видит smoke order;
- admin видит smoke order;
- buyer account видит smoke order;
- YooKassa sandbox credentials готовы, но `DAIBILET_YOOKASSA_CHECKOUT=1` еще не включен широко.

После макетов:

- Codex переносит UI в `apps/supplier` на `.159`;
- smoke логина поставщика;
- smoke заказов/входных билетов/готовности;
- polish перед широким привлечением поставщиков.
