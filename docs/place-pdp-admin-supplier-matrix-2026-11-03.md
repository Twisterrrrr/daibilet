# Place PDP: типы, шаблоны, админка и кабинет поставщика

Дата: 2026-11-03. Это аудит текущего кода и план связки; не миграция данных и не разрешение автоматически публиковать или индексировать площадки.

## Термины не смешиваем

| Слой | Текущее состояние | Роль |
|---|---|---|
| `PlaceType` | 12 значений: ARCHITECTURE, MONUMENT, MUSEUM, RELIGION, NATURE, URBAN, THEATRE, ENTERTAINMENT, FOOD, VENUE, TRANSPORT, OTHER | Основной предметный тип места и крупная навигация каталога |
| `placeSubtype` | Строковое значение на `Venue` | Уточняет конкретный предмет: например, причал, водопад, дворец, планетарий. Нужен контролируемый справочник/варианты, чтобы не накапливать разные написания |
| `PdpDocument.variant` | Сейчас 16 вариантов для мест и один для Event | Набор редакционных блоков и полей, доступных редактору |
| `Venue.pageTemplate` | Только DEFAULT и PIER_DEPARTURES | Особое поведение публичного шаблона, сейчас в основном для проверенных отправлений с причала |
| `Venue.pageStatus`, `Venue.isIndexable`, SEO-поля | Уже есть | Публичность и поисковая видимость; должны оставаться независимыми от типа и текста PDP |

Таким образом, «12 типов мест» не означают, что нужно создавать 12 разных приложений или таблиц. Нужен явный справочник соответствия **тип/подтип → рекомендуемый контентный вариант → допустимые блоки и поля**. Администратор может изменить рекомендацию; поставщик не может менять классификацию, SEO или публикацию.

## Текущий код

- Prisma уже содержит все 12 значений `PlaceType`, `placeSubtype`, `pageTemplate` и отдельный `PdpDocument` для Venue.
- В `apps/backend/src/pdp-documents.js` определены 16 вариантов для мест (`museum`, `theater`, `concert_hall`, `club`, `pier`, `landmark`, `nature`, `urban_area`, `food`, `attraction`, `transport`, `park`, `space`, `religion`, `sport`, `venue`) плюс отдельный `event`.
- Админская карточка `/admin/venues/[id]` уже подключает редактор, превью, выбор варианта и API чтения/сохранения. Есть начальное соответствие старых `VenueKind` и новых `PlaceType`; для `ARCHITECTURE` отдельного явного отображения сейчас нет. Вариант в документе хранится строкой и его соответствие PlaceType не валидируется как строгий контракт.
- Публичный сайт рендерит `PdpDocument` только со статусом READY. Публичный layout/template, контент документа, статус Venue и индексируемость — отдельные механизмы.
- В текущем `apps/web/app` нет маршрутов кабинета `/supplier/*`. Схемы и API общего EventChangeRequest не образуют готовый workflow изменений Venue/PdpDocument для поставщика.

## Рекомендуемое стартовое соответствие 12 PlaceType

Это дефолты редактора, а не жёсткие ограничения. Перед применением к существующим Venue их надо проверить на фактических местах.

| PlaceType | Рекомендуемый вариант контента | Возможные подтипы / особые поля |
|---|---|---|
| ARCHITECTURE | `landmark` | дворец, усадьба, крепость, историческое здание; история, архитектурные особенности, маршрут осмотра |
| MONUMENT | `landmark` | памятник, мемориал, скульптура; история и особенности посещения |
| MUSEUM | `museum` | художественный, исторический, научный, мемориальный; экспозиция, билеты, аудиогид, доступность |
| RELIGION | `religion` | храм, монастырь, собор; правила посещения, часы, ограничения фото/одежды |
| NATURE | `nature` | водопад, гора, озеро, пещера, заповедник; сезонность, маршрут, безопасность |
| URBAN | `urban_area` | парк, набережная, квартал, общественное пространство; точки внутри и прогулочные маршруты |
| THEATRE | `theater` | театр, оперная сцена, концертно-театральный зал; залы, репертуар, схема мест |
| ENTERTAINMENT | `attraction` | парк развлечений, зоопарк, планетарий, аттракцион; зоны, шоу, расписание, ограничения |
| FOOD | `food` | ресторан, кафе, гастропространство; меню, бронирование, правила посещения |
| VENUE | `venue` | клуб, концертная площадка, многофункциональный зал; пространства, услуги, правила входа |
| TRANSPORT | `transport` или `pier` | причал/терминал/станция; `pier` + PIER_DEPARTURES только при подтверждённой связи реальных отправлений с `EventSession` |
| OTHER | `venue` только как временный редакторский черновик | Не публиковать как автоматическую классификацию; поставить в очередь уточнения типа |

Спортивные площадки, концертные залы и городские пространства сейчас представлены отдельными контентными вариантами. Их можно оставить как **варианты редактора/профиля**, даже если тип по таксономии будет, например, `VENUE`, `THEATRE` или `URBAN`. Не менять родительский PlaceType ради выбора удобного PDP-варианта.

## Целевой экран админки

Карточка `/admin/venues/:id` остаётся одной сущностью с вкладками или секциями:

1. **Карточка и идентичность:** каноническое название, город, адрес, координаты, источник и provider IDs, связь с поставщиком, дубли/кандидаты.
2. **Классификация:** `PlaceType` → допустимые подтипы; рекомендации по контентному варианту; тип публичного layout; предупреждение при `OTHER` или противоречивой классификации.
3. **Информация PDP:** редактирование блоков по схеме выбранного варианта; общий переиспользуемый редактор; порядок блоков, факты и источники проверки, медиа с alt/авторством/правами, desktop/mobile preview.
4. **Связи:** события площадки, дочерние места, причалы и конкретные отправления, город/хаб, связанные подборки/статьи.
5. **SEO и публикация:** slug/canonical, title/description, `pageStatus`, `isIndexable`, checklist. Отдельно показывать, что индексируемость не включается от одного статуса READY.
6. **История и предложения:** diff «текущее → предложено», кто и когда изменил, решение редактора, возврат к прошлой версии.

Сейчас общая часть редактора уже работает, но для полноценной реализации нужны строгая валидация соответствия типа/варианта, явное отображение ARCHITECTURE, контролируемый список подтипов, роли/разрешения и workflow ревизий вместо прямого редактирования SEO/публикации.

## Кабинет поставщика

В кабинете поставщик работает с принадлежащими ему и разрешёнными местами, но не публикует PDP самостоятельно:

- **Связанное и управляемое поставщиком место:** поставщик предлагает фактические правки названия, адреса, описания, практических сведений и медиа с источником/правами. Изменения идут как заявка с preview/diff.
- **Импортированное место:** только чтение исходных значений и «Предложить исправление»; синхронизация остаётся источником истины для импортных полей.
- **Новое место:** заявка-кандидат с городом, адресом/координатами, предложенным типом, подтипом, практическими фактами и материалами. Самостоятельная публичная PDP не создаётся.
- **Недоступно поставщику:** подтверждение дублей/слияние, канонический slug, PlaceType окончательно, layout template, `pageStatus`, SEO metadata, `isIndexable`, публикация, страницы хабов и решение о типе причала/посадке.
- **Проверка:** Daibilet сравнивает исходное и предложенное, проверяет факты и права на изображения, применяет/отклоняет заявку, затем редактор отдельно управляет публичностью и индексированием.

До создания отдельного маршрута для place-request нельзя переиспользовать EventChangeRequest как будто это готовый API. Нужны supplier-scoped DTO/API с серверной фильтрацией владельца и отдельные разрешения на чтение/подачу заявки.

## Очерёдность реализации

1. Сверить перечень 12 PlaceType и подтипов с владельцем каталога; собрать существующие значения `placeSubtype` и найти разнобой/OTHER.
2. Утвердить registry `PlaceType + subtype → suggestedVariant + allowedSections + requiredFacts`; добавить автоматические проверки этой таблицы.
3. Довести карточку админки: фиксируем рекомендации, недостающий ARCHITECTURE, ошибки/конфликты, историю редакций и разделение «контент готов / страница опубликована / индексируется».
4. Спроектировать supplier DTO и маршруты отдельно для предложения нового места и предложения изменений. Ограничить по supplierId на сервере.
5. Добавить форму поставщику с текстом/фактами/медиа, источниками и просмотром статуса заявки. В поставщицком UX не показывать исполняющие публикацию/SEO-кнопки.
6. Проверить сценарии для музея, причала, городского пространства, гастро-места, импортированного кандидата и `OTHER`; затем тестировать на пилотном поставщике.

Не менять sitemap, canonical или индексацию мест в рамках одного только подключения редактора. Это отдельное решение на основании качества публичной страницы и подтверждённого типа/фактов.

## Реализовано в рабочей копии 2026-11-03

- Общий контракт в `packages/contracts/src/place-pdp.ts`: подписи всех 12 типов, рекомендация контентного варианта и специальное распознавание причалов/терминалов в `TRANSPORT`.
- Карточка админки сохраняет `placeType` и `placeSubtype`; рекомендация профиля показывается рядом с уже существующим редактором. Редакторский выбор профиля остаётся возможен.
- Добавлена отдельная таблица `SupplierPlaceRequest` и миграция. Поставщик с активным членством `OWNER`/`ADMIN`/`OPERATOR` может предложить новое место или фактические изменения связанного места. Место для изменения проверяется через активную связь `SupplierVenue`; поля классификации, SEO, slug, публикации и индексации не принимаются как изменяемые данные.
- `/supplier/places` показывает привязанные места, текущие заявки и формы предложений. Для существующего PDP поля секций зависят от выбранного контентного варианта; поставщик отправляет предложения, а не изменяет `PdpDocument`.
- `/admin/place-requests` — отдельная очередь с предложением и снимком текущего состояния. Редактор может запросить уточнение, отклонить или принять в редакционную работу. Принятие заявки **не применяет** данные автоматически: редактор переносит проверенные сведения в карточку площадки и отдельно управляет публикацией/SEO.
- Добавлены `GET /api/supplier/places`, `POST /api/supplier/place-requests` и защищённые общей admin-аутентификацией маршруты `/api/admin/supplier-place-requests`. Supplier API проверяет SiteUser bearer и принадлежность поставщику на сервере.

Граница готовности этой итерации: workflow подачи и редакционного решения есть; применение заявки в PDP как отдельная ревизия, каталог подтипов, полноценный аудит каждого поля/медиа и боевые роли уровня granular RBAC остаются отдельным следующим шагом. Миграция пока только в локальной рабочей ветке; production DB не менялась.
