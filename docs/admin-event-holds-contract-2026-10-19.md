# Административные брони на события

Статус: проект контракта. Основание для UX - `Admin_Lite.html` от 19.10.2026. Макет не выполняет серверных операций.

## Смысл операции

Администратор временно выводит часть инвентаря события из продажи для прессы, гостей или технических нужд. Бронь не является продажей, оплатой, заказом или выпущенным билетом. Снятие брони возвращает остаток в продажу, если остальные ограничения всё ещё разрешают продажу.

Для события с местами в зале бронь адресует конкретные места. Для свободной рассадки бронь адресует количество в категории билета и, если применимо, в слоте. Открытая дата без конечной общей квоты не может получить количественную бронь, пока для продукта не определён инвентарь.

## Текущее состояние кода

- `EventSession` хранит `ticketsVacant`, `capacityTotal`, `capacitySold`; `EventOffer` хранит `capacityTotal`, но не имеет прямой связи с `EventSession`.
- `decrementCapacity` в checkout резервирует остаток на время неоплаченного заказа; `releaseReservedCapacityInTransaction` возвращает его при отмене. Это другой вид резерва.
- В схеме нет отдельной административной брони, её владельца, причины, срока или аудита снятия. `ExternalTicket.origin=manual` описывает билет внешнего заказа, а не бронь инвентаря.

## Минимальный серверный контракт

1. `AdminInventoryHold`: id, eventId, sessionId?, offerId?, seatIds?, quantity, reason, comment?, status, createdBy, createdAt, releasedBy?, releasedAt?, expiresAt?, idempotencyKey.
2. Проверка в одной транзакции: событие и слот активны, источник допускает управление инвентарём Daibilet, остатка хватает, конкретные места не проданы и не забронированы. Повтор с тем же idempotencyKey возвращает ту же бронь.
3. Остаток для продажи вычисляется как `capacityTotal - sold - activeCheckoutReservations - activeAdminHolds`, с учётом правил источника. Для текущей модели `ticketsVacant` нужно явно определить, какие резервы она уже включает, чтобы не вычесть их дважды.
4. Создание и снятие пишут неизменяемое событие аудита. Снятие повторно не увеличивает остаток. Истечение срока обрабатывается идемпотентно.
5. API чтения возвращает для события/слота общую квоту, продано, ожидает оплаты, административно забронировано и доступно. API записи требует отдельного права `inventory.hold.manage`; чтение - `inventory.hold.read`. Поставщику можно показывать только его события и причину без внутренних комментариев.
6. Для внешних источников, чьей квотой управляет Ticketscloud/Teplohod или API поставщика, локальная бронь запрещена, пока адаптер не поддерживает подтверждённое бронирование и снятие в источнике. Ошибка/таймаут источника не превращается в успешную локальную бронь.

## Экран

В карточке события/слота: «Продано», «Ожидает оплаты», «Админ-брони», «Доступно»; список активных броней с автором, причиной и временем; форма количества или выбора мест; подтверждение создания/снятия с показом изменения остатка. Действия доступны только при серверном праве и поддерживаемом типе инвентаря. Если нет источника точного остатка, показывать «не рассчитано» и блокировать запись.

## Решения перед реализацией записи

- Нужна ли бронь без срока или обязательное `expiresAt` и максимальная длительность?
- Кому разрешено создавать/снимать бронь: SUPERADMIN, оператор каталога, сотрудник поддержки?
- Должна ли бронь позже превращаться в бесплатный/служебный билет? Это отдельная операция выпуска, с собственным основанием и учётом.
- Какие поставщики разрешают бронирование из админки и как их API подтверждает квоту?

Первый срез реализации: только внутреннее событие с собственной квотой и свободной рассадкой. Схему мест и внешний API-шлюз подключать отдельными адаптерами после проверки инвариантов на этом срезе.
