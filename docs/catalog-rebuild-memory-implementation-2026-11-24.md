# INC.504.5: оптимизация пика памяти пересборки каталога

Дата: 2026-11-24  
Ветка: `codex/catalog-rebuild-memory-20261124`  
База: `origin/cline/264a9` (`071f0170f2a1135ab6d34fb52b2a79d7bd02dabe`)

## Что изменено

- `apps/backend/src/public-catalog.dto.ts`: map идёт порциями по 80 строк с yield
  event loop; после преобразования raw SQL rows освобождаются до построения
  индексов. В лог добавлены RSS после освобождения строк, после построения
  индексов и полный elapsed time. Это замеры в контрольных точках, не системный
  максимум; значения в MiB округлены.
- `apps/backend/src/public-catalog-disk-cache.ts`: `sessionsBytes` считается
  по одному объекту за раз без дополнительной JSON-строки всего массива.

Форма snapshot, версия, атомарная запись, anomaly guard и семантика каталога не
менялись.

## Пример ресурсной экономии

Исходный кэш по handoff занимает около 17 MiB в UTF-8. Раньше writer создавал
строку `JSON.stringify(sessions)` целиком только для подсчёта байтов. Новый
writer сериализует каждый объект сессии отдельно, складывает размеры и добавляет
байты скобок/разделителей массива. Для 5 000 сессий это 5 000 небольших строк по
очереди вместо одной строки на весь массив.

Грубая верхняя оценка прежнего временного буфера - до 34 MiB в UTF-16 (17 MiB
UTF-8 × 2; реальный размер зависит от V8 и содержимого). Теперь временный буфер
ограничен размером одного DTO. Это расчёт по размеру snapshot, не замер RSS на
MSK.

Это убирает десятки MiB кратковременного пика на этапе записи при snapshot около
17 MiB. Оно **не объясняет и само по себе не устраняет** прежний RSS 3.2-4.0 GiB
и не подтверждает целевой пик <800 MiB. Для этого нужен отдельный этап с
измерениями на MSK и перепроектированием широкого `$queryRaw`/агрегации слотов.

Для масштаба: 17 MiB UTF-8 JSON и около 5 000 сессий - это уже крупная
сериализация, но меньшая часть измеренного 3+ GiB процесса. Нельзя умножать
пропорционально размер JSON и объявлять экономию 3 GiB: большая часть RSS может
приходиться на драйвер БД, Postgres client buffers, объекты слотов, DTO и индексы.

## Что измерять на MSK

Сначала снять baseline на одном ручном прогоне текущего worker: elapsed, RSS до
старта, пик из `systemd MemoryPeak`/`/usr/bin/time -v`, `sessions`, размер JSON,
`hasIndexes`. Затем на ветке выполнить тот же ручной прогон. Новые логи дадут
RSS по этапам, внешний peak сравнивать с baseline. Не запускать параллельно с
таймером и не менять лимиты/swap ради теста.

Критерии handoff остаются: ≥5000 sessions, <60 s, <800 MiB, стабильный таймер и
24 часа без OOM. Текущая итерация закрывает только лишнюю полную JSON-копию при
writer и добавляет измеримость; критерии памяти должны быть подтверждены на
проде до объявления INC.504.5 завершённым.
