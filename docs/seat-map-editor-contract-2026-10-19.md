# Схемы рассадки для залов и транспорта

Статус: проект продуктового и серверного контракта, 19.10.2026. Связан с [административными бронями](./admin-event-holds-contract-2026-10-19.md). Редактор и продажа конкретных мест ещё не реализованы.

## Решение

Инструмент проектировать сейчас, реализацию разделить на этапы. Схема - повторно используемый план зала или транспортного средства; инвентарь - состояние конкретного события и сеанса. Редактирование рисунка не должно менять уже проданные или забронированные места.

Поддержать три режима продажи:

1. `GENERAL_ADMISSION`: свободная рассадка, продаётся количественная квота. Схема не требуется.
2. `ZONED`: продаётся квота сектора, палубы, салона или категории. План помогает выбрать зону, но конкретное место не закрепляется.
3. `ASSIGNED_SEAT`: продаётся и бронируется конкретное место по стабильному ключу.

Режим задаётся для товара/сеанса, а не выводится из типа Place. Музей, концертный зал, автобус и теплоход могут предлагать разные режимы на разных продуктах.

## Сущности

- `SeatingLayout`: владелец (Place или транспортный объект поставщика), тип (`HALL`, `BUS`, `BOAT`, `OTHER`), название, статус draft/published/retired, версия, размеры холста и правила доступности.
- `SeatingZone`: секция, этаж, палуба или салон; порядок показа, подпись, вместимость для zoned-режима.
- `SeatingSeat`: неизменяемый `seatKey` внутри версии, зона, ряд, номер, координаты, угол, признаки доступности. Внешний ID поставщика хранится отдельно от нашего ключа.
- `SessionLayoutAssignment`: событие/сеанс, конкретная опубликованная версия схемы, режим продажи. Изменение версии для сеанса с продажами требует миграции соответствий мест и отдельного подтверждения.
- `SessionSeatInventory`: состояние места для сеанса. Доступно/бронь checkout/админ-бронь/продано/заблокировано - результаты подтверждённых операций инвентаря, а не свойства рисунка.
- `SeatCategoryAssignment`: связь места или зоны с категорией билета. Цена наследуется из предложения/слота; отдельное переопределение допускается только явным правилом.

Публичный билет содержит подписанные для человека зону, ряд и место, но каноническая связь для сканирования и возврата - `seatKey` + версия схемы + sessionId. Номер билета и номер места - разные идентификаторы.

## Редактор

Начать с шаблонов: прямоугольный зал с рядами, секторный зал, автобус с проходом, судно с несколькими палубами. Оператор может добавлять зоны, ряды, проходы, входы, сцену/экран, лестницы и недоступные места; клонировать схему; импортировать CSV с местами. Массовая нумерация должна показывать предпросмотр и конфликт дублирующих номеров.

В интерфейсе отдельно показывать:

- структуру схемы и вместимость по зонам;
- категории билетов и правило цены;
- состояние мест на выбранном сеансе;
- адаптацию для мобильного выбора места и доступность с клавиатуры;
- историю опубликованных версий и список сеансов, которые используют каждую версию.

Публикация запрещена при дублирующих `seatKey`, пересечении мест с проходом, неполной категории для мест в продаже или неразрешённой миграции проданных мест. Визуальные координаты хранятся нормализованно, чтобы план масштабировался на телефон, но выбор места всегда опирается на ID, а не на координату.

## Брони и конкурентная продажа

Админ-бронь конкретного места и checkout резервируют одну и ту же единицу инвентаря. Серверная транзакция атомарно переводит место из доступного состояния; повторный запрос с тем же ключом идемпотентен. Снятие админ-брони освобождает только места этой брони. Состояние мест нельзя вычислять из клиентского SVG или локального счётчика.

Для `ZONED` и `GENERAL_ADMISSION` работают количественные брони по зоне/категории или сеансу. Любая сумма доступных мест в UI должна быть получена из того же серверного источника, что проверяет checkout; если источник не подтверждает остаток, UI показывает «не рассчитано» и запрещает бронь.

## Схема поставщика по API

Редактор и собственный инвентарь мест относятся к внутренним продажам Daibilet. Если продажа целиком проходит в виджете Ticketscloud, его схема остаётся в этом виджете: переносить её в наш редактор или дублировать выбор места не требуется.

Для внутренних продаж через API поставщика сначала выяснить возможности конкретного API: можно ли получить геометрию/сектора/ряды, стабильный ID каждого места, актуальную доступность и версии схемы; можно ли атомарно забронировать место, подтвердить продажу, снять резерв и выполнить возврат. Также нужны сроки резерва и правила реакции на таймаут или изменение схемы. До подтверждения этих операций собственный выбор места для такого поставщика не включать. Схема и seat ID поставщика остаются источником истины; локальная визуализация, если понадобится, служит только представлением и не обещает доступность после ошибки синхронизации.

## Очерёдность

1. Реальная админ-бронь количества для собственного события со свободной рассадкой; аудит, идемпотентность, снятие.
2. Версионируемая схема и редактор без продажи конкретных мест; превью и публикационные проверки.
3. Привязка опубликованной схемы к сеансу, категории и количественным зонам.
4. Атомарный checkout, админ-бронь, возврат и перевыпуск конкретного места; билет с зоной/рядом/местом.
5. Подключение схемы поставщика для внутренних продаж через API только после проверки перечисленных возможностей и согласования контракта адаптера.

До шага 4 нельзя показывать кнопку «Выбрать конкретное место» покупателю. Редактор схемы может работать раньше, но он не создаёт товар, квоту или право продажи сам по себе.
