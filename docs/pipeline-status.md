Deploy now requires a full 40-character `sha` and `expected_ref`. CI checks
branch ancestry before build, checks out that SHA, and records DEPLOY_SHA and
BUILD_ID in the run name/logs/summary (GitHub's own head_sha still identifies
the workflow revision). The build runs once in CI. The uploaded server script
checks artifact SHA and BUILD_ID before switching the checkout or .next.
Public home must return HTTP 200; home failure restores the previous build
and checkout when a previous build exists. A missing optional literal HTML
marker fails verification without automatic rollback.

#### Оценка «+14 / +28 кликов» — методологическая ошибка

Расчёт «2 779 URL × CTR 0,5% = 14 кликов» неверен: **CTR применяется к показам,
а не к URL.** У URL нет показов, пока страница не проиндексирована и не
показана. Нельзя умножать количество URL на CTR.

Корректно: сначала оценить **показы** новых URL, и только потом клики.
Ориентир — текущие 7 135 показов на 328 индексированных площадок, то есть
≈ 22 показа на URL за 28 дней. При 2 779 новых URL это грубая оценка
**≈ 61 000 показов**; при CTR 0,5% — **≈ 300 кликов/мес**, при 1% — **≈ 600**.

Разница с «14 кликами» — в 20 раз. Оценка **занижена на порядок**, потому что
была посчитана от URL вместо показов. Но и это потолок: 22 показа на URL —
среднее по уже индексированным, а новые URL начинают с нуля.

> Правило: **сначала показы, потом CTR, потом клики.** Умножение URL на CTR
> даёт выдуманную цифру — ровно тот класс ошибки, что уже ловили четыре раза
> за сессию («87% из головы», «190 из чужого задания», «19 228 строк вместо
> событий», «2 685 вместо 2 779»).

### `/places/c/*` — не дубль, а пагинируемый каталог (уточнено 30.09)

Первоначальный вывод «52 URL дублируют `/cities/*`» **неверен.** Проверка кода
и пагинации показала: это самостоятельный каталог со своей пагинацией.

`apps/web/src/lib/catalog-url.ts`:
```ts
/** Indexable city catalog with its own canonical URL and server-side pagination. */
export function cityPlacesCatalogHref(citySlug: string, page = 1): string {
  const path = `/places/c/${encodeURIComponent(citySlug)}`;
  return page > 1 ? `${path}?page=${page}` : path;
}
```

**Совпадение слагов с `/cities/*` — да, но сущности разные:** хаб города
(«Казань» — обзор) против пагинированного каталога площадок города с
постраничным листингом. Совпадает только slug.

**Пагинация живая и индексируемая:**

| URL | `h1` | canonical | `robots` | Площадок |
|-----|------|-----------|----------|---------|
| `/places/c/kazan` | «Места и площадки: Казань» | self | `index, follow` | 24 |
| `/places/c/kazan?page=2` | «Места и площадки: Казань» | **self с `?page=2`** | `index, follow` | 24 |
| `/places/c/kazan?page=3` | — | — | — | 24 |
| `/places/c/kazan?page=99` | пусто | **канона нет** | **`noindex`** | 0 |
| `/places/c/ulyanovsk?page=2` | пусто | — | — | 0 |

Границы обработаны корректно: за концом — `noindex`, канон на `page=99` не
выводится. **Косметика здесь в порядке.**

**Почему нет в выдаче — не из-за дублей, а из-за пагинации.** Ни одна страница
`?page=2+` в sitemap не попадает: `entry()` добавляет только
`cityPlacesCatalogHref(slug)` без параметра. При этом 13 из 16 площадок на
вторых страницах **есть** в `venues.xml` и индексируются отдельно — Google знает
их по прямым ссылкам, а хаб с пагинацией нет.

**Вывод: вариант В (301 на `/cities/*`) — не делать.** Снёс бы рабочую пагинацию
и навигацию по страницам. Правильный выбор — **Б с оговоркой:** оставить
`/places/c/*` в карте, но снять `index` с `?page=2+` либо доанонсировать пагинацию.

> Урок: совпадение слага не означает совпадение сущности. Проверять назначение

#### РЕШЕНО 30.09: порядок 410 — A → B → C → D. Исполнитель: Codex

Выбран вариант «(а)», с явной оговоркой: **шаг A обязателен**, без него шаг D

| Шаг | Что | Обратимость | Владелец |
|-----|-----|--------------|----------|
| **A** | `/events/[slug]` различает «нет события» (404) и «было и завершилось» (410) | безопасный | Codex |
| **B** | `isIndexable = false` для 267 `SINGLE` | обратимый | Codex |
| **C** | дождаться переобхода; сверить 267 с GSC, вывести из скоупа то, что даёт трафик | — | Codex |
| **D** | сами 410 | **необратимый** | Codex |

**Почему A первым.** В `cached-event-data.ts` нет ни одного упоминания 410, а DTO
трактует любой не-200 как недоступность, публичная страница 410 не отдаёт
(проверено на проде 30.09: `/events/zooteatr-…` → 404). Если backend начнёт
отдавать 410 раньше, чем веб научится его различать, страницы молча отдадут 404 —
ровно тот эффект, которого шаг D и должен заменить. **Решение принимает страница,
а не DTO:** тогда `cached-event-data.ts` продолжает видеть отсутствие данных, и
учить его не нужно.

**Почему C перед D.** Сверка с GSC логичнее после снятия с индексации и переобхода:
видно фактическое поведение, а не только исторические клики. Вариант «(б)»
(вывести из скоупа по кликам до снятия) поглощается шагом C.

**Почему 410 первым, а не `isVenuePublic`.** 410 — необратимый по времени: шаг C
требует календарных дней, не итераций, и счётчик тем временем поедет. Эффект
`isVenuePublic` медленный по определению (правка индексации видна в GSC через
недели) и откладыванием не портится. Сущности разные: 410 — `/events/[slug]`,
`isVenuePublic` — `/venues/*` и `/locations/*`. Пересечение одно: 7 из 12
baseline-URL под `noindex` делают выборку Wave 1 на площадках нечитаемой, но
правка 410 этого не чинит.

### Причина и починка `deploy-verify.sh` (закрыто 29.09)

Дело **не** в отсутствии метаданных — все три значения на сервере верные:

```

apps/web/.next/DEPLOY_SHA   0db363aa03ee560ded8009a096d6f18ac577a326   (41 байт, с переводом)
```

**Next.js пишет `BUILD_ID` без завершающего перевода строки.** Скрипт склеивал выводы
подряд, и `BUILD_ID` с `git rev-parse HEAD` слипались в одну строку — `mapfile`

`nuhrSXN_O6Q7GUs1us9lM0db363aa03ee560ded8009a096d6f18ac577a326`, с фиксом — три
отдельные строки.

BUILD_ID. Синтаксис проверен, разбор даёт 3 элемента.

Guard не сломан был — он был слеп к формату входа. Но опасен именно тем, что
маскировал реальные метаданные под «опять не прочиталось».
