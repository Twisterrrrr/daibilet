# Доступ сотрудников к админке: аудит и проект RBAC

Дата: 2026-10-15. Область: сотрудники Daibilet в Next-админке, catalog API и finance API. Учётные записи поставщиков и покупателей остаются отдельными контурами.

## Вывод

RBAC нужен **до** выдачи доступа к финконтру нескольким сотрудникам. Переключатели пунктов меню не защищают данные: право проверяется на сервере для страницы, каждого API-запроса, экспорта и действия. Общий Basic Auth остаётся временным доступом владельца до готовности персональных сессий; нельзя включать редакторские аккаунты через общий пароль.

`@daibilet/contracts/admin-access` определяет профили и разрешения без иерархии. Схема БД содержит `AdminUser`, `AdminInvitation`, `AdminSession` и `AdminAuditLog` (миграция `20261016120000_admin_staff_identity`). Backend имеет login/me/logout, SUPERADMIN-only приглашения, принятие одноразового приглашения и first-admin bootstrap. Route-permission guard действует только при `DAIBILET_ADMIN_RBAC_ENFORCE=1`; без него admin/catalog маршруты остаются на общем Basic Auth. В режиме guard неизвестные маршруты закрыты, и покрытие пока неполное. UI входа, безопасные role-scoped DTO, применение MFA и finance bridge остаются незакрытыми.

## Что показал legacy SPBBOATS

Полезно взять:

- `AdminUser`: персональный email, хеш пароля, активность, время входа; возможность отключить сотрудника.
- Вход с ограничением попыток, короткой access-сессией, обновлением и отзывом refresh-сессии.
- Защиту от блокировки последнего владельца при изменении ролей.
- Журнал действий с привязкой к `userId` и сущности.
- Управление сотрудниками в настройках вместо правки env-файла.

Не переносить буквально:

- `RolesGuard` строит одну лестницу `OWNER > ADMIN > EDITOR > VIEWER`; она не выражает различие финансиста, SEO, копирайтера и инженера. `EDITOR` в legacy получает чтение settlement, а `VIEWER` — детали финансовых расчётов.
- Если `@Roles` не указан, guard пропускает любого вошедшего. В новой админке неизвестный маршрут/действие закрыт по умолчанию.
- Общий `AuditInterceptor` пишет тело мутирующего запроса как `after`, не снимает настоящее `before` и может занести секреты/персональные данные. Для финансовых действий нужен структурированный журнал разрешённых полей и результата операции.
- Сырой refresh token в браузере и один hash на пользователя ограничивают контроль отдельных устройств. Нужны серверные сессии с индивидуальным отзывом.

## Текущее состояние Daibilet

- Next `/admin` и catalog `/api/admin/*` принимают один Basic Auth из env. `adminApiFetch` пересылает тот же заголовок браузера на catalog API.
- Страница настроек прямо указывает, что роли являются UX-заделом и не действуют.
- Finance API находится на другом хосте; Next вызывает его серверным токеном. Этот токен удостоверяет **сервис Next**, а не конкретного сотрудника. Finance не должен принимать роль из заголовка, который мог бы задать браузер.
- В БД есть `SupplierUser`/`SupplierRole` для ЛК поставщика; это не модель сотрудника Daibilet. Права поставщика нельзя использовать как admin-права.
- Текущий `supplierPortalRoleAllowsRequest` разрешает любой GET вошедшему поставщику и различает роли в основном на запись. Это отдельный пилотный policy; не копировать его как правило чтения для сотрудников, где заказы, реквизиты и документы имеют разные уровни доступа.

## Модель

1. Персональный `AdminUser` с состоянием `INVITED/ACTIVE/SUSPENDED`, подтверждённым email и отметкой версии прав. Создание по приглашению владельца; пароль или иной фактор задаётся самим сотрудником. Отдельные серверные сессии с истечением и отзывом при увольнении/смене прав.
2. Профили из [операционного плана](./admin-operations-bible-2026-10.md): суперадмин, руководитель продукта, оператор поддержки, финансист, редактор каталога, копирайтер, SEO, инженер интеграций, аудитор. Сотруднику можно назначить несколько профилей.
3. Серверный список разрешений по действиям: `orders.read`, `orders.pii.read`, `refunds.request`, `refunds.execute`, `payouts.read`, `payouts.approve`, `documents.read`, `catalog.edit`, `catalog.publish`, `seo.edit`, `content.edit`, `integrations.read`, `integrations.retry`, `staff.manage`, `audit.read` и т.д. Роль задаёт набор разрешений; роль не заменяет проверку области (поставщик, объект, среда).
4. Разрешения на финансовые операции, экспорт персональных данных, публикацию и управление сотрудниками назначаются отдельно. Сервисные токены не получают пользовательскую роль. Оператор идентифицируется в подписанном короткоживущем утверждении от доверенного Next/backend gateway; finance проверяет подпись, срок, аудиторию и permission для операции.
5. Меню и кнопки строятся из того же списка разрешений, но это только UX. Прямой URL, server action, catalog API и finance API повторно проверяют право. На 401/403 данные не рендерятся и не кэшируются.
6. Журнал хранит actorId, permission, объект, действие, результат, время, correlationId и безопасный diff. Не писать пароль, токен, полный платёжный payload или лишние персональные данные.

## Порядок внедрения

| Срез | Результат | Проверка |
|---|---|---|
| 0. Инвентаризация | Все маршруты Next, catalog и finance размечены permission и типом данных | Не осталось неразмеченных admin endpoints; неизвестный endpoint закрыт |
| 1. Личность | AdminUser, приглашение, вход, серверные сессии, отзыв и восстановление доступа | Два пользователя имеют разные сессии; отключённый теряет доступ; владелец не может удалить последнего владельца |
| 2. Read RBAC | Страницы, списки, детали, экспорт, меню и ошибки 403 | Копирайтер не видит даже прямой URL/API финансов; финансист не меняет статью |
| 3. Действия | Catalog publish, refund request/execute, payout, настройки, retry интеграции с отдельными permissions | Запрет сохраняется при прямом POST; каждое действие имеет actor и audit record |
| 4. Finance bridge | Сервисная аутентификация Next → finance плюс проверяемое утверждение о сотруднике | Один service token без утверждения сотрудника не даёт произвольную денежную операцию |
| 5. Переход | Owner-сессия проверена на двух хостах, Basic Auth убран из пользовательского потока | Отозванный общий пароль не открывает admin; supplier/buyer auth работает отдельно |

На первом выпуске настроек достаточно списка сотрудников, приглашения, назначения готовых профилей, отключения и журнала изменений. Произвольный конструктор разрешений и per-user исключения добавлять после проверки базовых профилей. Финансовые действия не открывать новым ролям, пока срезы 1–4 не прошли smoke на обоих хостах.

## Приёмочные сценарии

1. Копирайтер открывает прямой `/admin/orders` и catalog `/api/admin/orders`: 403 без строк, покупателя и счётчиков. Финансовый endpoint finance также отказывает.
2. Финансист читает отчёт агента, но прямой запрос на публикацию события получает 403.
3. Оператор поддержки видит заказ с допустимо маскированным контактом, создаёт заявку на возврат, но исполнить возврат не может.
4. Инженер видит ошибку адаптера и повторяет безопасный обмен; не видит реквизиты и платёжные данные.
5. Смена профиля или блокировка сотрудника отзывает действующие сессии на Next, catalog и finance. Журнал содержит владельца изменения.
6. Суперадмин не может отключить последнего активного суперадмина. Отказ и успех денежного действия отражаются в аудите без секретов.

## Реализованный срез 2026-10-25

В `codex/rbac-finance-unified` выполнены персональный вход/выход Next, page permission guard, отбор навигации, guards на server actions/direct Prisma, forwarding HttpOnly session cookie в backend и signed actor assertion для внутренних finance read/operation endpoints. Backend order DTO применяет серверное PII-маскирование по permission. RBAC включается только явно через `DAIBILET_ADMIN_RBAC_ENFORCE=1`; при выключенном флаге остаётся Basic Auth переходный режим.

TOTP enrollment и verification ещё отсутствуют. Поэтому чувствительные финансовые permissions удаляются из session permission set до подтверждения MFA и не попадают в finance actor assertion. Это fail-closed подготовительная граница, а не завершённый RBAC rollout или готовность к реальным выплатам. Smoke и тесты на production не выполнялись; перед включением флага нужны MFA, route/action inventory audit и проверка согласованной схемы БД.
