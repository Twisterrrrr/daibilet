# Решения владельца по дублям площадок (03.10)

Приняты после разбора: 152 группы «имя + город», и отдельно класс
«один адрес в 20 городах» (пример — Турбаза «Спутник»).

## Решение 1. Турбаза «Спутник» — одна физическая площадка

Факт: 20 записей, адрес у всех `FC2R+W6 Ефремкино, Республика Хакасия`,
координаты совпадают в 6-м знаке. Привязка к 20 городам — ошибка импорта
(«ближайший крупный город» вместо фактического).

**Действие: оставить одну запись в правильном городе, остальные 19 удалить.**
Тип правки — ручная, не по правилу.

**Что проверить ДО удаления:**
- к какой из 20 записей привязаны события; удаление без переноса осиротит их;
- город-владелец: Ефремкино — Ширинский район Хакасии, ближайший крупный
  город Минусинск, а не Абакан;
- не осталось ли у площадки в других источниках (TC) своих адресов.

## Решение 2. Панорама (Сочи) — это ресторан, не концертный зал

Факт: две записи, адрес один (`ул. Альпийская, 7/7` и `7`),
`kind` = CONCERT_HALL (24 сессии) и CLUB_BAR_RESTAURANT (14 сессий).

**Действие: слить в одну запись с `kind = CLUB_BAR_RESTAURANT`.**

**Что проверить ДО слияния:**
- **24 сессии у записи с CONCERT_HALL против 14 у ресторана.** Слияние не должно
  потерять 24 сессии — их надо перевесь на каноническую запись;
- какая из двух записей выживает: у выжившей должны остаться все события;
- canonicalPath у выжившей должен стать `/venues/...` (ресторан → institution);
- старый адрес должен отдавать 301, а не 404.

## Общее правило (применять после этих двух)

```
1. одинаковое имя + один город + один адрес  → сливать, редирект
2. одинаковое имя + один город + РАЗНЫЕ адреса → не трогать, это разные места
3. одинаковый адрес + координаты в разных городах → класс Турбазы, ручная правка
```

**Слияние — через редирект, а не удаление.** Причина: по GSC 40% кликов Google
идёт на старые `tc-`-адреса с хешем (228 из 565). Удаление превратит их в 404,
редирект сохранит трафик и даёт откат.

Механика уже есть: `apps/web/src/lib/place-slug-aliases.ts` — алиасы
«старый slug → канонический». Расширение этого файла дешевле, чем удаление записей.

**Ручная проверка обязательна** для групп, где у обеих записей есть события
и разный `kind`: имя и город не различают «один venue, дважды занесённый» и
«два разных заведения по одному адресу». Различает афиша.

## Решение 3. История версий по описаниям — 5 полей, после поставщиков

Принято 03.10. Под историю: `shortDescription`, `description`, `hookFact`,
`wayToFind`, `openingHours`. Реализация — после появления поставщиков.

**Что уже готово:**
```
Venue.descriptionOverridden      защита от затирания импортом, ec70b6f96
EventChangeLog                   образец истории для событий, схема L1379
```

**Образец для копирования:** `EventChangeLog` содержит `supplierId`,
`actorType`, `actorSiteUserId`, `action`, `diff Json`, `createdAt`,
индексы по сущности/поставщику/актору/действию. В `EventChangeLogAction`
есть `RESTORED` — откат уже предусмотрен. Для `Venue` нужно то же самое:
модель, поле `venueChangeLogs` в `Venue`, запись в лог в точке, где
ставится `descriptionOverridden`.

**Открытое:** поля `openingHours` в схеме `Venue` нет. Добавление колонки —
часть этой же задачи, а не предшествующий шаг.

**Почему отложено:** сейчас descriptions пишет один человек; история нужна,
когда начнут писать несколько (админ и поставщик). Реализация до появления
`SupplierUser` создала бы таблицу, которую пришлось бы переделывать под
второго редактора.

Решение принято вне репозитория, в переписке. Зафиксировано здесь, чтобы
набор полей не пришлось восстанавливать.
