## Задача 1 — номер билета (`S0.TKT.1`)

**Сейчас:** отдельного `ticketNumber` нет. Номера хранятся в
`FulfillmentItem.providerData` (JSON). Отдельной сущности билета в схеме нет.

**Формат LOCKED** (`docs/qa.md`), не менять:
```
internal:     DB… + seq / TKT-…     (без ФИО в коде)
external:     код партнёра как есть
```

**Что сделать:**
1. Инвентаризация: что сейчас в `providerData` оплаченного билета 4157776 —
   есть ли там номер вообще. **Не начинай с правки.**
2. Решение: выпускать номер в существующей `FulfillmentItem` или завести
   отдельную сущность. Обоснуй по трём критериям: **скан на входе по номеру,
   уникальность, печать/QR.** Критерий скан — главный: площадка должна
   проверить билет, и это ручной контроль на первом договоре.
3. Уникальность: номер не должен переиспользоваться. Учесть, что
   `publicCode` уже аллоцируется, — не плоди второй параллельный генератор.
4. Миграция для уже оплаченных sandbox-заказов (их единицы).

## Задача 3 — письма: нет ретрая

**Это находка на живых данных.** Заказ 4157776 оплачен в 19:46:37, SMTP не был
настроен, письмо не ушло. После настройки SMTP **повторных попыток не было** —
отправка инициируется вебхуком один раз и не повторяется.

Логи на `.184`:
```
[buyer-ticket-mail] SMTP not configured - skip ticket mail → .../checkout/ticket/4157776
```
повторялось несколько раз за час — то есть код пытается, но **не перезапускает
отправку после появления конфигурации**.

SMTP теперь настроен (`smtp.timeweb.ru:587`, от `info@daibilet.ru`).

**Что сделать:** механизм доставки с ретраем.
- Не полагаться на вебхук: если SMTP недоступен, письмо должно уйти позже.
- Очередь доставки с попытками и backoff; состояние видно в логах.
- Ручная переотправка по заказу — сейчас пути нет.

**Проверка:** симулировать недоступный SMTP на оплате → письмо уходит после
починки без повторной оплаты.
