## Задача 1 — refund и cancel (`S0.OPS.3`)

Ничего не изобретай: `CheckoutOrder`, `FulfillmentItem`, `CheckoutPayment` уже
работают на живых данных. Нужно:

```
1. Инвентаризация: что уже есть по возврату, что отсутствует. Ответ по коду.
2. Полный возврат и частичный — по решению владельца зафиксировать, что
   поддерживается, остальное явно отклонять, а не молча игнорировать.
3. Идемпотентность: повторный вызов refund не должен удвоить возврат.
4. Взаимодействие с ЮKassa: какие статусы у неё, какие у нас, где расхождение.
5. Отмена заказа поставщиком отдельно от отмены покупателем.
```

**Проверка:** тест, что два вызова refund дают одну операцию; что отменённый
заказ нельзя оплатить повторно.

## Задача 2 — финансовый контур поверх существующих моделей

**Не миграция схемы — модели уже есть.** Нужна логика и вызовы:

```
1. Комиссия: SupplierCommissionRule уже объявлен — кто его читает и когда
   применяется. Правило по умолчанию и переопределение для поставщика.
2. Проводки: когда начисляется заказ — SupplierLedgerEntry. Одна на событие,
   идемпотентно.
3. Закрытие периода: SupplierSettlement создаётся вручную или по расписанию.
   Что считается «периодом закрыт» и что после этого нельзя менять.
4. Отчёт: SupplierReport + ReportLine — что показываем поставщику в первом
   отчёте. Минимум: период, сумма, комиссия, итог, расшифровка по заказам.
5. Выплата: PayoutStatus и PAYOUT — провести запись в проводках и зафиксировать,
   что фактическая отправка денег вне нашего контура (мы формируем документ,
   а не переводим деньги).
```

**Решение, которое нужно от владельца:** первая выплата — мы генерируем
документ для бухгалтерии или отправляем через банк-клиент? От этого зависит
объём задачи 5. По умолчанию — документ, фактическая передача вне нас.

поставщика ограничена его `SupplierVenue`.

## Решения владельца по выплатам, возвратам и доступу (04.10)

**Выплаты — по запросу поставщика из ЛК.** Не после каждой продажи.

```
Схема: деньги копятся на балансе поставщика, раздел «Вывод средств»
        в ЛК. Поставщик запрашивает выплату, дальше процесс.
Комиссия: считается с продаж (SupplierCommissionRule), НО
        распределение денег между платформой и поставщиком сейчас НЕ проводится
        по каждой продаже — только начисление на баланс.
Позже:   агентский признак и мгновенный развод через ЮKassa —
        отдельная задача, не в этом объёме.
```

Значит в этом объёме: **начисление на баланс + заявка на выплату + её обработка.**
Фактическая отправка денег — вне контура, мы формируем документ.

**Возвраты — всегда по решению администратора.** Автоматики нет.

```
Поддержать частичный возврат (за часть билетов) и полный (за все билеты).
Решение принимает админ, площадка не инициирует сама.
Требует: как технически отбирать билеты для частичного возврата.
```

**Админ может входить в ЛК поставщика, и его действия там видны.**

```
Это меняет модель доступа: не «роль поставщика», а вход админа с
идентификацией актора. EventChangeLog уже различает actorType
(SYSTEM / SITE_USER) — админские действия должны попадать туда же,
с supplierId поставщика, в чей кабинет вход.
```
