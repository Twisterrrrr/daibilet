## Разделение по смыслу

**Достопримечательность — ценность сама по себе**, даже без афиши:
`MONUMENT`, `MUSEUM_ART_SPACE`, `TEMPLE`, `ATTRACTION`, `PARK`,
`OUTDOOR_LOCATION`, `PIER`.

**Зал без афиши — оболочка**: `CONCERT_HALL`, `THEATER`, `SPORT_ACTIVITY_SPACE`
без сессий.

**Служебное**: `MEETING_POINT`, `VENUE`, `OTHER`, и `CLUB_BAR_RESTAURANT` /
`GASTRO`, у которых нет ни афиши, ни описания.

## Задача 1 — инвентаризация (до правок)

1. По каждому `kind` и по каждой группе (`с афишей` / `без афиши`) — сколько
   сейчас **в индексе**, сколько `noindex`, сколько попадает в sitemap.
2. Для 1 779 достопримечательностей: сколько имеет `description`, `heroImageUrl`,
   координаты, `shortDescription`. Это определяет, что вообще можно показать.
3. Сколько из 401 «залов без афиши» (228 CONCERT_HALL + 173 THEATER) сейчас
   индексируется. **Похоже, что почти все** — это надо подтвердить.
4. Есть ли среди 1 779 записи с `description` ≥120 симв. — они готовы, остальные нет.

Результат: `docs/research/venue-indexability-20261002/`, markdown + CSV, в git.

## Задача 2 — правило индексности (план, не применение)

Предложи правило в терминах существующего `evaluateVenueIndexability`
(`apps/web/src/lib/`), а не новую сущность:

- **индексировать:** достопримечательность с описанием **или** с афишей;
- **noindex:** зал без афиши и без описания;
- **на усмотрение owner:** зал без афиши, но с хорошим описанием — полезная
  страница или тонкая? Обоснуй цифрами из задачи 1.

Отдельно: что делать с 241 дублем названий. Слияние запрещено — «Дом культуры»
в Саратове и в Екатеринбурге это разные площадки, и схожесть даст HIGH, а слияние
уничтожит записи. Варианты: развести slug, снять с индексации одной, или пометить
канонической. Дай цифры по каждому варианту.

## Чего НЕ делать

- **Не писать контент.** Ни одного описания. Это инвентаризация и план.
- **Не чистить БД** без согласия owner.
- **Не расширять контент-гейт** и не трогать allowlist.
- **Не вводить `/{city}/venue/{slug}`.** Уникальный `slug` уже есть, публично
  не используется, а хеш-хвост в URL не резолвится (404).
- **Не считать через API.** `/api/public/venues` игнорирует `offset`,
  `/api/admin/events` — фильтры по дате. Только прямые запросы к БД.
  Для сверки: `Event` в БД 103 833, админ-API показывает 8 428 — это группировка
  серий, а не дефект.
