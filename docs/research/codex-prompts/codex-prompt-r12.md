## Задача 1 — `S0.TKT.2`: выпуск билетов

**Состояние сейчас:** отдельной сущности билета нет. Номера хранятся в
`FulfillmentItem.providerData` (JSON). Модель богатая — `checkoutOrderId`,
`checkoutItemId`, `lineItemIndex`, `status`, `amountKopecks`, `refundedKopecks`,
`externalOrderId`. Опираться на неё, не плодить параллельную.

**Требование:** при переходе заказа в оплаченное — выпуск билетов, Path A = 1 и
более на количество.

### Формат номера — LOCKED
```
internal:     DB… + seq / TKT-…     (без ФИО в коде)
external:     код партнёра как есть (TC KXM-…, order #…)
```
Канон в `docs/qa.md`. Не менять.

### Что сделать
1. Инвентаризация: где сейчас происходит выпуск, что пишется в `providerData`,
   что показывает `/checkout/ticket/{publicCode}`. **Не начинай с правки.**
2. Решение: выпускать как `FulfillmentItem` (один на билет, `lineItemIndex` уже
   есть) или завести отдельную сущность. Обоснуй по трём критериям: скан по
   номеру, уникальность, печать/QR.
3. План миграции для уже оплаченных заказов sandbox (их единицы).
4. Идемпотентность: повторный вызов не должен выпустить второй билет.
   Учти, что webhook `payment.succeeded` может прийти дважды.
