# Places: типизация, сверка PDP и передача Cline

Дата: 2026-10-15. Рабочая ветка каталога: `feat/next-monorepo`. Публичный сайт: `apps/web`; `apps/public` является legacy. Исходник редакционной подборки: `C:/Users/twist/Downloads/PDP.xlsx`.

## Границы источника

В Excel 1 598 строк. Это полный редакционный источник только для городских хабов, которые уже подготовлены владельцем. Это не полный список Places и не основание скрывать все другие существующие PDP. На момент аудита в prod есть 4 524 `Venue`, из них 1 859 опубликованы. В старом `VenueKind.PIER` встречаются объекты без подтверждённой посадки; в `CONCERT_HALL` встречаются пабы и арт-пространства. Старый kind не является доказательством нового типа.

## Словарь

Каждый Place имеет один основной `placeType` и один `placeSubtype`. Родительские типы: `ARCHITECTURE`, `MONUMENT`, `MUSEUM`, `RELIGION`, `NATURE`, `URBAN`, `THEATRE`, `ENTERTAINMENT`, `FOOD`, `VENUE`, `TRANSPORT`, `OTHER`. `OTHER` допустим только как временное состояние на проверке.

`isMainPlace` отвечает за «Главные места»; `hubTags` отвечает за редакционные разделы, включая «Гастро». Поэтому ресторан может быть `FOOD/restaurant` и не входить в «Гастро» хаба. `placeRoles` хранит функциональные роли (например, `boarding_point`), которые могут меняться; роли не заменяют тип. `pageTemplate` задаёт особый PDP, например `pier_departures`.

Для транспорта: `TRANSPORT/pier`, `river_terminal`, `sea_terminal`, `railway_station`, `bus_station`, `metro_station`, `cable_car_station`, `airport`, `marina`. `bus` не является подтипом места. Для природы необходим предметный подтип, например `waterfall`, `mountain`, `cave`, `lake`, `river`, `beach`, `forest`, `hot_spring`, `island`, `cape`, `reserve` или `park`.

Коммерческий PDP причала со временем отправлений допустим только после проверки связи `TripDeparture` с конкретным `EventSession` и точкой посадки. `Event.venueId`, старый `PIER` и упоминание адреса в описании этого не доказывают. Туристический маршрут хаба и билетный рейс остаются разными сущностями.

## Данные и процедуры

| Файл | Назначение |
|---|---|
| `data/places/pdp.json` | Нормализованный снимок Excel с типом, подтипом, признаками, описанием, промптом изображения и причинами проверки |
| `scripts/build-pdp-places.py` | Повторяемая сборка снимка из Excel |
| `scripts/audit-pdp-venues.py` | Чтение: кандидаты на связь с существующей Venue |
| `packages/db/scripts/sync-pdp-places.mjs` | Сухой прогон по умолчанию; `--apply` обновляет лишь подтверждённые совпадения и создаёт новые записи в `HIDDEN` |
| `scripts/classify-imported-venues.py` | Чтение: предложения типизации по всему импортированному каталогу |
| `data/places/imported-taxonomy.json` | 1 383 предложения, для которых название подтверждает старый kind и точный подтип |
| `packages/db/scripts/sync-imported-taxonomy.mjs` | Сухой прогон по умолчанию; `--apply` требует прежние ID, точное название, kind и пустые поля новой типизации |

Порядок при выпуске: резервная копия БД → `pnpm db:deploy` → выкладка API и web из одного SHA → сухой прогон обоих скриптов → применение каждого отдельно → проверка количества изменённых записей и публичных маршрутов. Не применять SQL вручную. Отсутствие строки в Excel не вызывает удаление. Ошибки координат, дубли source key, неоднозначные совпадения и соседние объекты остаются на проверке. Новые записи с этим импортом не индексируются и не показываются до проверки изображения и фактов.

## Изображения и факты

Описание Excel служит исходным материалом, а не инструкцией системы. Текст картинки создаётся отдельно для каждой конкретной локации. До публикации нужен визуальный референс этого же объекта, проверка геометрии и окружения, прав на изображение и атрибуции. Генерации Золотого моста с неверной геометрией отклонены; не использовать их в PDP. `data/places/image-references/golden-bridge.json` фиксирует этот кейс.

Нельзя подставлять типовое изображение города как фотографию точного объекта. Нельзя выдумывать адрес, цену, расписание, точку посадки или доступность. Если референс не найден, карточка остаётся скрытой. Для лицензированной реальной фотографии хранить автора, источник, лицензию и факт обработки.

## Работа Cline

Cline может полировать UI уже поддержанных полей в `apps/web`: чипы `/places`, отображение типа и подтипа на обеих разновидностях PDP, состояние скрытого кандидата в админке и экран ручной сверки. Для изменений `packages/db`, `packages/contracts`, `apps/backend`, слияния дублей, публикации и массовой записи сначала согласовать DTO и конкретный сценарий с владельцем каталога. Не менять старый `VenueKind` ради новой навигации: он ещё участвует в URL-family и старых интеграциях. Не выводить расписание причала из общего списка событий.

Перед UI-правкой Cline проверяет `AGENTS.md`, свежий `origin/feat/next-monorepo`, этот документ и фактические DTO. При передаче результата нужны SHA, файлы, скриншоты desktop/mobile и проверка реального фильтра `/places?type=food`, а также PDP существующего музея и новой скрытой записи. Если API не отдаёт нужный факт, описать gap без моковых данных.

## Критерии завершения всего контентного проекта

1. Все строки Excel имеют подтверждённые city, координаты, тип, подтип и связь с существующей Venue либо обоснованную новую запись.
2. У новых публичных PDP есть проверенные факты и реалистичное изображение именно этого объекта; у изображений оформлены права.
3. Удаление из завершённого хаба применяется только к подтверждённой редакционной принадлежности, без скрытия сторонних PDP.
4. Импортированные площадки классифицированы или стоят в явной очереди проверки; транспортные объекты не выводят ложных рейсов.
5. Prod smoke подтверждает `/places`, фильтры `food`, `religion`, `urban`, `transport`, существующие PDP, новые опубликованные PDP, sitemap/noindex и отсутствие регрессии продаж.
