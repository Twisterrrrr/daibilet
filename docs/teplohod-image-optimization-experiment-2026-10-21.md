Уже снятый мобильный Lighthouse для Event1360 подтверждает, что именно эта обложка была LCP-элементом: viewport 412×823, эмулированный DPR 1,75, `currentSrc` был исходным JPG 1536×1024. Для одного Event1360 JPG AVIF q55 при ширине 750 дал 86 414 Б за 3,33 с wall / 3,31 с CPU; WebP q75 дал 82 410 Б за 106 мс wall / 148 мс CPU. На этом примере AVIF больше и намного дороже по CPU. Не использовать этот результат как универсальное сравнение всех изображений.

Пять одновременных преобразований одного уже загруженного буфера в WebP 750 дали в среднем 82 410 Б, 178 мс wall и 473 мс суммарного CPU. Во время теста `/robots.txt` ответил 200 за 11 мс. Эти операции выполнялись отдельным Node-процессом, поэтому результат **не моделирует** конкуренцию за CPU внутри `daibilet-web` или несколько реальных запросов к `/_next/image`.

## Проверка настоящего Next Image Optimizer на staging

Staging на том же MSK-хосте работает на Next 16.4 и использует production-версию конфигурации Image Optimizer. Чтобы проверить разрешённый в его `remotePatterns` источник, точные байты Teplohod временно положили под непублично используемый путь `/images/optimizer-lab-20261021/` на production и staging. Optimizer запросил их как `https://daibilet.ru/images/optimizer-lab-20261021/...`; проба измеряет тот же Sharp/Next cache путь, но сама по себе не проверяет разрешение домена `cdn.teplohod.info` или компонент PDP. Исходники с обоих хостов после теста удалены.

| Запрос к staging Next | Результат | Кэш |
|---|---:|---:|
| Event1360, WebP 750, q75 | 82 410 Б, 0,295 с | Повтор: 7 мс |
| Event1360, WebP 1200, q75 | 179 330 Б, 0,327 с | Повтор: 55 мс |
| Event1332 PNG, WebP 750, q75 | 61 348 Б, 0,303 с | 200 |

Ответ содержит `Cache-Control: public, max-age=2592000, must-revalidate` и `Vary: Accept`. После удаления временного исходника прогретый Event1360 WebP всё ещё отвечал 200, 82 410 Б за 17 мс. Значит Next disk cache действительно отдаёт производную без повторного чтения origin.

Произвольная ширина 1125 px вернула 400: Next принимает только `deviceSizes`/`imageSizes` из `next.config.ts`. В текущем конфиге есть 1200 px и 1920 px, но нет 1125 px. Для теста использовали штатную ширину 1200 px. При реализации проверить фактический `srcset`/`currentSrc` на DPR 2–3; сам факт наличия 1200 в конфиге не гарантирует, что браузер выберет её при каждом viewport.

Пять одновременных запросов к staging `/_next/image`, со свежими WebP q85 разных размеров 640/750/828/1080/1200, получили 200 за 0,61–0,75 с каждый. Совокупное wall time — 775 мс, CPU cgroup `daibilet-web-staging` вырос с примерно 213 до 246 МБ памяти, CPU набрал 1,144 с. В этот интервал `/api/health` ответил 200 за 82 мс, `NRestarts` не вырос. Повтор тех же пяти кэшированных вариантов завершился за 86 мс, прибавив 51 мс cgroup CPU; TTFB каждого был 38–63 мс. Тест выполнялся на staging-сервисе с лимитом памяти 1,2 ГБ, не в production `daibilet-web`.

## Вывод для реализации

Байтовый потенциал на этих трёх исходниках подтверждён: сокращение примерно в 18–25 раз для WebP шириной 750. Это не измеряет выигрыш LCP. На проверенной PDP обложка была LCP-кандидатом в Lighthouse, но перед внедрением проверить 750/1125 px на реальных мобильных viewport и DPR 2–3, включая URL и размер реально выбранного файла.

Staging подтвердил, что Next Image Optimizer и его 30-дневный cache работают с приемлемым временем на пяти параллельных запросах, а повторы почти не тратят CPU. При этом есть два разных варианта внедрения: заранее собранные WebP в `/images/` вообще исключают Sharp на запросе; on-demand optimizer тратит CPU при первом запросе и отдаёт готовый файл из cache дальше. Нынешняя проба проверила второй вариант на staging, не поменяв PDP-код.

Для Teplohod не менять общий приоритет AVIF/WebP: текущая страница обходит optimizer через `unoptimized`, а `remotePatterns` сами по себе этого не меняют. Глобальный `formats: ['image/avif', 'image/webp']` выбирает AVIF для поддерживающих его браузеров; поэтому чтобы гарантировать WebP и избежать дорогого AVIF пути, нужен заранее созданный WebP URL либо отдельный image loader/маршрут с явно WebP-ответом. Включать это сначала для малой выборки и подтвердить полным PDP тестом.

Откат без сборки пока не обеспечен. Для него путь исходник/производная должен задаваться данными или внешней runtime-конфигурацией; переключатель, вшитый в клиентский код, обычно потребует web deploy. Cline должен включить механизм отката в дизайн до активации широкой выборки.

## Чек-лист для Cline

1. Выбрать 3–5 реальных PDP/карточек, включая Event1360; сохранить исходные URL, размеры и контрольные суммы.
2. Генерировать WebP варианты 750 и 1125 px вне запроса SSR; устойчивый URL должен кэшироваться. Проверить кэш-хиты и срок хранения.
3. На мобильном Chrome зафиксировать LCP node, viewport, DPR и выбранный `currentSrc`; сделать 2–3 прогона до/после.
4. Через реальный путь оптимизатора проверить 5 параллельных запросов с прогретым и холодным кэшем. Одновременно измерить CPU, RSS/cgroup, TTFB `/robots.txt` и PDP, 5xx и длительность Sharp.
5. Успех: байты LCP-картинки заметно ниже, LCP улучшается или не деградирует, TBT не растёт, SSR/5xx остаются в обычном диапазоне, повторный запрос не запускает кодирование снова.
6. AVIF для Teplohod рассматривать только если на выборке он выигрывает по байтам без неприемлемой CPU-стоимости. Для Event1360 на текущих параметрах он не прошёл.
7. До широкого включения добавить runtime rollback, затем наблюдать healthcheck, TTFB, RSS/heap/cgroup и 5xx несколько дней.

## Ограничения и незавершённые измерения

- Сравнение Lighthouse после изменения не проводилось: production код изображений не менялся.
- Пять параллельных запросов `/_next/image` проверены внутри `daibilet-web-staging`; аналогичный тест внутри production `daibilet-web` не проводился.
- Lighthouse после замены URL на реальной PDP не запускался: производственная страница и исходный компонент остались без изменений.
- Многодневное наблюдение SSR невозможно подтвердить в этой сессии. Healthcheck продолжает штатные часовые heartbeat; после релиза требуется проверить логи через несколько дней.
- Freshness работает, и 100 sitemap дат совпали с API. Старый cached sitemap успел обновиться; повторная ручная инвалидация больше не нужна.
