## Проба Sharp на MSK

Источник `cdn.teplohod.info`, ответ 200. Выполнялась отдельным короткоживущим Node-процессом на том же MSK-хосте, а не через Next Image Optimizer и не внутри cgroup `daibilet-web`.

| Изображение | Оригинал | Размер | WebP 750 px, q75 | Sharp wall / CPU |
|---|---:|---:|---:|---:|
| Event1360 JPG | 1 526 004 Б | 1536×1024 | 82 410 Б | 109 мс / 171 мс |
| Event51 JPG | 1 671 095 Б | 1536×1024 | 88 448 Б | 95 мс / 97 мс |
| Event1332 PNG | 1 523 774 Б | 3410×2288 | 61 348 Б | 135 мс / 137 мс |

Для Event1360 ширина 1125 px дала 162 816 Б и 180 мс wall / 195 мс CPU. Это подходит для проверки на DPR 3, но выбор кандидата должен подтвердить фактический `srcset` в браузере.

Уже снятый мобильный Lighthouse для Event1360 подтверждает, что именно эта обложка была LCP-элементом: viewport 412×823, эмулированный DPR 1,75, `currentSrc` был исходным JPG 1536×1024. Из 7,2 с LCP resource-load phase около 6,5 с заняла загрузка картинки. Этот Lighthouse — отдельное измерение страницы до любых изменений; Sharp-проба не доказывает, что WebP уже улучшил LCP.

Для одного Event1360 JPG AVIF q55 при ширине 750 дал 86 414 Б за 3,33 с wall / 3,31 с CPU; WebP q75 дал 82 410 Б за 106 мс wall / 148 мс CPU. На этом примере AVIF больше и намного дороже по CPU. Не использовать этот результат как универсальное сравнение всех изображений.

Пять одновременных преобразований одного уже загруженного буфера в WebP 750 дали в среднем 82 410 Б, 178 мс wall и 473 мс суммарного CPU. Во время теста `/robots.txt` ответил 200 за 11 мс. Эти операции выполнялись отдельным Node-процессом, поэтому результат **не моделирует** конкуренцию за CPU внутри `daibilet-web` или несколько реальных запросов к `/_next/image`.

## Вывод для реализации

Байтовый потенциал на этих трёх исходниках подтверждён: сокращение примерно в 18–25 раз для WebP шириной 750. Это не измеряет выигрыш LCP. На проверенной PDP обложка была LCP-кандидатом в Lighthouse, но перед внедрением проверить 750/1125 px на реальных мобильных viewport и DPR 2–3, включая URL и размер реально выбранного файла.

Генерировать WebP производные заранее или при загрузке и кэшировать их. Не запускать многократные Sharp-трансформации синхронно при SSR. Включать только несколько тестовых изображений и затем провести нагрузочную пробу через реальный маршрут/кэш Next, наблюдая CPU, RSS, TTFB и 5xx. Для Teplohod не менять общий приоритет AVIF/WebP: источник сейчас обходится через `unoptimized`, а `remotePatterns` сами по себе этого не меняют.

Откат без сборки пока не обеспечен. Для него путь исходник/производная должен задаваться данными или внешней runtime-конфигурацией; переключатель, вшитый в клиентский код, обычно потребует web deploy. Cline должен включить механизм отката в дизайн до активации широкой выборки.

## Чек-лист для Cline

1. Выбрать 3–5 реальных PDP/карточек, включая Event1360; сохранить исходные URL, размеры и контрольные суммы.
2. Генерировать WebP варианты 750 и 1125 px вне запроса SSR; устойчивый URL должен кэшироваться. Проверить кэш-хиты и срок хранения.
3. На мобильном Chrome зафиксировать LCP node, viewport, DPR и выбранный `currentSrc`; сделать 2–3 прогона до/после.
4. Через реальный путь оптимизатора проверить 5 параллельных запросов с прогретым и холодным кэшем. Одновременно измерить CPU, RSS/cgroup, TTFB `/robots.txt` и PDP, 5xx и длительность Sharp.
5. Успех: байты LCP-картинки заметно ниже, LCP улучшается или не деградирует, TBT не растёт, SSR/5xx остаются в обычном диапазоне, повторный запрос не запускает кодирование снова.
6. AVIF для Teplohod рассматривать только если на выборке он выигрывает по байтам без неприемлемой CPU-стоимости. Для Event1360 на текущих параметрах он не прошёл.
7. До широкого включения добавить runtime rollback, затем наблюдать healthcheck, TTFB, RSS/heap/cgroup и 5xx несколько дней.

## Ограничения и незавершённые измерения

- Сравнение Lighthouse после изменения не проводилось: production код изображений не менялся.
- Не проводился 5–10-поточный тест `/_next/image` внутри `daibilet-web`; текущая проба — только Sharp отдельным процессом.
- Многодневное наблюдение SSR невозможно подтвердить в этой сессии. Healthcheck продолжает штатные часовые heartbeat; после релиза требуется проверить логи через несколько дней.
- Freshness работает, и 100 sitemap дат совпали с API. Старый cached sitemap успел обновиться; повторная ручная инвалидация больше не нужна.
