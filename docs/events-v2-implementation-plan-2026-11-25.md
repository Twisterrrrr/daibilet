# Events V2 — план реализации

Дата: 2026-11-25

Ветка: `codex/events-v2-implementation-20261125`

Основа: `origin/feat/next-monorepo` (`0c6e5d71e`).

Документ переводит утверждённую архитектуру Events V2 в последовательность реализации. Он не вводит новые продуктовые решения и не меняет исходное ТЗ.

## Зафиксированные решения

- `/afisha` — редакционная витрина; `/events` — самостоятельный коммерческий каталог. `/afisha2` остаётся preview-маршрутом.
- `Event` и `AdmissionProduct` остаются самостоятельными сущностями, отображаемыми в одной выдаче `/events`.
- Каноническая страница AdmissionProduct: `/admissions/[slug]`. Страница `/venues/[slug]` остаётся страницей объекта; checkout URL не является canonical продукта.
- Один продукт может иметь несколько офферов. Продукты разных поставщиков не объединяются без подтверждённой идентичности.
- Действующие способы покупки сохраняются. В текущей работе изменяется только публичное чтение и представление каталога; платёжный runtime не расширяется.
- Комплексные продукты с несколькими местами и различными правилами посещения пока не включаются в каталог.
- `boat_trip` — стабильный тип водной прогулки; `DATE_ON_REQUEST` — согласованный режим на будущее. Новые значения Prisma не добавляются до проверки необходимости миграции.

## Что есть в текущей кодовой базе

- Prisma уже содержит `Event`, `EventSession`, `EventOffer`, `AdmissionProduct` и `AdmissionOffer`.
- `Event` поддерживает `OPEN_DATE`; backend уже выводит для него текст «Открытая дата» без фиктивного ближайшего сеанса.
- `AdmissionProduct` имеет собственные validity-поля и связь с одним `Venue`.
- Web уже читает публичную finance projection для страниц Venue и городских блоков через `finance-projection-client.ts`; у карточки AdmissionProduct есть существующий gate `canSell`.
- Общий web-контракт каталога пока описывает Event-карточки. Контракт AdmissionProduct существует только как web projection shape, не как каталоговый DTO в `@daibilet/contracts`.
- Публичный admission list API поддерживает query, city, venue, supplier, type и offset-пагинацию до 100 записей. В текущем read-контракте нет фильтров цены и действия билета на выбранную дату.
- В каталожной админке есть классификация Event по Category/Subcategory/Tag. Поля AdmissionProduct для нового предметного типа, тематики, аудитории и режима бронирования в редакторе каталога не обнаружены.
- `/admissions/[slug]` отсутствует. Существующий `/checkout/admissions/[slug]` используется в purchase flow и не должен переименовываться или становиться страницей продукта.

## Этапы

### 1. Архитектура и DTO

Добавить общий discriminated DTO для каталога: `productKind: EVENT | ADMISSION`, стабильный `productId`, canonical href, город, место, категории/тип, цена, доступность и поля карточки. Event-поля расписания и Admission-поля срока действия остаются типизированными по вариантам, а не маскируются под общий сеанс.

Определить серверный composition layer, который читает обе публичные проекции. Фильтры, сортировка, total и пагинация применяются к объединённому набору на сервере. Браузер не загружает полный каталог для фильтрации.

До реализации сверить ограничения пагинации и cache TTL обеих проекций. Если finance read API не может отфильтровать цену/дату и вернуть полный счётчик, добавить только необходимые параметры в read DTO/API; checkout, YooKassa и платежные операции не менять.

### 2. Классификация и админские поля

Существующие широкие категории и URL остаются без изменения. Новые контролируемые поля добавляются параллельно и не переопределяют старую категорию автоматически.

Для продукта администратор должен уметь задавать основной предметный тип, несколько тем, признаки аудитории и режим бронирования. Политика подтверждения поставщика отделена от режима времени. `6+` хранится как ограничение возраста и само по себе не устанавливает аудиторию `family`.

Сначала проверить, покрывают ли существующие Category/Subcategory/Tag и EventKind/AdmissionValidityMode требуемую семантику. Создавать Prisma-поля и миграции только для выявленных пробелов и после фиксации DTO.

### 3. Backend и публичные маршруты

- Добавить серверную объединённую выдачу Event + AdmissionProduct с точными фильтрами, сортировкой, пагинацией и счётчиками.
- Дата фильтра включает Event-сеансы выбранного дня и AdmissionProduct, срок действия которого включает выбранный день; просроченные билеты исключаются.
- Добавить AdmissionProduct в общий `/api/public/search`; подсказка ведёт на `/admissions/[slug]`.
- Добавить SSR-страницу `/admissions/[slug]` с собственными metadata/canonical и данными продукта. Покупка остаётся на текущем существующем пути.
- Не объединять одинаковые названия и Venue без явной проверенной связи идентичности.

### 4. UI и адаптивность

После стабилизации backend/DTO подключить общий каталог и карточку AdmissionProduct. Сохранить редакционный `/afisha` и самостоятельный `/events`. Глобальная шапка всегда использует global search; поля афиши и каталога явно показывают контекст Events.

Проверить desktop, tablet и mobile: сетку карточек, фильтры, календарь, поиск и подсказки, overlay шапки, длинные названия и отсутствие горизонтального переполнения.

### 5. Проверка и staging

Проверить Event с сеансами, Event `OPEN_DATE`, Admission `OPEN_DATE`, истёкший билет, фильтры даты и цены, сортировку, пагинацию, глобальный поиск, прямую страницу AdmissionProduct, отказ finance API и сохранение существующего способа покупки. Проверить canonical, sitemap, SSR/ISR и отсутствие дублей. Staging — после завершения реализации; live не выкладывать без отдельного запроса владельца.

## Ограничения текущей итерации

- Не менять финансовые операции и платёжные настройки.
- Не добавлять поддержку комплексных билетов.
- Не выполнять массовую переклассификацию исторических Event.
- Не создавать дубликаты AdmissionProduct в таблице Event.
- Не менять старые URL, canonical или category filters без совместимого адаптера.

## Статус реализации

Первая вертикаль реализации находится в коммитах `337581c51` и далее на этой ветке:

- В `@daibilet/contracts` добавлен discriminated DTO объединённого каталога.
- Серверный глобальный поиск включает опубликованные AdmissionProduct и ведёт на `/admissions/[slug]`; полный поиск показывает билеты в разделе «События» вместе с Event.
- Создана SSR-страница `/admissions/[slug]` с canonical, validity-информацией и переходом по существующему checkout path.
- Sitemap включает отдельный чанк опубликованных индексируемых AdmissionProduct.
- В Admin добавлен список и редактор существующих полей AdmissionProduct: тип, прежняя категория/подкатегория, срок действия и окно продаж. Backend валидирует связи классификации; Prisma schema и миграции не менялись.
- Backend, web и contracts typecheck проходят после локального `pnpm db:generate`.

Текущая Prisma-схема не хранит темы и аудиторию для AdmissionProduct; это остаётся блокером полной многомерной классификации и не замещается свободным текстом в админке. Продолжение списка этапов находится в статусе реализации ниже.

### Вертикаль единого каталога (в работе)

- Добавлен серверный `/api/public/catalog`: Event читается из текущего public catalog API, AdmissionProduct - из finance read projection; общий фильтр, сортировка, total и offset применяются на сервере. Результаты и API-ответ кешируются на 300 секунд.
- `/events`, городские `/[city]/events` и подборки, использующие `CatalogShell`, получают общий DTO при SSR и последующих запросах. Карточки AdmissionProduct ведут на `/admissions/[slug]`, показывают режим/срок действия и не придумывают сеанс.
- Единая сетка поддерживает карточки, строковый и табличный режимы. Старые Event-only rails остаются Event-only.
- Страница билета позволяет выбрать действующий тариф; выбранный существующий `AdmissionOffer.id` передаётся через текущую checkout форму. Новый payment handler и finance operations не добавлялись.
- В AdmissionProduct каталоге учитывается `canSell` от finance projection, активный тариф и категория из существующей связи Category/Subcategory. Дата учитывает пересечение выбранного диапазона со сроком действия; OPEN_DATE не получает фиктивный timestamp.
- Global search и sitemap получили проверку публикации, индексируемости (для sitemap/search), активного поставщика, PLATFORM checkout, действующих окон продаж/валидности, остатка и активного тарифа от 100 ₽.
- Добавлены unit-проверки смешанной сортировки, OPEN_DATE, сроков действия и блокировки недоступного продукта.

Для mixed-data smoke создана временная изолированная БД `daibilet_events_v2_smoke_20261125` в локальном Docker через `pnpm db:deploy`; добавлены один синтетический Event и пять синтетических AdmissionProduct с теми же slug, что у finance mock. Основные локальная БД и staging-копия не менялись. Штатный TS backend запущен на `4002`, Next на Webpack на `3103`: `/api/public/catalog` вернул 6 записей (1 Event + 5 AdmissionProduct); пагинация `limit=2` на трёх страницах вернула 6 уникальных ID. Глобальный поиск через backend/Next вернул Event по `тестовый` и AdmissionProduct по `Зелёный`; `/events`, `/events/[slug]`, `/admissions/[slug]` и `/sitemaps/admissions.xml` ответили 200, sitemap содержит 5 тестовых канонических URL.

С отдельной пустой finance projection `/api/public/catalog` сохранил Event: `total=1`, единственный `productKind=EVENT`, без AdmissionProduct. Это проверяет пустую выдачу Admission на изолированном локальном контуре. GET `/checkout/admissions/virtual-museum-entry?offer=virtual-offer-museum-child` ответил 200; выбор тарифа, создание заказа и оплата не выполнялись. Для визуального локального просмотра mixed-каталога использовался `http://localhost:3103/events`.

Проверки 2026-11-25: web typecheck и backend typecheck прошли; `pnpm --filter @daibilet/web test:ci` - 398/398; backend `test:ts` с локальной Docker-БД на порту 5438 - 298/298. В браузере подтверждены пять разных входных билетов в каталоге, корректные индивидуальные `/admissions/[slug]` ссылки и открытая дата без фиктивного сеанса. Визуально проверены desktop 1265 px (три колонки) и tablet 765 px (две колонки). Mobile визуально ещё не проверен: доступный browser control не поддерживает переопределение viewport. Реальное оформление заказа намеренно пропущено по решению владельца. Composition ограничивает finance projection 1 000 продуктами на запрос и возвращает ошибку вместо неполного total, если лимит превышен. Staging остаётся перед выпуском.
