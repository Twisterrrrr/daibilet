# Organizer email intake (info@daibilet.ru)

Организаторы присылают доп.инфо и фото о событиях на `info@daibilet.ru` (почта на Timeweb).
Пайплайн: IMAP → staging на сервере → ручное ревью → публикация в каталог.

## Ставка на безопасность

- Креды IMAP — только через env (`ORGANIZER_IMAP_USER` / `ORGANIZER_IMAP_PASS`),
  никогда в репозиторий. Пароль — app-password из панели Timeweb.
- Ничего не публикуется автоматически: письма попадают в staging, оператор
  проверяет текст и фото перед apply (правило «не выдумывать факты»).

## Поток

1. **Fetch** — `node apps/worker/bin/run.mjs organizer-inbox`
   (или `node scripts/ingest-organizer-emails.js --since-days 3`).
   Стейджит каждое письмо как `tmp-organizer-inbox/<key>/record.json` + фото.
   Ссылка `daibilet.ru/events/<slug>` в письме автоматически становится `eventSlug`.
   **Фильтр отправителя**: стейджатся только письма от `agent@ticketscloud.com`
   и пересылки владельца `v.butin@yandex.ru` (Ticketscloud шлёт организаторские
   письма на личную почту, владелец пересылает их на `info@daibilet.ru`).
   Остальные отправители пропускаются. В пересланном письме ссылка на событие
   сохраняется в теле — `eventSlug` подхватывается автоматически; тема с
   префиксом «Fwd:» на матчинг по названию не влияет (при отсутствии ссылки
   оператор дописывает `eventSlug` в record.json вручную).
2. **Ревью** — оператор читает `record.json`: сверяет текст, фото, событие
   (без ссылки в письме — дописать `eventSlug` в record.json вручную).
3. **Apply** — `node scripts/apply-organizer-email.js --key <key> --with-text --apply`.
   Лучшее горизонтальное фото (если оно лучше текущей обложки) →
   `apps/web/public/images/organizer/<slug>/` + `EventOverride.imageUrl`;
   остальные фото остаются в staging. Текст → `EventOverride.description`
   (проверки: без строк дат-сеансов, без HTML, normalizeUserFacingCopy).

## Backfill: уже имеющиеся письма

Скрипт идемпотентен: каждое письмо стейджится в папку с именем = хеш Message-ID,
повторный прогон перезаписывает те же записи, дублей не появляется. Поэтому
старую почту закрываем одним прогоном с широким окном:

```bash
# 1. сначала посмотреть объём (ничего не пишет, кроме last-run.json)
node scripts/ingest-organizer-emails.js --dry-run --since-days 365 --limit 1000

# 2. затем застейджить всё окно
node scripts/ingest-organizer-emails.js --since-days 365 --limit 1000
```

(`--limit` по умолчанию 50 — для backfill поднять; если писем больше, повторить
прогон, выборка идёт от старых к новым.)

Политика разбора старых записей при ревью:

1. **Событие уже прошло** — текст не заливать (расписание в нём устарело),
   запись пометить/удалить. Фото при желании оставить в staging как архив.
2. **Событие текущее/будущее** — обычный apply (`--key <key> --with-text --apply`).
   Проверка «событие уже прошло» автоматическая: apply сверяет активные сессии
   события в БД и отказывается заливать текст/фото, если последняя сессия уже
   прошла (override — флагом `--force`). Open-date сессии (без даты) не дают
   событию «закрыться»; если активных сессий нет вовсе — выводится предупреждение
   и решение остаётся за оператором.
3. **Фото площадки без явной привязки** — можно сохранить как справочные
   материалы, но не привязывать к событию задним числом.

## Hero-обложка из письма (вариант А)

При apply скрипт сам решает, станет ли фото из письма обложкой события:

1. Все фото из письма оцениваются: разрешение ≥ 800×600, только горизонтальные
   (16:9 / 4:3). Вертикальные, мелкие и явно негодные остаются в staging.
2. Лучший кандидат сравнивается с текущей обложкой (`EventOverride.imageUrl` →
   `Event.imageUrl`): замена, если текущей нет / это генер-заглушка / текущая
   меньше и хуже по форме. Решение и причина печатаются в логе (`REPLACE/KEEP`).
3. При `--apply` фото копируется в `apps/web/public/images/organizer/<slug>/` и
   пишется `EventOverride.imageUrl`.
4. Остальные фото остаются в staging как материалы события.

Ограничения (осознанно):
- **Водяные знаки / коллажи / логотипы на весь экран не детектируются
  автоматически** — это ревью оператора. Правило: «лучше средняя, но своя
  обложка, чем плохое фото организатора».
- Яркость (тёмное/пересвеченное) не проверяется — нет декодера изображений
  в рантайме; критерий остаётся на ревью.

## Б (бэклог, следующий спринт) — галерея события

Когда закончим с текстами и финконтуром:

1. **Модель**: таблица `EventImage` (id, eventId, url, isHero, sortOrder) или
   массив `galleryUrls` в `EventOverride` (по образцу venue-editorial-packs).
   Таблица — `packages/db`, отдельным коммитом на ревью владельцу.
2. **Загрузка**: из staging (фото писем уже лежат там с привязкой к event_id)
   и/или через ЛК поставщика, когда он будет готов.
3. **UI**: компонент-галерея под Hero на PDP события (образец — галерея
   площадок в `venue-editorial-packs.ts`).
4. **JSON-LD**: массив `image` в разметке Event (Schema.org любит несколько
   картинок).
5. Вертикальные фото из писем (сейчас остаются в staging) — материал для неё.

## Cron (после выкладки кода на MSK)

```cron
*/15 * * * * cd /opt/daibilet && node apps/worker/bin/run.mjs organizer-inbox >> /var/log/daibilet/organizer-inbox.log 2>&1
```

Env для сервиса (systemd `daibilet-worker` или crontab): `ORGANIZER_IMAP_USER=info@daibilet.ru`,
`ORGANIZER_IMAP_PASS=<app password>`, по умолчанию `ORGANIZER_IMAP_HOST=imap.timeweb.ru:993`.

## Код

- `scripts/lib/organizer-email-intake.js` — парсинг/матчинг (unit-тесты рядом)
- `scripts/ingest-organizer-emails.js` — IMAP fetch → staging
- `scripts/apply-organizer-email.js` — ревью → фото в каталог + опц. текст
