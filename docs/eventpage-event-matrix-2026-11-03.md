# Матрица событий и связей с EventPage

Статус: рабочее предложение для каталога и админки. Основано на текущей Prisma-модели и решениях, подтверждённых в обсуждении. Это не команда массово объединить существующие события: фактические связи между слотами и страницами требуют отдельной карты.

## Главный принцип модели

Не кодировать все свойства события одним большим `type`. Это независимые оси:

1. **Что это за предложение** — категория и подкатегория для каталога, поиска и редакторской очереди.
2. **Как устроено расписание** — разовое, повторяющееся или с открытой датой (`Event.kind`).
3. **Кто управляет данными** — импорт, Daibilet или поставщик (`managementMode`, `sourceLinks`, `supplier`).
4. **Как покупают** — внешний виджет/переход или checkout Daibilet (`purchaseFlow`).
5. **Как показываем и индексируем** — стабильная редакционная `EventPage`, её статус и явный `isIndexable`.

Так пользователь каталога сможет выбрать «Концерты», а редактор при этом увидит, что конкретный концерт импортирован, повторяется и продаётся во внешнем виджете. Эти признаки не должны конкурировать друг с другом.

## Матрица измерений

| Измерение | Значения / примеры | Где хранить сейчас | Влияет на каталог | Влияет на расписание | Влияет на URL / SEO |
|---|---|---|---|---|---|
| Категория | Концерты, Театр, Экскурсии, Музеи и выставки, Мастер-классы, Детям и семье, Активный отдых, Ночная жизнь, Фестивали | `Category` | Да: верхний фильтр и навигация | Нет | Может создавать отдельную SEO-подборку при наличии спроса и содержимого, но не меняет EventPage саму по себе |
| Подкатегория | Джаз, классика, рок; драматический театр, мюзикл; пешая/автобусная/речная экскурсия и т. п. | `Subcategory`, `Event.primarySubcategoryId`, `EventSubcategory` | Да: быстрые фильтры, поиск, админские очереди | Нет | Не создаёт URL события автоматически |
| Формат расписания | Разовое, повторяющееся, открытая дата | `Event.kind` (`SINGLE`, `RECURRING`, `OPEN_DATE`) | Фильтр/бейдж только если полезен покупателю | Да | Сам по себе не определяет число индексируемых страниц |
| Управление / происхождение | Импортировано; заведено Daibilet; черновик поставщика; поставщик управляет через API | `managementMode`, `EventSourceLink`, `Supplier`, `SupplierIntegration` | Админские фильтры и действия | Источник истины для слотов и остатков | Импорт не запрещает EventPage. Синхронизация обновляет данные слотов, а не должна удалять стабильную страницу |
| Покупка | Внешняя система (например, Ticketscloud/TEP); продажа через Daibilet | `purchaseFlow`, `EventOffer`, `ProviderLink` | Может определять CTA | Да: виджет/квота/билет | Не определяет индексируемость. Импортируемые продажи остаются у поставщика, финансовый контур Daibilet не включается |
| География | Город события, площадка, адрес; для маршрута — точки отправления/остановки | `primaryCityId`, `venueId`, `EventVenueRouteItem`, `TripDeparture` | Да | Для некоторых форматов определяет конкретный слот/отправление | Город входит в решение о самостоятельной странице и локальном поиске; площадка и адрес показываются отдельно |
| Редакционная страница | Черновик, на проверке, опубликована; индексируется или нет | `EventPage`, `EventPageEvent`, `EventPageRoute` | Список требует редакторской работы | Не владеет билетами и слотами | Да: стабильный slug, редакционный текст, индексируемость, история старых адресов |

## Предлагаемое дерево категорий

Это стартовая таксономия для обсуждения, а не миграция справочника. Названия и глубину следует проверить на реальных запросах и текущем каталоге. Подкатегории добавлять, когда они помогают найти события или ускоряют конкретную редакторскую операцию.

| Верхняя категория | Примеры подкатегорий |
|---|---|
| Концерты | Поп и рок; классика; джаз и блюз; органная музыка; авторская музыка |
| Театр и шоу | Драматические спектакли; комедия; мюзикл; балет и опера; цирк; кабаре и иммерсивные шоу |
| Экскурсии | Пешие; автобусные; речные прогулки; гастрономические; квесты и городские игры |
| Музеи и выставки | Музеи; временные выставки; арт-пространства; планетарии |
| Мастер-классы | Искусство и ремёсла; кулинария; музыка; для детей |
| Детям и семье | Спектакли для детей; семейные экскурсии; интерактивные музеи; игровые программы |
| Активный отдых | Водные активности; спорт; загородный отдых; сезонные активности |
| Фестивали и специальные события | Музыкальные фестивали; городские праздники; тематические события |

Одно событие может иметь одну основную категорию и несколько релевантных подкатегорий. Для скорости каталога фильтровать по стабильным ID категории/подкатегории и индексированным связям, а не плодить отдельные enum-значения и отдельные типы сущности. Неиспользуемые теги не нужны для первого этапа.

### Подтверждённая гастрольная группа

`Сова` — владелец подтвердил один гастрольный продукт в 22 городах. Для каждого города нужна своя EventPage со своим расписанием и предложением; связываем страницы только через `tourGroupId`. Это не основание объединять Event ID или показывать город без действующего предложения.

## Матрица расписания и страницы

| Ситуация | Event и слоты | EventPage | Что видит посетитель | Индексация |
|---|---|---|---|---|
| Разовое событие | Один `Event`, обычно один `EventSession` | Одна EventPage | Информация о событии, площадке/адресе, билетах и времени | Индексировать при опубликованной странице с полезным содержимым и подтверждённой публичной идентичностью |
| Повторяющееся событие | Один `Event`, много `EventSession` | Одна EventPage на устойчивое событие/продукт | Страница события с ближайшими доступными датами; прошедшая дата не должна превращать страницу в 404 | Индексируется EventPage; отдельные URL слотов не продвигаются как самостоятельные страницы |
| Открытая дата | Один `Event`, слот/предложение может не иметь фиксированной даты | Одна EventPage | Страница объясняет условия записи/посещения; доступность и покупка берутся из источника | Индексировать, если предложение реально доступно или страница имеет самостоятельную сезонную/справочную ценность; нельзя объявлять визит подтверждённым по одной оплате |
| Одно шоу заведено билетной системой несколькими карточками в одном городе | Несколько `Event` только если такова фактическая структура источника; связь не выводить лишь из похожего названия | Можно связать несколько Event одной EventPage после проверки, указав основной Event и остальные как варианты/сеансы | Одна страница, варианты покупки/сеансы сгруппированы без потери конкретных площадки, даты, цены и провайдера | Индексируется одна EventPage, если редактор подтвердил тождественность предложения |
| Гастроли по разным городам | События/слоты сохраняют конкретные город, площадку, адрес и поставщика | Самостоятельная локальная EventPage на город; общий контент можно переиспользовать. Страницы связываются явным признаком группы тура (`tourGroupId`), без слияния локальных PDP | На PDP показывается блок смены города/быстрого перехода на другие локальные страницы этой группы. Ссылки ведут на соответствующий город, площадку и расписание; текущая страница и покупка остаются локальными | Каждая городская страница индексируется отдельно только при уникальной локальной ценности и продаваемых/объявленных датах. Группа тура не создаёт общую индексируемую страницу и не меняет canonical локальных PDP |
| Импортированная карточка с неоднозначным совпадением | Сохраняется отдельной; синхронизация и продажи не останавливаются | Временная отдельная EventPage или кандидат с временным slug; связь помечается на проверку | Страница доступна пользователю после синхронизации, даже если текст пока базовый | Доступность не равна индексируемости: сомнительную/тонкую страницу оставить доступной с `noindex,follow` до решения |
| Все даты закончились, событие сезонное/возвращается | EventPage и история связей остаются; старые сеансы закрыты | Страница остаётся стабильной, на ней нет устаревшего CTA покупки | Плашка о завершённой дате и полезный переход к расписанию/похожим событиям; при новом сезоне показываются новые даты | Сохранять индексируемой, если есть самостоятельная ценность и ожидается повторение; иначе оставить 200 и временно `noindex` по редакционному правилу, не удалять автоматически |
| Событие иного характера в той же площадке | Отдельный Event | Отдельная EventPage | Собственное описание и покупка | Самостоятельная страница, если заслуживает её | Не объединять только из-за одинаковой площадки, поставщика или жанрового тега |

## Признак гастрольной группы и переключение города

Гастрольные EventPage остаются самостоятельными локальными страницами. Для связи между ними вводится явная принадлежность к группе тура:

- `EventTourGroup` — редакционная группа тура с внутренним ID и названием для админки; сама по себе не является публичной или индексируемой PDP.
- `EventPage.tourGroupId` — nullable-связь/признак. Если значение пустое, блок смены города не показывается. Если задано, страница является локальной PDP тура.
- Город, площадка, адрес, слоты, цены и покупка берутся с локальной EventPage и связанных с ней Event. Общий текст можно переиспользовать, но локальные факты должны быть своими.
- На PDP блок «Другие города тура» появляется только когда в группе есть минимум две опубликованные локальные EventPage. Текущий город отмечен; остальные пункты ведут прямыми ссылками на их EventPage.
- Группа и переключатель не объединяют события, не меняют canonical, slug, robots или sitemap. Для каждой локальной страницы сохраняются собственные SEO-настройки и URL.
- Добавлять EventPage в одну группу можно только после проверки тура по исполнителю/продукту, программе и фактическому городу. Совпадения названия недостаточно.

Рекомендуемая модель данных:

```text
EventTourGroup 1 ── N EventPage (локальные страницы тура)
EventPage 1 ── N EventPageEvent ── Event (город, площадка, адрес, слоты и офферы)
```

Это отдельный признак для навигации между локальными PDP, а не способ свернуть тур в одну страницу.
## Когда объединять, а когда оставлять отдельные EventPage

**Кандидат на объединение в одну страницу:** одно и то же устойчивое предложение/программа, совпадают исполнитель или продукт, содержание и формат; отличаются только сеанс, слот либо техническая карточка источника. Связь должна быть проверяемой и обратимой.

**Оставлять отдельно:** разные программы одного исполнителя; разные мероприятия одной площадки; разные мастер-классы; разные маршруты/услуги, даже если поставщик общий; гастрольные карточки в разных городах — отдельные локальные страницы по умолчанию.

Практические решения, уже зафиксированные в этой работе:

| Группа | Уже принятое решение | Что ещё нужно сделать |
|---|---|---|
| «Васса» | Это гастроли; страницы и адреса конкретных городов самостоятельные, с общим контентом и переходом между городами | Сопоставить конкретные Event ID и проверить город/площадку каждой карточки |
| «Северная Венеция» | Один поставщик и разные причалы отправления; причалы сами по себе не требуют отдельных EventPage | Сверить, что конкретные рейсы действительно один продукт; сохранить причал и время в варианте/сеансе |
| Иммерсивный мастер-класс | Не объединять в один EventPage | Сохранять отдельные страницы при похожих названиях, пока не подтверждено, что это одна программа |
| «Гамма Джаз» | Разные мероприятия одной площадки не сливать в одну страницу | Разбирать возможные дубли отдельных карточек только по программе и сеансам |
| «Воскресный джазовый вечер» | Не объединять его с другими событиями площадки | Разбирать возможные дубли отдельных карточек только по программе и сеансам |

Эти решения **не являются открытыми вопросами для повторного обсуждения**. Открыта только привязка конкретных исходных Event ID и исторических URL к уже выбранным страницам.

## Рекомендуемая структура связей

```text
Category 1 ── N Subcategory
     │                │
     └──── Event (каталоговый объект, город/площадка/источник/способ продажи)
                 ├── 1 ── N EventSession (дата, остаток, внешний ID)
                 ├── 1 ── N EventOffer (цена/категория/виджет поставщика)
                 ├── N ── 1 Supplier / Source links
                 └── 0 ── 1 EventPageEvent ── N ── 1 EventPage
                                                     ├── стабильный slug и контент
                                                     ├── SEO и ручной isIndexable
                                                     └── 0 ── N EventPageRoute (старые/кандидатные URL)
```

В текущей модели каждый Event привязывается максимум к одной EventPage; EventPage может агрегировать несколько Event. Слоты остаются под Event и не становятся отдельными редакционными страницами. Таблица исторических маршрутов пока служит картой/аудитом и не должна сама по себе запускать редиректы.

## Правила поиска и скорости работы

- В каталоге верхняя категория — быстрые крупные фильтры; подкатегория — более точное уточнение.
- В админском реестре нужны фильтры по `categoryId`, `primarySubcategoryId`, расписанию, management mode, поставщику, городу, статусу EventPage и статусу/состоянию слотов.
- Начать с текущих `Category`, `Subcategory` и индексов `Event.status`, `Event.primaryCityId`, `Event.categoryId`, `Event.supplierId`, `EventSession(eventId, isActive, startsAt)`; измерить запросы на реальном каталоге до добавления новых индексов.
- Не создавать отдельную таблицу или enum на каждый подтип. Новый структурный тип оправдан, только если у него собственные обязательные поля, операции или проверяемая бизнес-логика (например, маршрут/отправление для речной прогулки уже оформляется отдельно).
- Подкатегории не должны автоматически менять `Event.kind`, источник продаж, поставщика, URL или SEO.

## SEO: безопасные состояния страницы

| Состояние | HTTP / доступность | Robots / sitemap / canonical |
|---|---|---|
| Нет утверждённого объединения или исторической карты | Не менять старые URL и fallback | Не переключать canonical, sitemap и массовые редиректы |
| Опубликована стабильная EventPage, но контент/связь ещё проверяются | Страница доступна по стабильному адресу; при необходимости `noindex,follow` | Не добавлять в sitemap; canonical не переназначать с прежнего URL до карты |
| Проверенная EventPage с полезным текстом и актуальным предложением | HTTP 200 | `index,follow`; canonical на стабильную EventPage; включать в sitemap только после проверки URL mapping |
| Все сеансы завершены | HTTP 200, страница остаётся полезной | Решение по индексации зависит от сезонности/самостоятельной ценности, а не от календарного месяца и не только от числа слотов |
| Старая страница слота | Fallback/сохранение до разбора URL | После карты — точный 301/308 на соответствующую EventPage только там, где связь доказана; неизвестный URL не отправлять на случайную страницу |

Страница должна явно различать **доступна пользователям** и **готова к индексации**. Импортированные новые события должны появляться после синхронизации; редакционная очередь управляет полнотой, связями и индексированием, а не тем, увидит ли покупатель событие вообще.

## Что надо решить до масштабного применения

1. Утвердить названия и дерево категории/подкатегории на выгрузке текущего каталога; сохранить исторические значения и не менять их массово автоматически.
2. Уточнить, будет ли «каталоговый подтип» всегда простой `Subcategory` или некоторым подтипам нужны отдельные поля/валидаторы.
3. Составить карту Event → EventPage → исторические URL из Search Console и Вебмастера.
4. Подтвердить правила группировки карточек Ticketscloud/TEP и гастрольных событий на реальных данных.
5. Только после проверки карты включать canonical/sitemap/301/308. До этого сохранять fallback и прежние адреса.
