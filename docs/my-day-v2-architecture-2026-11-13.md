# My-day v2: аудит текущей архитектуры и план перехода

**Дата:** 2026-11-14  
**Основа интерфейса:** `my-day_v2.html`  
**Статус:** V2 реализована в web: рабочая область следует шаблону со сдержанной тёмной шапкой, прокручиваемым списком маршрута и большой настоящей OSM-картой; сохранены реальные каталоговые точки и flat-list. Редакционные маршруты читаются из опубликованных записей с fallback на городские пресеты; личный план сохраняется в аккаунт и открывается по приватному `?plan=...`; добавлен защищённый admin API для публикации. Миграция применена к локальной `daibilet_baseline`; production не менялся.

## Что уже работает в production-приложении

Каноническая страница - `apps/web/app/my-day/page.tsx`, UI и клиентская логика - `apps/web/src/components/DayRoutePanel.client.tsx` и `apps/web/src/components/my-day/`.

- План хранится у гостя в `daibilet:dayRoute` (localStorage). Сценарии-снимки хранятся отдельно в `daibilet:my-day-scenarios`.
- Готовые именованные пресеты хабов открываются по `?route=<preset-id>` и загружаются как отдельная копия. Сначала ищется опубликованная запись в БД, затем используется статический `CITY_INFO` fallback. Быстрый каталоговый сценарий принимает `?city=...&items=...`; старый `?day=...` остаётся fallback. При конфликте приоритет: `plan` > `route` > `items` > `day`. Точки разрешаются через `/api/day-route/matches`.
- На PDP и хабах есть CTA добавления/замены точек. Текущие данные и каталог остаются источниками карточек.
- Доступны перестановка мышью/клавиатурой, изменение длительности, оптимизация порядка, оценка времени и расстояния, режимы пешком/авто, soft-планирование по часам, реальные OSM-карты, мобильный лист карты, поиск, готовые сценарии, свои точки и PDF.
- Публичная ссылка создаётся через `DayRouteShare` с коротким непредсказуемым кодом (`/d/{code}` или `/m/{slug}`). Она переносит каталоговые locators и используется для шаринга. Это отдельная функция от локального сохранения.

## Границы данных и доступа

- `DayRouteShare` уже существует, но предназначена для публичного snapshot-шаринга. У неё нет поля владельца или ссылки на исходный маршрут; публичный POST сейчас не требует пользовательской авторизации. Использовать эту таблицу как личное облачное хранилище нельзя.
- `TripPlan`/`TripPlanItem` связаны с `SiteUser`, билетами и поездками. Это коммерческая/операционная модель, а не планировщик прогулки. Повторно использовать её для My-day без отдельного контракта нельзя.
- `EventPage`/`EventPageRoute` покрывают редакционные страницы событий, не городские маршруты.
- Пользовательская авторизация уже есть: `UserAuthProvider`, access token, refresh-cookie и `/api/user/auth/me` поверх `SiteUser`. Это можно переиспользовать для приватных планов; админ Basic Auth остаётся отдельным контуром и не заменяет user session.
- Реализованы `/api/admin/my-day/routes` под admin Basic Auth для списка и upsert черновика/публикации, а также авторизованные `/api/day-route/plans` для создания/обновления и чтения владельцем. Личные планы требуют входа; гостю остаётся localStorage и существующая публичная snapshot-ссылка. Приватная ссылка `?plan=...` не является публичным share.

## URL и приоритеты для будущего расширения

Сохранить текущую совместимость `city + items` и `day`. После добавления новых идентификаторов применять эксклюзивный порядок:

1. `plan` - открыть конкретную сохранённую персональную копию; игнорировать остальные payload-параметры.
2. `route` - загрузить опубликованный редакционный маршрут; игнорировать `items` и локальный контекст города.
3. `items` - быстрый маршрут из каталога; `destination` задаёт город планирования, `origin` применяется только при явно поддержанном пути из отправления.
4. `day` - legacy fallback, когда более новый payload отсутствует.
5. Без payload - восстановить текущий локальный план/выбор города по существующему поведению.

`city` остаётся legacy-городом/контекстом, а не доказательством города каждой выбранной точки. В частности, не отклонять комбинацию `city=perm` с объектами Москвы: нормализовать точки по их catalog identity. Параметр `ref` не участвует в выборе или содержимом маршрута.

## Предлагаемые этапы

1. **URL и слои данных:** добавить чистые parser/resolver функции и тесты для precedence/старых ссылок; `route` должен разрешаться только в опубликованную запись. Никаких изменений SEO/canonical для `/my-day`.
2. **Редакционные маршруты:** схема, опубликованный runtime resolve и защищённый admin API подготовлены. Следующий шаг для редакционной команды - форма управления в админке и наполнение утверждёнными маршрутами.
3. **Личный план:** отдельная модель от `ExternalOrder`, `CheckoutOrder` и `TripPlan`. Авторизованные планы сохраняются и обновляются в аккаунте; гостям остаются localStorage и публичный snapshot-share без облачного гостевого владения.
4. **UI V2:** развивать существующие `MyDayShell`, `MyDayToolbar`, picker, itinerary и map components. Не переносить SVG-карту, фейковые данные, имитацию сохранения/копирования или взаимоисключающие с текущим каноном секции периода дня. Оставить flat route list, OSM и настоящие действия.
5. **Проверка интеграций:** проверить PDP → My-day, city hub → My-day, article → route, My-day → PDP/EventPage, старые `city/items` и `day`, мобильные режимы, публичный share, пустые/удалённые locators.

## Ограничения и ввод в эксплуатацию

Перед включением DB-маршрутов и аккаунтного сохранения нужно отдельно просмотреть `packages/db/prisma/schema.prisma`, миграцию `20261113120000_my_day_routes_and_plans` и сгенерированный клиент, затем применить миграцию штатным `pnpm db:deploy` владельцем. До этого новые DB endpoints не заработают на окружении с прежней схемой; статический fallback и локальные сценарии остаются доступны. Production deploy в этой итерации не выполнялся.
