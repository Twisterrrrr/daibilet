# Admin MVP from Lovable/Admin V4

## Вывод

Admin V4 из старого проекта стоит использовать как UX/UI-референс для новой админки. Текущий статический `apps/admin` в новом проекте хорошо описывает MVP-сценарии, но визуально и операционно слабее: Lovable/V4 лучше решает операторскую работу через плотные таблицы, быстрые фильтры, статусы готовности, явные проблемы и переходы в нужную вкладку карточки.

Новая админка должна взять из V4 не весь продукт, а рабочие паттерны:

- shell с боковым меню, зонами навигации и верхней строкой поиска;
- restrained admin-палитру, токены и компактные компоненты;
- `PageHeader`, `FilterBar`, `QuickFilterBar`, `DataTableShell`;
- `StatusBadge`, `SourceBadge`, readiness/SEO/checklist blocks;
- URL-state фильтры для списков;
- queue workflow: "следующее событие с проблемой";
- `returnTo` при переходе из списка в карточку;
- deep-link на вкладку карточки по типу проблемы;
- явное разделение source-managed данных и ручных override;
- `InfoNote`/`ManagedBySource` для объяснения, какие поля нельзя править напрямую.

## Структура MVP

### 1. Dashboard

Оставить как операционный центр, а не декоративную страницу.

Блоки:

- готовность каталога;
- события, требующие внимания;
- свежий импорт и ошибки синка;
- покрытия лендингов;
- кандидаты на объединение площадок;
- внешние заказы, когда включим order sync.

### 2. Events Workbench

Главный рабочий экран MVP.

Фильтры:

- источник: Ticketscloud / Teplohod;
- статус публикации;
- требует модерации;
- без категории;
- без подкатегории;
- без города/площадки;
- без цены;
- без картинки;
- нет активных сеансов;
- нет offer/widget/deeplink;
- возможный дубль.

Таблица:

- событие;
- источник;
- город/регион;
- площадка/meeting point;
- категория и подкатегории;
- дата/тип расписания;
- цена от;
- offer/purchase readiness;
- проблемы;
- статус.

### 3. Event Detail

Взять V4-подход с вкладками.

Вкладки:

- overview;
- classification;
- schedule;
- venue;
- media;
- offers;
- source/raw.

Нужные элементы:

- исходные данные поставщика рядом с нормализованными;
- ручной override без стирания импортированных данных;
- checklist готовности к публикации;
- подсказки, почему событие не попадает в каталог или лендинг;
- переход к следующему событию из текущей очереди модерации.

### 4. Venues

Из V4 оставить табличный экран площадок, но расширить под импорт.

Нужно добавить:

- `venue_kind`: venue, museum_art_space, theater, concert_hall, club_bar_restaurant, pier, meeting_point, outdoor_location, sport_activity_space, attraction, online, other;
- `page_status`: none, candidate, published, hidden;
- imported aliases;
- merge candidates;
- confidence score;
- needs review;
- количество событий и источников;
- признак "это просто точка сбора".

### 5. Landing Rules

LandingDetail из V4 полезен как модель: coverage, matching, SEO, blocks, diagnostics.

Для MVP лендинг должен быть не ручной подборкой, а правилом выборки:

- города/регионы;
- категории;
- основные подкатегории;
- дополнительные подкатегории;
- теги;
- price/date/session constraints;
- include/exclude keywords;
- source constraints;
- venue kind constraints;
- mandatory features.

Админка должна показывать:

- сколько событий найдено;
- какие события вошли;
- какие почти вошли, но не прошли условие;
- какие поля мешают попаданию в лендинг;
- табличный preview публичного вывода.

### 6. Sources / Sync Health

Минимальный экран для MVP:

- последний sync по источнику;
- сколько записей получено;
- сколько создано/обновлено/пропущено;
- ошибки;
- кнопка ручного запуска;
- ссылка на raw records.

### 7. Mapping Inbox

Нужен рано, потому что качество каталога зависит от типизации.

Очереди:

- неизвестная source category;
- неизвестная source subcategory;
- неоднозначный город;
- неоднозначная площадка;
- возможный дубль события;
- событие без purchase offer.

### 8. External Orders

Оставить как второй шаг после order sync.

Важно сохранить принцип V4:

- мы показываем внешний статус;
- не проводим платежи;
- не делаем автоматические возвраты;
- можем хранить buyer snapshot, external order id, ticket ids, статус и историю обновлений.

## Что не переносить в MVP

- supplier cabinet;
- внутренний checkout;
- YooKassa/платежный контур;
- возвраты как полноценный операционный модуль;
- promo/coupons;
- articles/reviews/content-heavy SEO;
- несколько версий админки;
- сложные роли и permissions;
- самостоятельный SEO-раздел вне лендингов/городов;
- one-off landing components вроде отдельной ручной сборки под один праздник.

## Техническая рекомендация

Для новой версии админку можно делать как отдельное приложение `apps/admin`.

Оптимальный путь:

- public: Next.js;
- admin: Vite React SPA или Next.js app, если хотим единый стек;
- backend: Fastify/Nest-lite API;
- db: Prisma + Postgres;
- shared ui: вынести только реальные общие primitives после первого рабочего экрана.

Если цель быстро получить операторский инструмент, Vite React для `apps/admin` выглядит легче и ближе к текущему Admin V4.

## Первый перенос

Первым экраном стоит собрать не dashboard, а `Events Workbench`, потому что именно он проверит всю модель:

- импорт;
- нормализацию;
- категории;
- города/регионы;
- площадки;
- offers/widgets;
- проблемы качества;
- попадание в лендинги.

После него dashboard станет честной сводкой, а не набором моковых счетчиков.
