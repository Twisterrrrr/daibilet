# Дайбилет: QA и деплой перед первыми продажами

Дата подготовки: 2026-06-20

Цель документа: быстро пройти последние вопросы перед стартом продаж, не раздувая MVP. Мы запускаем агрегатор с покупкой через виджеты Ticketscloud и Teplohod.info. Финансовый контур остается на стороне билетных систем; у нас хранятся факт покупки, покупатель, номер/статус билета и операторские заметки.

## Статус На Сегодня

- Ticketscloud: свежий full sync прошел, Source Health зеленый.
- Teplohod.info: локально работает через fixture bridge и `TEP_API_URL`, Source Health зеленый.
- Public catalog: показывает сгруппированные события, а не отдельные слоты.
- TC slots: каждый слот в сгруппированной карточке ведет в свой TC `event`.
- Teplohod event page: отдает `widgetPayload`, ближайшие сеансы и реальные категории билетов.
- Admin: есть Sources, Events, Venues, Cities, Landings, Buyers, Orders.
- Git: локальный репозиторий есть, remote пока не настроен.

## QA Вопросы К Владельцу

Перед smoke-тестами нужно ответить:

1. Какие домены используем на старте?
   - public: `daibilet.ru` или временный поддомен?
   - admin: `admin.daibilet.ru` или закрываем админку по IP/basic auth?
   - api: `api.daibilet.ru` или backend под тем же доменом через `/api`?

2. Что считаем успешной первой продажей?
   - пользователь открыл карточку события;
   - выбрал дату/слот;
   - открыл виджет поставщика;
   - купил билет у поставщика;
   - заказ появился/обновился у нас в admin;
   - оператор видит статус и может вручную добавить номер билета, если API заказа еще не синхронизировался.

3. Что скрываем до запуска?
   - неготовые лендинги;
   - пустые города/площадки;
   - события без будущих сеансов;
   - события без цены от 100 рублей;
   - события без purchase URL/widget.

4. Кто делает smoke?
   - тестировщик проходит public и admin маршруты;
   - владелец проверяет бизнес-смысл контента, цены, названия, посадочные;
   - Codex закрывает найденные баги;
   - ментор помечает блокеры и не-блокеры.

5. Какие легальные/контактные данные нужны на сайте?
   - контакты поддержки;
   - условия покупки через партнерские виджеты;
   - политика обработки персональных данных;
   - текст о том, что оплата и чек формируются билетной системой.

## Smoke Public

### Главная

- Открыть `/`.
- Проверить, что счетчики событий, городов и площадок появляются без длинной пустой паузы.
- Проверить меню: каталог, города, лендинги/подборки, мои покупки.
- Проверить footer: все ссылки либо рабочие, либо скрыты до запуска.
- Проверить hero-текст: без технических фраз, без "по данным источника".

Ожидаемый результат: пользователь за 5-10 секунд понимает, что можно купить билеты на события/экскурсии, и видит путь в каталог.

### Каталог

- Открыть `/events`.
- Проверить верхние фильтры: город, категория, дата, цена, источник.
- Проверить, что карточки не повторяют один и тот же слот как отдельное событие.
- Проверить, что у карточки есть цена от 100 рублей и ближайшие слоты.
- Проверить TC карточку с несколькими слотами: каждый слот открывает свой `event` в Ticketscloud.
- Проверить Teplohod карточку: кнопка покупки ведет в Teplohod/widget flow.

Ожидаемый результат: каталог быстрый, фильтры не ломают URL, повторяющиеся события выглядят как одна карточка со слотами.

### Карточка События

- Открыть TC событие.
- Проверить hero: без длинного описания.
- Проверить описание: HTML очищен, нет `<p>`, `<br>`, технической разметки.
- Проверить город и площадку: есть ссылки на страницы города/площадки.
- Проверить ближайшие 5 сеансов, не простыню всех дат.
- Проверить категории билетов и цены.
- Нажать покупку: открывается виджет поставщика.

Повторить для Teplohod события.

Ожидаемый результат: с карточки можно понять место, город, цену, ближайшее расписание и перейти к покупке без возврата в каталог.

### Города, Площадки, Лендинги

- Открыть город, например `/cities/sankt-peterburg`.
- Проверить, что это "Страница города", не сухая таблица.
- Проверить контент-блоки, быстрые подборки, каталог событий.
- Открыть площадку.
- Проверить "Что важно знать о {название}".
- Проверить, что события на странице площадки не идут полотном одинаковых слотов.
- Открыть лендинг, например речные прогулки.
- Проверить hero, быстрые фильтры, табличный/быстрый вывод ближайших предложений.

Ожидаемый результат: SEO-страницы выглядят как полезные посадочные, а не как техническая выгрузка.

### Мои Покупки

- Открыть страницу "Мои покупки".
- Проверить поиск по телефону/email/номеру заказа.
- Проверить пустое состояние.
- Проверить, что нет слова "внешние" для покупателя.

Ожидаемый результат: покупатель видит человеческую страницу поиска покупки, без внутренних терминов.

## Smoke Admin

### Источники

- Открыть `/sources`.
- Проверить Ticketscloud: статус `ok`, свежий sync, нет открытых проблем.
- Проверить Teplohod.info: статус `ok`, свежий sync, нет `TEP_BRIDGE_NOT_CONFIGURED`.
- Нажать sync TC.
- Нажать sync Teplohod.
- Проверить, что ошибки показываются честно, без моковых данных.

Блокер: источник красный перед запуском, если планируем продавать его события.

### События

- Открыть `/events`.
- Проверить, что повторяющиеся TC события сгруппированы в одну карточку/строку.
- Проверить фильтры "нужно внимание", "к публикации", "покупка не готова", "без фото", "в лендингах".
- Открыть карточку события.
- Проверить вкладки: контент, медиа, SEO, расписание, продажи.
- Проверить readiness issues: цена, покупка, будущие сеансы, категория, площадка, изображение.
- Проверить, что source-managed поля не перетираются ручными override.

Блокер: событие выглядит готовым, но не имеет purchase URL или будущего сеанса.

### Заказы И Покупатели

- Открыть `/orders`.
- Проверить лаконичный вывод: заказ, событие, статус, действия, покупатель только если есть.
- Проверить короткий номер заказа.
- Проверить русские статусы.
- Создать/обновить ручной билет, если это предусмотрено текущим UI.
- Открыть `/buyers`.
- Проверить связь покупатель -> покупки.

Блокер: оператор не может понять, что куплено, у кого и какой статус билета.

## API Smoke

Проверить HTTP:

- `GET /api/admin/sources`
- `GET /api/public/stats?refresh=1`
- `GET /api/public/events?limit=20&refresh=1`
- `GET /api/public/events/{slug}`
- `POST /api/v1/tep/sync`
- `POST /api/admin/sources/ticketscloud/sync`
- `POST /api/admin/orders/sync`

Минимальные ожидания:

- public stats cold: до 300-500 ms;
- public catalog warm: до 100 ms;
- public home cold: желательно до 1000 ms, допустимо временно до 2000 ms перед первым запуском;
- ошибки backend не маскируются моками в admin.

## Деплой: Что Нужно От Владельца

1. Сервер в РФ.
   - Ubuntu 22.04/24.04.
   - 2 CPU, 4 GB RAM минимум для MVP.
   - Доступ по SSH.
   - Белый IP, который можно отдать/подтвердить для Teplohod.info.

2. Домены и DNS.
   - `daibilet.ru`.
   - Решить схему: `daibilet.ru`, `admin.daibilet.ru`, `api.daibilet.ru`.
   - Доступ к DNS, чтобы поставить A-записи на сервер.

3. Секреты и env.
   - `DATABASE_URL`.
   - `TICKETSCLOUD_API_TOKEN` или `TC_API_TOKEN`.
   - `TICKETSCLOUD_WIDGET_TOKEN` или `TC_WIDGET_TOKEN`.
   - `TEP_API_URL` для боевого bridge/API.
   - `TEP_WIDGET_ID`.
   - `TEP_WIDGET_BASE_URL`.
   - `VITE_DAIBILET_API_URL`.
   - `VITE_DAIBILET_PUBLIC_URL`.
   - временный admin password/basic auth или IP allowlist.

4. Git online.
   - Нужен не "каталог", а приватный репозиторий.
   - Можно использовать существующий `Twisterrrrr/daibilet_tickets`, если он будет основным.
   - Либо создать чистый приватный `Twisterrrrr/daibilet` / `daibilet`.
   - После этого локально подключить `origin` и пушить `main`.

5. CI/CD.
   - Для запуска за неделю лучше thin CI/CD:
     - GitHub Actions: typecheck/build.
     - Deploy job по SSH на сервер.
     - На сервере: pull, install, build public/admin, restart backend.
   - Не надо сейчас городить Kubernetes или сложный Docker Swarm.
   - Docker нужен минимум для Postgres и, возможно, для backend после стабилизации.

6. Доступы для проверки.
   - тестовый пользователь/телефон/email для "Мои покупки";
   - тестовая/минимальная реальная покупка через TC;
   - тестовая/минимальная реальная покупка через Teplohod после белого IP;
   - контакт тестировщика, кто пройдет smoke.

## Рекомендация Ментора

Перед первым продакшен-деплоем не добавлять новые крупные фичи. Допускаются только:

- исправления покупки;
- исправления свежести источников;
- исправления пустых/битых страниц;
- исправления админских блокеров для оператора;
- минимальная защита админки;
- деплойная автоматизация.

Не блокировать старт из-за:

- идеального дизайна всех лендингов;
- полноценного блога;
- supplier кабинета;
- сложной SEO audit системы;
- внутреннего checkout;
- финансового контура.
