# Передача UI-работ по админке Cline

Дата: 2026-10-13. Канон продукта: [admin-operations-bible-2026-10.md](./admin-operations-bible-2026-10.md). Рабочая ветка prod-каталога: `feat/next-monorepo`; Next-админка — `apps/web/app/(admin)/admin`. Финконтур находится в отдельном checkout/host и не должен меняться в UI-итерациях.

Для UI Places и очереди сверки PDP использовать отдельный [словарь и handoff Places](./places-taxonomy-cline-handoff-2026-10.md).

## Когда подключать Cline

Сейчас. Начать с оболочки и рабочих текстов. Единый реестр заказов уже закоммичен в каталожной ветке (`090a44ef6`, `3848e74d6`), а групповой фильтр оплаченных внутренних заказов — в finance-ветке `codex/stage0-admission-ticket-core` (`32532dc5a`). Эти изменения ещё требуют согласованного выпуска: finance API → catalog API → Next web. До выпуска проверять UI локально/в preview и не объявлять live-фильтр завершённым.

## Владелец областей

| Область | Ответственный | Граница |
|---|---|---|
| Next admin shell, таблицы, фильтры, карточки, mobile, доступность, тексты | Cline | `apps/web/app/(admin)/admin`, `apps/web/src/components/admin`, точечные UI helpers |
| Данные заказов из двух API, DTO, статусы, supplier/finance/support backend, миграции | Codex | `apps/web/src/server/admin-orders-data.ts`, `apps/backend`, `packages/contracts`, `packages/db`, finance branch |
| Приёмка пользовательских сценариев, финансовые smoke и выпуск | Codex + владелец | Проверка на реальных тестовых данных и согласованный deploy |

Если UI требует нового поля, Cline описывает DTO gap с примером объекта и нужным состоянием интерфейса. Codex добавляет контракт и API; Cline подключает его следующей итерацией. Не вводить локальные догадки о статусе платежа, билета, публикации или балансе.

Настройки ролей пока проектируются в продуктовой библии: общий Basic Auth не различает сотрудников. Не добавлять работающие на вид переключатели модулей или фильтрацию меню по роли до персональной авторизации и серверной проверки прав в catalog/finance API. Текущую статическую секцию «Роли (UX-контур)» в Настройках при очередной UI-итерации обозначить как план или заменить ссылкой на документацию, чтобы она не выглядела действующим ACL.

## Порядок итераций

Одна итерация — один reviewable diff/ветка или серия небольших коммитов. Перед новой итерацией Codex принимает предыдущую: проверяет данные и сценарий, сообщает конкретные замечания, Cline исправляет. Не вести параллельные правки одного файла.

| № | Cline | Codex параллельно | Приёмка |
|---|---|---|---|
| 1. Оболочка (1–2 дня) | Группировка существующего меню, понятные названия, мобильная навигация, breadcrumb/возврат, удалить устаревшие технические тексты | Согласует map маршрутов, проверяет скрытые зависимости | Все действующие маршруты доступны; нет пустых пунктов и `ECR`/`Hero` в навигации |
| 2. Заказы (2–3 дня) | Полирует единый реестр, компактную строку, быстрые статусы, сброс фильтров, сохранение URL, одинаковую структуру карточек | Выпускает finance + catalog + web в правильном порядке; проверяет totals и возврат | Внутренний/внешний заказ ищется в одном окне; «Оплачены» одним нажатием; ошибка API видна |
| 3. Каталог (3–4 дня) | События как workbench: готовность, проблемы, вкладки карточки, source vs override; затем площадки/города, кандидаты и preview merge | Даёт реальные readiness/merge DTO и ограничения записи | Оператор проходит очередь → карточка → исправление → следующая задача; импортные данные не перетираются |
| 4. Поставщики и входящие (2–3 дня) | Реестр/карточка поставщика, типизированные входящие черновиков и изменений по готовым API | Supplier DTO, CREATE/venue/supplier draft contracts, audit | Нет фиктивных approve/apply; статус и источник заявки понятны |
| 5. Поддержка и приёмка (1–2 дня) | Очередь обращений и карточка по согласованному контракту; visual/mobile pass | Support model/API, роли, связка с заказом и возвратом; smoke | Обращение связано с объектом и ответственным; история видна; нет подмены refund обращением |

Срок двух недель — цель для операционного MVP. Если backend новых черновиков или поддержки не готов к соответствующей итерации, Cline продолжает независимые рабочие экраны. Нельзя закрывать итерацию одной макетной страницей. SEO-отчёты, массовый merge, ЭДО и произвольные API-коннекторы остаются следующими выпусками.

### Уточнение к итерации 2: внутренний заказ через API поставщика

Не вводить третий взаимоисключающий финансовый канал «API». Если покупатель платит Daibilet, заказ относится к продажам Daibilet независимо от того, кто выпускает билет. В строке и карточке покупки оставить место для отдельных подписей «Оплата» и «Билет/исполнение»; для будущего API-исполнения предусмотреть состояние «оплачен, ждём билет от поставщика» и ошибку выпуска. Пока DTO не передаёт достоверный способ исполнения, не определять его по `sourceCode`, названию поставщика или внешнему ID. Наличие внешнего ID не означает, что деньги принимал поставщик. API-адаптер и его операции в эту UI-итерацию не реализовывать; Codex подготовит проекцию и статусы отдельно.

В API-сценарии оплату принимает Daibilet, но единый checkout UI пока не вводится: у поставщика может быть собственный экран/маршрут покупки через адаптер. Сплит и полное получение денег с последующим расчётом — варианты settlement, а не интерфейса покупки. Квота/открытый слот должны отражаться как доступность продажи, а подтверждение выпуска билета — отдельным статусом после оплаты. Не показывать номер или QR по одному факту успешного платежа.

## Ежедневный обмен

1. Cline сообщает до правок: базовый SHA, точные файлы, сценарий и DTO gap.
2. Codex подтверждает границу API и сообщает, какие файлы/контракты меняются у него. При пересечении файлов сначала развести изменения.
3. Cline делает маленький diff, проверяет lint/typecheck и сценарий desktop/mobile, присылает SHA, изменённые файлы, скриншоты ключевых состояний и список непроверенного.
4. Codex проверяет статусную семантику, отсутствие пустых метрик и финансовых действий для внешних заказов; запускает адресные тесты и интегрирует.
5. После интеграции — общий smoke и выпуск по проектному cadence. На следующую итерацию переходить после принятия предыдущей.

## Переключение на ЛК поставщика

После приёмки итераций 1–4 админки фиксируем общий словарь статусов, supplier DTO, роли и условия продажи. Затем Cline переходит на supplier UI отдельными срезами:

1. **Read-first:** обзор, мои события/площадки, заказы, баланс, отчёты/документы, реквизиты — только реальные данные и разрешённые действия.
2. **Черновики:** новое событие/площадка и изменение существующих объектов, статус модерации и комментарий администратора; сначала backend state machine и audit.
3. **Вывод средств и поддержка:** запрос на доступный к выводу баланс после состоявшегося заказа, история заявок, обращения в поддержку и связка с заказом.
4. **API-подключение:** статус адаптера и паспорта подключения, ошибки обмена, правила ID/номера/QR билета. Секреты не показывать в браузере.

Критерий переключения: администратор уже может увидеть и обработать то, что поставщик создаёт в ЛК. Не открывать поставщику форму, для которой в админке нет очереди и решения.
