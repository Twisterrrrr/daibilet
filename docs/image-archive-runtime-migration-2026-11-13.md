## Целевая структура архива

```text
Daibilet_images/
├── main/{hero,tiles}/
├── cities/<city>/{preview,hero/night,identity,routes,suburbs}/
├── blog/<article>/{hero,article/inline,og}/
├── places/<city>/<place>/{card,hero,gallery}/
├── events/<provider>/<event-id>/{poster,hero,gallery}/
├── collections/<collection>/{hero,card,items}/
├── banners/{main,cities,blog,events,collections}/
├── shared/
└── provenance/
```

Перекладка выполняется после фиксации текущего облачного снимка. Манифест сохраняет исходный путь, контрольную сумму и новый путь архива; одинаковые файлы не копируются повторно. `banners` остаётся отдельной библиотекой для переиспользуемых и будущих баннеров.

## Текущая схема production

Публичные адреса `/images/...` напрямую раздаёт Nginx из постоянного каталога `apps/web/public/images`. Каталог не симлинк, alias не менялся; после очистки он содержит 11 711 файлов и занимает около 2,7 GiB.

В commit `e8b8c286f` deploy scripts больше не копируют изображения из `apps/public` на production и только проверяют постоянный web image root. Этот кодовый commit пока не установлен на production (checkout был `accbec979`). `pnpm web:build` всё ещё вызывает `apps/web/scripts/sync-public-assets.mjs`; он может добавлять отсутствующие в web файлы из оставшегося legacy-дерева, не перезаписывая существующие.

Изображения в `apps/web/public/images` игнорируются Git, кроме точечных исключений. Перед очисткой или новым клонированием нужно сначала включить архив/production-пакет в процесс гидрации web-статики; генератор, который пишет новый файл только в `apps/web`, сам по себе не делает его доступным на CI или production.

В runtime-аудите 849 URL остались без прямого файла: 836 — производные fallback-варианты blog card/thumb/OG, для которых есть fallback-цепочка к оригиналу; 5 — ключи CDN-карты, не локальные пути; 8 — отсутствующие `generated`-картинки событий/мест, уже не найденные ни в локальных, ни в production-снимках. Эти восемь ссылок требуют отдельной проверки данных API. У 72 проверенных city slug все пять без прямого PNG имеют другой действующий вариант (preview или night hero).

Примерно 2 000 файлов production image root не встретились в списке runtime URL. Они не включены в delta и остались на сервере: одного отсутствия в этом аудите недостаточно для удаления.

## Очистка точных production-дублей

На production сравнили содержимое файлов по одинаковым относительным путям в `apps/public/public/images` и `apps/web/public/images`. SHA-256 совпал у 11 610 изображений; из legacy-дерева удалены только эти точные копии — 2 764 720 991 байт (2,575 GiB). Активные файлы в web-каталоге не менялись.

Сохранены 1 605 изображений, которые встречаются только в legacy-дереве, и 17 файлов с совпадающим путём, но разным содержимым. После очистки legacy image root содержит 1 622 файла (~27 MiB), web image root — 11 711 файлов (~2,7 GiB). Перед удалением deploy marker отсутствовал, активный сайт отдавал web image root; после удаления три файла разных категорий проверены через production Nginx и ответили HTTP 200. Web и API активны, health API — HTTP 200. Занятость корневого диска снизилась с 70% до 67%.

## Безопасный порядок миграции

1. Production URL и активный web image root сохранены; exact-hash копии убраны только из `apps/public/public/images`.
2. Следующий кодовый шаг — разнести asset-sync режим сборки и runtime: сборка не должна использовать legacy как неявный источник новых файлов. Перед удалением оставшихся уникальных legacy-версий требуется закончить URL-аудит и проверить восстановление из архива.
3. Отдельно проверить, нужны ли 1 605 legacy-only файлов редакторским и диагностическим скриптам; сейчас они сохранены.
4. Для освобождения места в staging повторить тот же hash-аудит и удалить только точные дубли после smoke на актуальной среде.
5. Перед дальнейшим удалением production-файлов применять runbook `docs/production-network-and-disk-diagnostics.md`, проверять deployment marker, активные процессы и HTTP после изменений.

Удаление бинарников из текущего Git-tree не уменьшает уже опубликованную историю Git. Force-push и переписывание истории не входят в эту миграцию.

Проверить production после следующего штатного deploy на commit `e8b8c286f`, затем спроектировать сокращение staging и его API. Удаление оставшихся уникальных legacy-файлов и бинарников из Git — отдельный этап после URL-аудита и проверки сценария восстановления.
