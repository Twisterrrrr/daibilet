## Целевая структура архива

```text
Daibilet_images/
├── main/{hero,tiles}/
├── cities/<city>/{preview,hero/night,identity,routes,suburbs}/
├── blog/<article>/{hero,article/inline,og}/
├── places/<city>/<place>/{card,hero,gallery}/
├── events/<provider>/<event-id>/{poster,hero,gallery}/
├── collections/<collection>/{hero,card,items}/
├── banners/{main,cities,blog,events,collections}/
├── shared/
└── provenance/
```

Перекладка выполняется после фиксации текущего облачного снимка. Манифест сохраняет исходный путь, контрольную сумму и новый путь архива; одинаковые файлы не копируются повторно. `banners` остаётся отдельной библиотекой для переиспользуемых и будущих баннеров.

## Текущая схема production

Публичные адреса `/images/...` напрямую раздаёт Nginx из `apps/web/public/images`. Новые генераторы и редакторы должны писать только в `apps/web`; `apps/public` и `apps/public/public` считаются read-only legacy. Скрипт `apps/web/scripts/sync-public-assets.mjs` пока читает legacy-дерево как fallback для отсутствующих файлов и копирует их в web. Workflow сборки и production deploy вызывают синхронизацию. Поэтому legacy-источник нельзя удалять до замены этого fallback на проверенную сборку из архива.

Изображения в `apps/web/public/images` игнорируются Git, кроме точечных исключений. Перед очисткой или новым клонированием нужно сначала включить архив/production-пакет в процесс гидрации web-статики; генератор, который пишет новый файл только в `apps/web`, сам по себе не делает его доступным на CI или production.

В архивном runtime-аудите перечислено 11 206 доступных путей-кандидатов. Из них 9 707 есть в текущем `web`-дереве, 1 499 находятся только в `public` и не попадают под текущий Nginx alias; ещё 853 кандидата отсутствуют в обоих деревьях. Это требует сверки ссылок и отдельного решения по пропущенным изображениям до формирования production-пакета. Около 2 022 production-файлов не встретились в runtime-кандидатах; их также нельзя удалять только по этому аудиту.

## Безопасный порядок миграции

1. Дождаться завершения повторной синхронизации Яндекс.Диска и подтвердить в клиенте или облаке наличие нового изображения, манифестов и двух файлов источников.
2. Зафиксировать подтверждённое состояние в summary и журнале. Выполнить round-trip-восстановление выборочных файлов из облака и сверить SHA-256.
3. Переложить архив в структуру выше, обновив пути манифеста; сохранить все прежние source paths и версии с различающимся SHA-256.
4. Построить отдельный версионируемый production-набор только для проверенных URL. Оригиналы из архива в Яндекс.Диске не перекодировать. Для production выбрать формат и параметры по проверке прозрачности, размеров, визуального качества и совместимости с потребителями OG-изображений.
5. Подготовить Nginx/deploy-переход так, чтобы публичные URL `/images/...` оставались рабочими. Сначала держать старую и новую версии рядом; перед переключением проверить HTTP-статусы, `Content-Type`, изображения из каждой категории и отсутствующие пути.
6. Переключить Nginx на новый набор с сохранением прежнего alias/релиза для отката. После smoke-проверки оставить предыдущую версию до окончания окна наблюдения.
7. Убрать копирование оригинального дерева из deploy только после перехода. Перед удалением файлов на production выполнить диагностику диска по `docs/production-network-and-disk-diagnostics.md`, проверить активные ссылки/процессы и убедиться, что предыдущий набор для отката доступен.

Удаление бинарников из текущего Git-tree не уменьшает уже опубликованную историю Git. Force-push и переписывание истории не входят в эту миграцию.

## Следующая задача

Сначала дождаться и подтвердить повторную синхронизацию архива. Затем подготовить проверяемый production-пакет и деплой-путь, сохранив прежние адреса изображений и быстрый откат. Остальные группы грязного дерева в эту миграцию не входят.
