# Хранение и архивирование сеансов Ticketscloud

## Исходный срез production на 03.11.2026 (до архивации)

- `Event`: 139 081 строк. Это события, а не слоты и не счётчик всех когда-либо импортированных записей.
- `EventSession`: 141 353 строк, из них 138 814 относятся к Ticketscloud.
- 92 292 сеанса имеют `endsAt` раньше текущего времени; 91 721 из них уже неактивен или отменён.
- 571 сеанс закончился в дату проверки, 03.11.2026: 349 со статусом `PUBLIC`, 178 — `STAND_BY`. Это не накопившийся исторический хвост.
- 61 завершённый сеанс связан с импортированным билетом. Слот нельзя физически удалять, если он нужен для истории заказа.

Схема `EventSession` раньше не имела полей архива. Синк деактивирует TC-события, исчезнувшие из выгрузок `PUBLIC`/`STAND_BY`, но физически не удаляет их. Публичный каталог отдельно фильтрует расписание по дате. При этом прошедшие записи сохраняются для ссылок и истории.

## Правило

1. Сеансы сохраняются в БД; физическое удаление не применяется.
2. Сеанс Ticketscloud архивируется, если у него есть корректные `startsAt` и `endsAt`, а `endsAt` старше текущего времени минимум на 2 часа. Правило применяется и к уже неактивным/отменённым прошедшим сеансам: архивирование описывает срок жизни расписания и не стирает историю отмены.
3. Сеансы без даты окончания, включая события с открытой датой, автоматически не архивируются.
4. Архив — отдельное состояние (`archivedAt`, `archiveReason=session_ended`), не равное отмене (`cancelledAt`). После срока хранения сеанс получает `isActive=false`, но сохраняется для истории и старых билетов.
5. Если Ticketscloud обновит тот же ID и перенесёт сеанс в будущее, синк снимет архивное состояние и снова активирует сеанс, если он не отменён.
6. Автоархив запускается после успешного полного sync и после успешного точечного sync по Event ID. Ручная команда по умолчанию только считает кандидатов; запись требует явного `--apply`.

Ручные команды:

```bash
pnpm tc:archive-past-sessions                 # только оценить число кандидатов
pnpm tc:archive-past-sessions -- --apply       # применить архивирование
```

## Результат rollout 03.11.2026

- Коммит `ca5d85507` (`feat/next-monorepo`) содержит Prisma-поля, миграцию, архиватор и вызов архиватора после полного и точечного TC sync.
- На staging применены все ожидавшие миграции, включая `20261103170000_event_session_archive`; сервисы web и API ответили HTTP 200.
- На staging архивировано 65 143 сеанса в основном проходе и ещё 3, появившихся после синхронизации; итоговый dry-run — 0. 113 строк `ExternalTicket` связаны с архивированными сеансами; ссылки сохранены, осиротевших ссылок не обнаружено.
- На production применены две ожидавшие additive-миграции: `20261103143000_supplier_place_requests` и `20261103170000_event_session_archive`.
- На production архивировано 92 160 сеансов в основном проходе и ещё 5, появившихся после следующего TC sync. Итоговый dry-run — 0; активных завершённых более чем на 2 часа сеансов не осталось.
- 357 строк `ExternalTicket` связаны с архивированными сеансами. Записи билетов и сеансов сохранены, осиротевших ссылок нет.
- TC catalog sync timer активен. К его service добавлен systemd `ExecStartPost`, который запускает `daibilet-tc-session-archive.service` после успешного sync. Одноразовый архивный сервис использует отдельный worktree коммита `ca5d85507` и production DB credentials; зависимости больше не берутся из staging.
- Production web (`:3001`) и API (`:4000`) после изменений ответили HTTP 200. Приложение не пересобиралось и не перезапускалось: rollout меняет схему/данные и расписание фоновой операции, а не web runtime.
- `Event` остался 139 081; `EventPage` остался 0. Архивирование не создаёт PDP и не меняет URL/canonical/sitemap.

## Гарантии и оставшиеся проверки

- Архивная команда не удаляет заказы, билеты, EventPage, SEO URL или записи сеансов. TC checkout и финконтур поставщика не затрагиваются.
- Перенесённый в будущее тот же TC session ID может быть реактивирован импортёром, если источник сообщает `PUBLIC`/`STAND_BY` и запись не отменена.
- После следующего планового TC sync проверить журнал `daibilet-tc-session-archive.service`: ожидаемый результат — успешный запуск; если за время sync появились завершившиеся сеансы, они будут архивированы.

## Периодическая проверка событий с прошедшим расписанием

Архивация TC-сеансов и проверка готовности самого события — разные процессы. Для второй задачи добавлен read-only отчёт `pnpm events:audit-past`, который группирует события без актуальных сеансов по типу, статусу и источнику активного предложения. `OPEN_DATE` исключён из проверки расписания. Отчёт не меняет статусы, предложения, EventPage, индексируемость, URL, canonical или sitemap.

Снимок production на 03.11.2026, 19:33 MSK:

- 4 650 событий `SINGLE` со статусом `READY` имеют активное предложение и текущий/будущий активный сеанс.
- 17 `SINGLE` `READY` имеют активное предложение, но только прошедшие сеансы Ticketscloud.
- 539 `RECURRING` `READY` имеют активное предложение, но только прошедшие сеансы Ticketscloud.
- Ещё 42 `RECURRING` `READY` имеют активное предложение TEPLOHOD, но вообще не имеют строк `EventSession`; это отдельная очередь проверки источника, а не доказательство прошедшего события.
- Два `SINGLE` `READY` имеют только неактивные будущие сеансы; они не смешиваются с прошедшими.

Для периодического мониторинга подготовлены `daibilet-past-event-audit.service` и `.timer` (ежедневный запуск в 04:30 MSK, после обычного окна TC sync). В staging данные заметно отличаются от production, поэтому staging подходит для проверки выполнения скрипта, но не для принятия решений о конкретных production-событиях.
